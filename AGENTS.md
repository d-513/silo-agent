# Silo Agent

Token-conserving multi-user agent. Each **Bot** is a durable container with a GUI. Architecture: `docs/Description.md`. UI: `DESIGN.md`.

How to build and run: [DEVELOPMENT.md](DEVELOPMENT.md). The DB is Postgres 17 + pgvector (`database_url`, default the dev compose on `localhost:5433`); `docker-compose.dev.yml` runs only Postgres, never the CP. `Makefile` is the command surface — `make help` lists every target. Never start the dev servers yourself; see Dev below.

Operator config: [docs/CONFIGURATION.md](docs/CONFIGURATION.md). Koanf **defaults → `silo.yaml` → `SILO_*` env**. Nested keys use `__` (`SILO_PROVIDERS__OPENROUTER__API_KEY` → `providers.openrouter.api_key`). Admin Settings edits `silo.yaml` (form + YAML editor). Env still wins; the UI warns and disables those fields. Providers carry `api_key`/`base_url`/`cache`/`cache_ttl`; `local` is any self-hosted OpenAI-compatible server (required `base_url`, optional key; Silo never hosts models); `models` is the allowlist, `model` the default (`provider/model`), `model_title` the title model. `providers.openrouter.ignore` (default `DeepInfra`) is sent as OpenRouter `provider.ignore`: some upstreams buffer tool-call arguments into one final chunk, which kills the live `tool_args_chunk` stream of exec_python/terminal/write input. Default model when unset: `openrouter/openai/gpt-5.6-luna`. Default search engine when unset: `duckduckgo_scraper`.

The project should follow test-driven-development. For now end to end testing is not yet to be fully implemented, but the unit tests in Go should test as much as possible using the dummies.

## Shape

- **Package layout:** `internal/app` is the runtime (agent loop and run engine, Bot lifecycle, worker RPCs, the tool gateway with its rules and approvals, subagents) and wires the domains in `app.New`; each domain is a `Service` in `internal/app/<domain>` that owns its RPCs and Bot tools: `access` (who is asking: user on the context, ownership checks, `RowByToken`), `models` (provider clients, model choice, embeddings, thinking, the LLM log), `workspace` (the Bot's files through the worker), `connector`, `drive`, `channel`, `skill`, `artifact`, `knowledge`, `memory`, `automation`, `feed`, `tunnels`, `voice`, `admin`, plus `chats`, `toolarg`, `host` and `run`. A domain never imports package `app`: it takes concrete services it depends on (`models`, `workspace`) and declares the few things it needs from the App in a small `Host` interface (`host.Authorizer`, `host.Runs`, `host.Emitter`; `run.Engine` for starting and steering runs) that `*App` implements. `handler.go` embeds every service into the one `uiHandler`, so their RPCs are promoted instead of re-declared; services are exported fields of `App` (`a.Knowledge`, `a.Models`, …) so tests and tick loops call them directly. A new domain follows the same shape; do not add methods to `App` for something a domain can own.
- **Control Plane (Go):** users, bots, secrets, skills (bodies on `data/skills/`; enablement in Postgres; `ListSkillFiles`/`ReadSkillFile` walk the CP volume, no worker), **security engine** (`internal/security` — catalog of connector.action → title/fields/default; `*` for files/desktop; each secret is `secrets.<name>` not `secrets.get`; unknown MCP actions get a generic prompt), **HTTP MCP client** (`internal/mcpx` — streamable HTTP over a URL or an injected transport), **STDIO MCP sidecars** (one isolated container per attached STDIO connector; `silo-mcp-bridge` **dials the CP** over ConnectRPC `MCPHost.Tunnel` with a per-attachment bridge token and raw-pumps JSON-RPC to its child; curated image or generic Node/`npx` command; structured argv, never a shell; no published port), **agent loop** (the modular `internal/llm` engine: providers `openrouter`/`openai` speak the OpenAI-compatible API, `anthropic` the native Messages API; model ids are `provider/model`; operator allowlist `models`, default `model`, chat override `chats.model`; the system prompt is a base `SYSTEM.md` plus ordered session providers in `internal/app/systemprompt.go` — connectors, skills, channels, then SOUL/CORE MEMORY and the per-run channel note; blocks are ordered stable→volatile with provider cache breakpoints; bots get `list_models`/`switch_model` under the `model` rule), **web search** (`internal/search` — engine registry on the CP; `web_search` chat tool and `silo_runtime.web_search` share `web.search`; MCP stays Python-only), Docker lifecycle = create/start/stop/inspect only (bots and STDIO sidecars). Chat tools and Python `CallTool`/`GetSecret` share `AuthorizeAction`. Approval slip never dumps `args_json` (and redacts `desktop.type` text). `allow_once` is a valid vote. Connector tokens and extra headers stay on the CP. Reserved connector slugs: python, terminal, files, desktop, bot, secrets, skills, web, artifact, channels, chats, model, automations, agents, tasks, tunnels. **Channels** are built-in adapters (`internal/channels`, Telegram via gotd MTProto) that talk to a Bot. One adapter instance is a `Channel` row (per bot, unique name); channel conversations are `Chat` rows tagged `channel_id`+`external_id` (web chats keep `channel_id=''`). Adapters own config (per-channel secrets live as `channel.<id>.<key>` Secret rows, hidden from the Secrets tab and `secrets.*`), dynamic state (`State`: info/QR/select for QR logins and chat pickers), and lifecycle. The Channels tab adds/edits them from adapter-declared fields, with sub-routes `/bots/:id/channels[/new[/:adapter]|/:channelID[/setup]]` so browser back works; `requires_target` adapters (Telegram) bind the row to exactly one chat picked in the Setup menu (`set_target` → `external_id`/`target_title`), and only that chat is read or written. Telegram bot accounts cannot enumerate dialogs (`messages.getDialogs` → `BOT_METHOD_INVALID`), so the picker lists chats the bot has seen (persisted in channel state) and accepts a manually entered `@username`/`t.me` link/id. Adapters declare interactive `Setup` actions (`pick`/`run`/`qr`) and an embedded `GUIDE.md`; a channel that still needs its target shows a blinking **Set up**. The `chats` tool asks the adapter for a channel conversation's history (Telegram `messages.getHistory`) so the Bot can see older messages; bot accounts are refused (`BOT_METHOD_INVALID`), so it falls back to the local run log (adapter flags `noHistory` per channel and stops retrying). `present`/`artifact` on a channel attach the real bytes (`workspace.Service.Attachment`; a skill directory is zipped by `artifact.Service.ZipAttachment`), and the Telegram adapter uploads them with `uploader.FromBytes` + `.File`. A channel with `inbound=false` is send-only (tools only). Channel workers start from `channel.Service.Reconcile`; adapter `Start` is live-only — never backfill missed messages. The `channel` chat tool sends (default the origin channel; rule key `channels.<channelID>`); `chats` reads history through the adapter for channel conversations and the DB for web chats (rule `chats.read`); `silo_runtime.send_channel`/`read_chats`/`feed` are the Python paths. Python and chat tools should be roughly equivalent for any action that is not chat-only: each built-in shares one function that authorizes inside it (`channel.Service.SendTool`/`ChatsTool` and `runShared` in `internal/app/builtins.go`) and `callBuiltin` routes the Python `call` to it. `sharedTools` maps chat tool → `connector.action` for `feed`, `remember`/`recall`/`forget`, the four automation tools, the four taskboard tools, the three tunnel tools, and `list_models`; add a new non-chat-only tool there and give it a `silo_runtime` helper. Python gets JSON where the chat tool gets prose (`recall` → `{memories: [...]}`). Chat-only: `soul`, `core_memory`, `switch_model`, the agent tools (`spawn_agent`/`agent_status`/`message_agent`/`stop_agent`), and `sleep`. `artifact` is one engine: the chat tool and Python `silo_runtime.artifact`/`CallTool` share `artifact.Service.Tool`, `artifact.Service.Describe` turns a dir-with-`SKILL.md` into a skill card or any file into a downloadable card, and `/artifacts/skill.zip` + `/artifacts/file` stream the bytes (cookie auth).
- **Worker (Go, inside Bot):** dials the CP. Local Unix-socket HTTP for Python tools (`get_secret`, `call`, desktop). `desktop.*` CallTool is a grant; the Worker runs look/click/type/key/scroll and strips type text before the RPC. Writes `/opt/silo/tools` from `SyncTools` and `/opt/silo/skills` from `SyncSkills` (empty those dirs; do not rmdir them — `/opt/silo` is root). `start.sh` mkdir+chowns both. Tunnels VNC and a console PTY. Desktop is Openbox + Thunar + mousepad + iron wallpaper (`botimage/`). Dock: Files, Terminal, Editor, Chromium. `start.sh` is root only to chown mounts and supervise; the worker, X stack, console PTY, and dock apps run as user `silo` (uid 1000) with passwordless sudo. `start.sh` starts the worker before the X stack so the bot is online without waiting for x11vnc. ConnectRPC bidi does not send headers until the first `Send` — `Commands` must heartbeat immediately or the CP treats the worker as offline until the 10s ticker. x11vnc uses `-speeds lan` (localhost tunnel; skip the link-speed probe). Double-click text in Thunar opens the editor.
- **Python in the Bot:** `exec_python` + `silo_runtime` + generated `tools.*`. Not the orchestrator. The box also has Node.js LTS with `npm`/`npx`/`pnpm` (copied from `node:24-bookworm-slim` in its own `botimage/Containerfile` layer; `SYSTEM.md` tells the model so). `toolsgen` escapes `\` and `"` in generated docstrings — a description ending in `"` must not become `""""` and SyntaxError the whole package import. `tools/__init__.py` is `toolsgen.RootInit` (lazy PEP 562 `__getattr__`), so `import tools; tools.<slug>.fn()` works without importing the subpackage; docstrings name the snake_case kwarg the stub takes, not the MCP camelCase. A nonzero exit from `exec_python`/terminal returns the captured output (the traceback) as the result; never just `exit status 1`. Desktop GUI is first-class `look` / `click` / `type` / `key` / `scroll` (1600×900 X11; worker uses `scrot`/`xdotool`) — that is how the model clicks the machine. The same actions are on `silo_runtime` (`type_text`, not `type`) so a secret can be typed without a chat `type` call. `silo_runtime.web_search` is the Python path for CP web search (same `web.search` gate as the chat tool). Playwright `silo_runtime.chrome_page()` is page screenshots, mutating displayed HTML, and automated scripts — not the live click loop. The worker opens `silo-chromium` when `exec_python` mentions Playwright / `chrome_page` (and `chrome_page` hits `/v1/chrome/ensure` again). Do not ship `chrome_eval` / raw CDP helpers or `pyautogui`. SYSTEM.md must forbid the model `xdotool`, `pyautogui`, `playwright install`, and `apt` for a GUI driver. Computer-use shots attach without `detail: high` (OpenAI-family tiling breaks xy).

The run stream (`useRunStream`) is the one hand-written reader. MCP HTTP URLs keep their query — `?codemode=false` is real server config (it turns off Cloudflare’s code-mode `execute` wrapper and exposes the full tool list) — but the query/fragment must be stripped from the request handed to OAuth `Authorize`, because the SDK derives the resource identity (`resource=`, `.well-known` lookups) from it and Cloudflare validates that strictly (its issuer is `https://mcp.cloudflare.com`). `internal/mcpx` is a thin wrapper over the official go-sdk client — do not hand-roll the transport (handshake, sessions, SSE, `Mcp-Method`/`Mcp-Name` headers all live in the SDK). Cloudflare (and similar) advertise RFC 9207 `iss` but omit it on the callback — fill from the authorize URL origin. The model must not retype it. A presented png/jpg/webp/gif is attached as pixels on the next completion so the model can see Chromium. Persist fetched blobs from `exec_python` to `/workspace`, then `present` — do not copy them through `write`. Thinking is a spinner only while `thinking_chunk`s are the live tail — a later tool/assistant event (or send end) becomes Thought; leaving `streaming` true keeps the spinner forever. Desktop is the hatch only. A connected worker is **online** (pine lamp), not idle. The CP holds the VNC and Console streams until a viewer attaches, then the Worker dials x11vnc or opens a PTY. Each hatch/console WebSocket gets a viewer ticket; closing an old socket must not clear a newer one (React Strict Mode remounts the hatch). VNC and console are separate lanes — both can stay up. Replacing a worker session must cancel any waiter on the old session. Sign-in must call `setSession` from the response (email + admin) or the session cookie is ignored. `StreamRun` persists every event, replays history, and accepts `after_event_id` so the client can reconnect without duplicates. Every string that is persisted or emitted is normalized to valid UTF-8 and capped on rune boundaries: a single invalid byte in a `RunEvent` makes protobuf replay fail, and the client then spins on an open run forever (surviving restarts) because it never sees the `done`. Interrupted runs get a synthetic `done` in `recoverOrphans`. Chat Stop is `StopRun` (that chat’s live run + worker `CancelCmd`); it is not Stop Bot. Commands carry `run_id`; children get `SILO_RUN_ID`. A worker-side call (`silo_runtime`/`CallTool`/`GetSecret`) belongs to a chat only while that run is `running` on the same Bot (`callRun`); otherwise (no id, Console, a background process that outlived its command) it is an **orphan**: Bot rules still apply, its events go to the bus with no chat and are never persisted, `artifact` refuses, and its approval has no run (slip source "Background process"). `StreamRun` forwards only its own chat's events. `ListApprovals` is oldest first and each carries a `source` (chat/automation/channel/subagent) shown on the slip. One live run per conversation: a new chat message while a run is active is injected into that run's inbox (`App.StartOrInject`), not run in parallel; parallel runs across different conversations are allowed. The model ends a user-visible block with `<section_send />`; that finalizes a `section` event (its own chat bubble) and delivers it on a channel. A sentinel closed mid-tool-turn emits `section_live` (shown/delivered, not replayed as history). Channel runs deliver only sections — thinking/tool output stays in the log. If a message arrives while the box is down, the run starts the container and worker-backed tools wait (`waitWorker`) for the worker to connect. `startRun` always calls `ensureRunning`, which confirms the box with Docker even when a worker session exists — a session can outlive a container removed out of band, and trusting it would leave the Bot unreachable. Bot status is derived from remaining running runs and pending approvals. A Docker inspect error is not proof the box is gone — only not-found or a box whose `SILO_BOT_TOKEN` hash ≠ `bots.token_hash` clears the cached ID and `Drop`s. `live` and `ensureRunning` reload the bot row under the lifecycle lock; acting on a row loaded before a concurrent create drops the just-made box as a token mismatch and writes the old hash back. A stopped box keeps its ID. Stop is `docker stop`, not rm. `ResetContainer` is stop+rm and clears the ID. Persist a new token hash only after Create succeeds; a failed recreate plus `live()` adopting the leftover box is what makes the worker hammer 401s. Worker auth misses and rule lookups (no row = catalog default) use `Find`, not `First` — GORM `record not found` is not an error log. Desktop processes are fail-fast: if Xvfb/Openbox/x11vnc/worker dies, the container exits and `unless-stopped` recreates it. Chromium is a dock launcher (`silo-chromium`), not a supervised process. Chrome profile bind is `/home/silo/chrome-profile`. The wrapper is `--enable-low-end-device-mode` + 128MB disk cache + `--load-extension=/opt/silo/ubol`; site isolation stays on — do not launch raw `chromium`. Do not also Chrome-Web-Store force-install uBOL (that duplicates it). Managed policy sets page zoom to ~67% and uBOL lists (ads + cookie/overlay). If `exec_python` mentions Playwright / `chrome_page` and :9222 is down, the worker starts headed `silo-chromium` on `DISPLAY=:1` (not a start.sh child). Connectors are discovered as `import tools` in `exec_python`, not as extra OpenAI tools. Those calls emit `call` / `call_result` and render above the Python fold. Ctrl+C must `Hub.CloseAll` then `http.Server.Close` — never `Shutdown`. The hatch WebSocket is hijacked, so graceful Shutdown waits until a timeout (`context deadline exceeded`) and `signal.NotifyContext` eats extra SIGINTs.

## Two hops

1. **CP ↔ Worker:** ConnectRPC, Worker-initiated, bot token. Concurrent RPCs.
2. **Python ↔ Worker:** HTTP/JSON on `unix:///var/run/silo/worker.sock`.

File tools stay five: `read` (numbered lines; the Worker slices `offset`/`limit`, rejects binaries, and returns `next_offset`; displayed `N|` is the file's absolute line number), `write`, `patch` (exactly one `old_text` match), `delete` (recursive `Cmd_Remove`, refuses the workspace root), `grep` (ripgrep-only, `include` glob, `max_hits` cap, deterministic `--sort path`, heavy dirs pruned; runs without the shell so it emits no `tool_chunk`). A repeat guard short-circuits a 3rd identical `read`/`grep` in a run and resets on any mutating tool. Do not add a sixth unless a real loop needs it. `present` is a chat tool on the CP (shows a workspace file in the thread via `browse_file`); it is not a fifth worker file tool. A presented image is also attached as pixels on the next model turn so Chromium work can Perceive → Reason → Act → Verify — do not oneshot cookies+search with guessed labels. Scratch lives in `/workspace/bot`; user-facing files in `/workspace`. Chat uploads go to `/workspace/tmp` via the composer paperclip (ConnectRPC `PutFile`, 50 MB cap), carried as a `RunEvent.attachments` list persisted in `RunEvent.Meta`; `start.sh` wipes `/workspace/tmp` on every container start, session_start etc, so it is input only. The model is told the paths in `historyFromDB`; it chooses to `read`/`present`. `present` asks `browse_file` for up to 32 MB (worker `presentLimit`), while the Files tab previews at 2 MB (`browseLimit`) and uploads cap at 50 MB (`putLimit`). `present bot/…` is a collapsed “Looked at …” row, not a folio. The Files tab is a human browser (`mkdir` / `remove` / `put_file` / `browse_file` on the worker). Recreate the box after those worker cmds change.

Long-term memories are pgvector rows (`memories`, `vector(1536)`, per bot) behind `remember`/`recall`/`forget` (rules `bot.*`, default allow); `embedding_model` must be OpenAI-compatible (`llm.Embedder`; Anthropic cannot embed), and auto-recall puts close matches in the trailing prompt block once per run — never above a cache breakpoint. Vector `ORDER BY` goes through `Clauses(clause.OrderBy{Expression: …})`: GORM silently drops `Order(clause.Expr)`. SOUL and CORE MEMORY live in Postgres (`bots.soul` / `bots.memory`), not on the box. Injected into the system prompt every run. Tools `soul` and `core_memory` (rule `bot.core_memory`; `Migrate` renames old `bot.memory` rules) write the DB (no worker hop). Model may write both; Settings edits SOUL, the Memories page edits CORE MEMORY. CORE MEMORY cap is 8000 chars — over that the prompt and the tool tell the model to compact, they do not silent-truncate. ListBots omits the bodies; GetBot/UpdateBot include them.

**Memory collector** (`internal/app/collect.go`, prompt `prompts/MEMORY.md`) saves what the Bot forgot to `remember`. It reads a chat's events after its watermark (`chats.memory_seq`, a `run_events.seq`) as a flat transcript (tool output capped short, failures kept longer), and one tool-less completion with `model_memory` (default: the title model) answers JSON `save` (`kind` `fact`|`lesson`) / `update` / `forget`. The model is shown CORE MEMORY plus the 15 closest existing memories, and may `update`/`forget` only those ids. Saves go through `memory.Service.Save` (the `remember` dedupe). The watermark advances after a read, including an unreadable reply, but never on a provider/embed error, so every event is read once. Chats older than the column start at their newest event (`Migrate`). The sweep (a `tickLoop`, 5 min, `memory.collect`) reads web and channel chats (never automation or subagent logs) whose newest new event is over 10 min old and that have no live run, at most 5 per tick, and pauses 15 min after a provider error. A delta over 12k tokens is split into at most 3 calls and the oldest excess dropped. The composer's brain button (`MemoryCollect.tsx`, `CollectMemories` RPC) runs it now for one chat. Memories carry `kind` and `chat_id`; recall marks lessons.

**Compaction** (`internal/app/compact.go`) keeps a conversation inside the model's context window. The window is `context.windows` (per-model override) → the provider's `llm.ContextWindower` (OpenRouter `/models` `context_length`, cached 6 h) → `context.window`. Before each turn `runLoop` takes the last turn's provider usage plus an estimate of what was appended (runes/3.5; the whole request on a run's first turn) and, at `context.compact_at` of the window, summarizes the history with the chat model (`prompts/COMPACT.md` over a flat, front-trimmed transcript) — mid-run too, with a continue note. A provider context-length error compacts once and retries the turn. A compaction is a persisted `compaction` event (body = summary, `tool` = auto/manual, `Meta.after` = last summarized event), opened by a `compacting` event; the thread keeps every event and `historyFromEvents` replays the last summary then only events after its anchor (so a message injected while the summary was written survives), folding the next user turn into it. Diverge remaps the anchor. Usage events carry `window`; the composer's context meter (ring + %) shows it and its click is `CompactChat` — a manual compaction run (origin `compact`, no user event) refused while a reply runs, for channel chats, or when the history is already just a summary; a message sent during it is injected and answered after. Never compact by deleting events.

**Thinking levels** (`internal/llm/thinking.go`, `internal/app/models/thinking.go`) are one neutral ladder (`off`/`minimal`/`low`/`medium`/`high`/`xhigh`/`max`; `""` = model default, nothing sent) on `llm.Request.Thinking`. Each provider maps the level itself: OpenRouter `reasoning.effort` (`off`→`none`), OpenAI/local `reasoning_effort`, Anthropic adaptive thinking (`display: summarized`) + `output_config.effort` or a `budget_tokens` budget with `max_tokens` raised past it. Anthropic's signed thinking blocks come back as `EventThinkingBlock`, ride on the in-run assistant message (`Message.Thinking`/`ThinkingModel`, never persisted), and are replayed first in that turn only to the model that wrote them — a tool loop with thinking needs them.

**Knowledge** (RAG; `internal/rag`, `internal/app/knowledge`, worker `knowledge.go`) lets the owner pick any workspace folder, drives included, and the Bot search it with `search_docs` (chat tool + `silo_runtime.search_docs`, `sharedTools`, rule `bot.search_docs`, Allow; offered only while the Bot has a folder and `knowledge.enabled`). Files stay on the box; `knowledge_folders` / `knowledge_sources` / `knowledge_chunks` (`vector(1536)` + generated `tsv`, HNSW + GIN) live in Postgres, per Bot, separate from `memories`. The worker has two read-only commands: `Walk` (path/size/mtime, recursive, skips hidden + heavy dirs + symlinks, skips `drives/` unless the root is in one, **a missing or unreadable root is an error, never an empty list**) and `Extract` (text + sha256 of the bytes: text/sniffed as is, PDF `pdftotext -layout` with form feeds as pages, docx/odt/rtf/epub/html `pandoc -t gfm`, `.doc` `catdoc`; binary or over 50 MB is `skipped`; the converter is looked up before the file is read so a missing tool costs no drive download). An empty listing of a `drives/` folder that had an index is treated as a disconnected drive (error, nothing deleted). Chunks come from `rag.Split` (form-feed pages, markdown heading path, ~2400 chars with overlap, the embedded text is prefixed with file + heading). Search is hybrid: top 30 by cosine (dropped past 0.85 distance) + top 30 keyword (`plainto_tsquery('simple')`, all-words matches first, stopwords stripped), fused by reciprocal rank in one SQL; it runs on the raw ConnPool with `$n` args because GORM `Raw` mis-handles `@@`, and sets `hnsw.iterative_scan` (pgvector 0.8) behind a savepoint so the per-Bot filter still returns k rows. The sweep (a `tickLoop`, `knowledge.Tick` = 30 s, `knowledge.sync_interval` default 15 m, drives ×4) syncs a folder when it is stale or `dirty_at` is 15 s old (set by the Bot's `write`/`patch`/`delete` and the Files tab's put/remove via `knowledge.Service.Dirty`), skips Bots with no worker (never starts a box), at most 2 per tick, pauses 15 min on a provider error. Add refuses the workspace root, `bot/`, `tmp/`, the bare `drives` root, anything missing, and any folder nested in or holding another. Caps: 5000 files and 2 MB of text per file. **OCR** (`knowledge.ocr`, default on; worker `ocr.go`): after `pdftotext`, only pages with under 20 non-space characters are rasterized (`pdftoppm -r 200`) and read with tesseract (every installed language, English first; the image ships eng + pol in its own layer), 3 pages in parallel at one thread each, at most 100 pages and 4 minutes per file; image files (png/jpg/tif/bmp/gif/webp, at least 8 KB) go straight to tesseract. Recognized text must be at least 60 % letters/digits or it is dropped as photo noise. With OCR off the worker words a scan with `OCR is off`, the source is recorded as skipped/ok with that detail, and `sourceUnchanged` re-reads such files once OCR is turned on (a file OCR already looked at is not retried). A missing tesseract fails that file only. The worker tests that need the image tools skip on a host and run for real in the image (TESTING.md); `TestContainerKnowledgeAllFormats` is the end-to-end proof. The `Knowledge` side page (`/bots/:id/knowledge`, the Chat tab stays lit) has a folder picker (dirs only, drive disclaimer, `NeedMachine` when the worker is down), per-folder status/Sync now/armed remove, the not-indexed list, and a try-a-search panel (`SearchKnowledge`). The prompt lists folder paths only (counts would bust the cache tier). Snippets can lag edits: the tool tells the model to `read` the cited path before relying on one.

**Feed** (`internal/app/feed`) is the owner's read-only inbox per Bot. **Tunnels** (`internal/app/tunnels`, `internal/tunnel`) give the owner addresses for services on a Bot's localhost. A `Tunnel` row is a generated `adjective-colour-animal` name (the subdomain), a port, and `Public`; one per port, 20 per Bot. The CP answers `<name>.<tunnels.host>` (`App.Handler` wraps the mux in `Tunnels.Route`; every other Host falls through) with one `httputil.ReverseProxy` whose `Transport.DialContext` calls `Hub.DialTunnel`: that queues `Cmd.open_tunnel{conn_id, port}` on the `Commands` stream, the worker dials `127.0.0.1:port` and opens a `BotWorker.Tunnel` bidi stream (first frame names `conn_id` or carries the dial `error`), and both ends wrap their stream in `tunnel.Conn`, a real `net.Conn` (deadlines, partial reads), so keep-alive, SSE and WebSocket upgrades need no special code. Rules that bit: a worker must close **gracefully** (`CloseRequest`, then wait for the CP to end the stream) or it cancels away the last frames of a service that writes and hangs up; the CP handler must not return while a conn's write goroutine is inside `stream.Send` (connect forbids it; the send guard in `App.Tunnel`); a `Conn` copies the caller's slice before sending because its goroutine outlives a write deadline. `tunnel.CheckPort` refuses 5900 (x11vnc) and 9222 (Chromium) on both CP and worker. Config is `tunnels.enabled`/`host`/`scheme`; with no `host`, a local `public_url` derives `localhost:<http_addr port>` (the CP's port, not Vite's: Vite would serve the SPA), anything else is "not configured" (`ListTunnels.state` = `ok`/`off`/`no_host`) and the tools, prompt note and add form disappear. `host` equal to the `public_url` host is refused (a tunnelled app could set cookies for the CP's domain). **Private** tunnels hand off the owner's session: no grant → a page load redirects to `{public_url}/tunnels/auth?name&rd` (the CP session cookie never leaves the CP origin), which (signed out) first redirects to `/signin?next=<the handoff>` — the SPA honors `next` for the `/tunnels/auth` path only, by full navigation (`web/src/signinNext.ts`; anything else is ignored, so it is no open redirect) — then mints a 30 s single-use ticket and redirects to `<name>.<host>/.silo/auth`, which sets the host-only `silo_tunnel` cookie (a `TunnelGrant` keyed by the cookie's hash, 12 h, **bound to the Silo session that made it** and re-checked on every request against that session still being live and the Bot's current owner — so signing out, or the session expiring, ends tunnel access at once; `SignOut` therefore deletes the `Session` row (`auth.EndSession`, which also drops its grants), it is not just a cleared cookie; stripped from the request before the service sees it); an API call without a grant is a 401, never a redirect, and `rd` is only ever a plain path. A tunnel request never starts a box (no worker → 503). The Bot's tools (`open_tunnel`/`list_tunnels`/`close_tunnel`, `silo_runtime.open_tunnel`/… via `sharedTools`) gate on `tunnels.open|list|close` (Allow) and **`tunnels.public` (Ask)** for anything exposed to people other than the owner, including flipping an existing tunnel; opening an existing port returns it and never downgrades it. The prompt section (`prompts/TUNNELS.md`) is the same for every Bot so it stays in the cached prefix. The Tunnels tab (`/bots/:id/tunnels`) lists, adds, flips Private | Public (`TunnelAccess`, the same segmented control as a rule; going Public on an existing tunnel takes a second click) and deletes (armed); it polls because the Bot can add rows. Admin Settings has a Tunnels group, and `Settings.tunnels_host` is the effective suffix shown where the field is unset. Changing the suffix re-points every tunnel at once (rows hold only the name).

**WhatsApp and Discord** (`internal/channels/whatsapp`, `internal/channels/discord`) have the Telegram shape: one row binds one conversation (`requires_target`), `GUIDE.md`, live-only inbound, `reply_mode` gates groups/servers (DMs always answer). Shared in `internal/channels`: `Chunk` (rune-aware cut at paragraph/line/word that closes and reopens a ``` fence across a split) and `Seen` (bounded id set for redelivery and echoes). `channels.Remover` is an optional adapter hook that `channel.Service.Delete` calls *before* stopping the worker (so `DeleteBot` runs it too); its failure is logged and never blocks the delete. `Host.DatabaseURL()` is for libraries that keep a session in SQL; it carries the password, never log it. **WhatsApp** is whatsmeow as a *linked device* on the owner's account, so the account is the Bot and there are no fields beyond `reply_mode`. The session lives in the CP Postgres (`whatsmeow_*` tables via the pgx `database/sql` driver), not a SQLite file: `CGO_ENABLED=0`, and it is backed up with the rest. A device is found again by the JID the adapter saves in channel state (`Values["jid"]`, published on `PairSuccess` before anything else can fail); a JID with no row (DB reset) pairs fresh. Pairing is a QR (`rsc.io/qr` → PNG data URL in `StateQR`, status `pending_auth` = “Needs linking”) that the library rotates; a timeout does not loop, the run waits for the **Link device** action (`run.relink` is unbuffered on purpose: a press nobody is waiting for is dropped, never remembered). The Setup page adopts the polled state only while it is a pairing state (`qr`/`auth`), because Telegram/Discord publish value-only states that must not replace the picker list under the user. `LoggedOut` (the library has already deleted the device) clears the JID and waits for Link device; `StreamReplaced`/`ClientOutdated`/`TemporaryBan` end the run as errors. Chats are matched by user+server, and a direct chat can arrive as a phone number or a LID: use `SenderAlt` for a message from them and `RecipientAlt` for one the owner sent — never the owner's own alt, or a message to Alice reads as a note to self — then the library's LID→number map. `IsFromMe` is ignored except in the “message yourself” chat, and there the Bot's own sends are ignored too (`client.sent`: the id is remembered *before* `SendMessage`, because the echo can beat its return). Messages older than `liveSince` (start minus 5 s) are dropped: the server delivers an offline queue on connect. Event handlers run one at a time on the library's queue, so a slow one delays every later event: the read receipt and “typing…” go through `client.spawn`. Outbound Markdown becomes WhatsApp markup (`format.go`); files go as image (png/jpeg/webp), video, audio or document by mime (GIF/SVG are documents); inbound media is a `[image]`/`[voice message]` placeholder plus caption, not downloaded; `History` always errors so `chats` reads the local log; `Outbound.ReplyTo` is unused (a quote needs the quoted body). It is the unofficial protocol: GUIDE.md says to use a spare number. `Remove` logs the device out (unlinks it on the phone) and deletes its keys. **Discord** is discordgo: the gateway for inbound, REST for send, history and the picker. The target is a channel id (a `discord.com/channels/…` link or `<#id>` is accepted; ids are numeric snowflakes). A bot, unlike Telegram's, can enumerate: **Pick a channel** lists every text/news channel it can write in across its servers plus the DMs it has seen (kept as `dm:<channelID>` state values, like Telegram peers); **Invite link** builds the OAuth URL (`client_id` is the bot user id). Intents are guilds + guild/DM messages + the privileged Message Content; gateway close `4014` retries without it and runs *limited* (DMs and @mentions only) with a warning in the status, `4004` is a bad token. In a server it answers an @mention or a reply to the bot unless `reply_mode=always`; other bots, webhooks and system messages are ignored. Sends use `allowed_mentions: users only` (a model-written `@everyone` must not page a server), chunk at 1900 runes, and put files (10 per message) on the last chunk. Tests drive the adapters without a network: Discord through a fake `http.RoundTripper` on the session plus direct calls of the inbound handler, WhatsApp through a `waAPI`/`directory` seam over the client and the real dev Postgres for the session store.

**Built-in connectors** (`internal/builtin`, transport `builtin`) are connectors written in Go on the CP: a descriptor declares config fields (`Advanced` ones fold under "More settings"), tools (JSON-schema `Params`, per-action `Mode`), and a `Check` login, and registers from `init()` (blank-imported in `internal/app/connector/builtin.go`). Per-action modes are the `AuthorizeAction` fallback (`connector.BuiltinMode`). Config is on the Bot's copy: `ConfigJSON` plain, `SecretsJSON` secret (never returned; a blank secret on update keeps it; library rows hold none). A required field unset is `needs_auth` with a "Fill in …" detail, and the UI shows **Set up** (edit) instead of Authorize. Secrets are masked from results and errors. The descriptor `Prompt` (short, code-owned usage notes; `{slug}` becomes the copy's slug) is appended after the row's catalog prompt in the Connectors section, so it stays current on old copies — keep it terse and show the exact call shape. **Drives** (`internal/drives`, `internal/drivehost`, `internal/app/drive`) mount rclone remotes at `/workspace/drives/<name>`. **Automations** are scheduled background prompts (`internal/app/automation`). Each has a name, a prompt, a 5-field cron schedule in the CP's local time, and an on/off switch; the prompt is sent as the user message of a run through the same engine as chat, with a trailing per-run note (`prompts.AUTOMATION.md`) naming the automation and saying nobody is watching live. Every run starts from a **fresh context** (`historyFromRuns` of just this run, not `historyFromDB`) so the log does not grow with each firing — the prompt must be self-contained and keep state in files/`bot` or memory. The scheduler (a `tickLoop`, `automation.Tick` = 20 s) fires due rows **once**: `automation.Service.FireDue` claims the slot with a conditional `next_run_at` update so two writers cannot both fire, and a firing that lands while the previous run is live is skipped, never queued. `rescheduleAutomations` advances anything missed while the CP was down without backfilling. `parseSchedule` rejects a schedule whose first two firings are under 5 minutes apart (`* * * * *` cannot burn a call a minute), and a Bot has at most 50 automations. Every Bot has one pinned **Heartbeat** (`kind=heartbeat`, created with no schedule so it never fires until given one; cannot be deleted). Each automation owns a hidden `Chat` (`chats.automation_id`) that is its run log: it is excluded from web chat lists and Send/Edit/Diverge/Delete refuse it (`writableChat`); deleting the automation drops the log (`chats.Drop`). Bot tools `list_automations`/`create_automation`/`update_automation`/`delete_automation` sit under the `automations` rule (create/update Ask, list/delete Allow; `update_automation` sets the Heartbeat's schedule). UI: `/bots/:id/automations` list + `/bots/:id/automations/:id` log + `/new` and inline editor; the log renders the shared `Thread` with `userAs="run"` (each run is a "Ran …" divider), and `web/src/schedule.ts` is the schedule picker. Chat and automation logs share `useRunStream`.

**Subagents** (`internal/app/subagents.go`) are background agent loops a chat's lead starts with `spawn_agent` (name, goal, context, optional allowlisted model — default `model_subagent` when set and allowed, else the lead's model; rules `agents.*`, Allow). Subagents keep their own trimmed tool list: the prompt cache is per model and siblings spawn in parallel, so matching the lead's tools would not buy cache hits. The prompt tells a lead to end its turn after spawning rather than `sleep`, since every wake from `sleep` is a full turn. Like an automation, each owns a hidden log `Chat` (`chats.subagent_id`; excluded from web chat lists, `writableChat` refuses it) and runs through the same engine from a **fresh context** (its history is only its own log; the brief and later `message_agent` texts are `user` events with `tool="lead"`). A subagent run gets the tool list minus `leadOnlyTools` (no agent tools, `task_reset`, `channel`, `switch_model`, automations) and the trailing `prompts/SUBAGENT.md` note. Depth is 1; at most 8 run at once per lead chat. **Waking:** a subagent's `finish` stores its result (`runResult`: the last model turn's text) with `reported=false`, nudges the lead's live run (`liveRun.wake`, which `sleep` selects on; `inject` nudges it too), and `scheduleWake` (debounced) calls `wakeLead`: if the lead chat has no live run it marks the finished results reported and starts a lead run that opens with a persisted `subagent_report` event (Tool `name:status,…`), replayed as a framed user turn. A running lead inspects on its own; a lead run that ends `done`/`error` with unseen results wakes once (no loop: the report marks them seen). Automation logs are never woken. Stops the lead already knows about (its Stop — `StopRun` cascades via `stopSubagents` — `stop_agent`, Stop Bot) go through `quietSubagents` first so they do not wake it; a human `StopSubagent` does. `DeleteChat` drops the lead's subagents and board. **Taskboard:** `task_items` rows per lead chat, shared with its subagents (`boardChat`); `task_add` parses a leading `[NAME]` into the assignee; a subagent cannot reset. The board and the lead's subagent status ride on the **last message of each request only** (`withTurnNote`), never in stored history, so the model sees only the latest version and cache breakpoints stay ahead of it. Board and subagent changes publish transient `board`/`subagents` bus pings (no id; `useRunStream` hands them to `onPing`, not the thread). Runs are capped by `runs.max_duration` (default 120m, `-1` unlimited; `runContext`). UI: `Taskboard` strip above the lead thread, `SubagentTray` between thread and composer (running cards + "N finished"), and `/bots/:id/run/:chatId/agent/:agentId` is the read-only `SubagentPage` (shared `Thread`, Brief, Stop; the Chat tab stays lit).

After create, never `docker exec`, `docker cp`, or a published VNC port.

Container ID in the DB is the last box. `GetBot`/`ListBots` inspect Docker (and the `silo-{id}` name) and clear a vanished box. `StartBot` starts that ID if it still exists; it creates only when there is no ID or the box is gone. Do not trust a stored ID after a `podman rm`.

# Dev

## Commands

`make help` is the list; these are the ones you will actually need.

- `make build-cp` / `make build-all` / `make images` — `bin/silo`, worker, bridge; then bot + STDIO images.
- `make bot-image` (runs `build-worker` first) after worker, `botimage/`, or toolsgen changes; `make stdio-image` (runs `build-bridge`) for the bridge / `mcpimage/`. Neither touches containers: a running Bot keeps its old image until Container → Reset (or `podman rm -f silo-<id>`) and Start.
- `make db-up` / `db-down` / `db-psql` — dev Postgres (`silodb-postgres`, not `silo-*`, so `cleanup` spares it). You may start it; `make db-reset` drops the volume (destructive, only when asked).
- `make test` — `go test ./cmd/... ./internal/...` (never `./...`: it walks `data/`). Needs `make db-up`: `dbtest.New(t)` gives each test its own schema in `silo_test`; never open a DB by hand in a test.
- Postgres rejects NUL and invalid UTF-8 in `text`; `internal/db` scrubs every create/update, so do not bypass GORM with raw inserts. Run events order by `seq` (timestamps tie at µs), never `created_at`.
- `make proto` — `buf generate` (Go + TS) after any `.proto` change, then rebuild the CP and worker.
- `make cleanup` — `podman rm -f` every `silo-*` container. `make clean-images` drops the local images.
- `make dev` — tmux session with `watch-control` (watchexec, 750 ms debounce, SIGTERM + 5 s grace) and Vite; `make attach` reattaches.
- `make reset-data` — deletes `./data`; destructive, only when asked.

## Commits

Commit with **Conventional Commits** per [DEVELOPMENT.md § Commits](DEVELOPMENT.md#commits): `<type>(<scope>): <summary>`. Every commit made with a model's help carries an `Assisted-by: <model name>` trailer naming the model that made it (e.g. `Assisted-by: DeepSeek V4.1 Flash`). Do not spend too much time in loops around commits - it is fine to bundle features in a single commit if they are a big change, but describe it clearly. You should also look at and commit the user's changes rather than leaving things uncommited.
DO NOT add yourself as contributor or co author, this is especially to claude!!!. Only assisted-by.
While changes are unpushed the log is yours to rewrite: if the user is not satisfied with a change, amend, rebase, squash, or reorder to fix it up cleanly instead of stacking `fix`/`wip` commits. Never rewrite pushed history.

## Who runs what

- **Never start the frontend or the control plane yourself.** The user owns those processes (`make dev` or their own tmux). Do not run `make dev` / `run-control` / `run-frontend` / `watch-control`, and do not kill or clean up their background processes. If `make dev` is not up but you need it for something (eg tests), FAIL early and tell the user to start it up.
- **You may** run builds (`make build-*`, `make images`), tests, `make proto`, and container cleanup (`make cleanup`, `make clean-images`).
- **You may** attach to the user's already-running tmux for debugging: inspect with `tmux ls` and `tmux capture-pane -p -t silo`, or attach (`make attach`) when you have a TTY. Do not start a second session under the same name.
- Do not run big command chains of tasks that take a long time to finish (especially ones that download things). Do them separately to avoid leaving a state where an unknown command in the middle is hung, and do not blindly supress the output of commands like builds that may get stuck.

## Debug via Chromium

Debug and test your stuff with chromium MCP for MAJOR CHANGES.
Use localhost as the actual URL of the Silo Agent, not 127.0.0.1. Something is wrong with the ip.
**DO NOT** Start another automation browser, only use your mcp, never start some custom aah browser in some random aah folder
If the chromium MCP is offline, just tell the user. It usually simply means this task will be tested manually.
