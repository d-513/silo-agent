A token-conserving, self-hosted, multi-user agent. Each **Bot** is a durable container with a desktop, driven by a Go **Control Plane** (CP).

# Working in this repo

## Who runs what

- **Never start the frontend or the control plane yourself.** The user owns those processes (`make dev` or their own tmux). Do not run `make dev`, `run-control`, `run-frontend` or `watch-control`, and do not kill or clean up their background processes. When you need the running stack (`make e2e`, `make test-integration`, a browser check) and it is not up, stop early and ask the user to start it.
- **You may** run builds (`make build-*`, `make *-image`, `make images`), tests, `make proto`, `make fmt`/`vet`/`tidy`, and container cleanup (`make cleanup`, `make clean-images`). You may start the dev databases (`make db-up`).
- **You may** inspect the user's running tmux session for debugging (`tmux ls`, `tmux capture-pane -p -t silo`, or `make attach` with a TTY). Never start a second session under the same name.
- Run long steps one at a time (builds, image builds, downloads) so a hang is visible, and do not hide a build's output.
- Destructive targets only when asked: `make db-reset` (drops the Postgres volume) and `make reset-data` (deletes `./data`). Both ask y/N on a TTY, so without one they abort.

## Commands

`make help` lists every target. The ones you will need:

| Target | Does |
| --- | --- |
| `make build-cp` | `bin/silo` (built with cgo) |
| `make build-worker` / `build-bridge` / `build-drive` / `build-egress` | Static (`CGO_ENABLED=0`) binaries for the containers |
| `make bot-image` / `stdio-image` / `drive-image` / `egress-image` | Build the binary, then its image (`botimage/`, `mcpimage/`, `driveimage/`, `egressimage/`) |
| `make images` | All four images; `make build-all` = every binary and every image |
| `make db-up` / `db-down` / `db-psql` | Dev dependencies from `docker-compose.dev.yml`: Postgres 17 + pgvector on `:5433`, Lightpanda MCP `:9223`, smtp4dev `:1025/:1143/:8025`, Radicale `:5232`, Dex `:5556`. All are `silodb-*`, so `make cleanup` spares them; the compose file never runs the CP |
| `make test` | `scripts/gotest.sh` over `./cmd/... ./internal/...` (never `./...`: it walks `data/`), `internal/app` split into `SHARDS=8` processes, includes the real-container tier (run `make images` first) |
| `make test-fast` | Same without the container tier |
| `make test-containers` | Only the real-image tests; fails if Podman or an image is missing |
| `make test-integration` / `make e2e` | Need the user's running stack; real tokens / Playwright |
| `make proto` | `buf generate` (Go + TS) after a `.proto` change, then rebuild the CP and whatever uses that proto (worker, drive sidecar, egress gateway). iOS stubs: `buf generate --template buf.gen.swift.yaml` |
| `make cleanup` / `make clean-images` | `podman rm -f` every `silo-*` container / remove the local images |

- **cgo:** the CP and the tests build with cgo (`CGO_ENABLED=1`, the Makefile default: libopus for calls). Anything that runs in a container is `CGO_ENABLED=0` (the Makefile targets and `apptest` pin it): a cgo binary built on this NixOS host links the host's glibc loader, which no image has.
- **Images do not touch containers.** A running Bot keeps its old image until its box is recreated: Settings → General → Reset container (or `podman rm -f silo-<id>`), then Start. After a worker, `botimage/`, `silo_runtime.py` or `internal/toolsgen` change: `make bot-image` and recreate the box. After the bridge or `mcpimage/`: `make stdio-image` and refresh the connector. See DEVELOPMENT.md § After you change….
- **The container engine** is reached through the Docker API client (`internal/dockerx`) on the Podman socket by default (`DOCKER_HOST`, `docker_host`). "Docker" in names below means that engine.
- **Database:** `database_url`, default the dev compose on `localhost:5433`. Postgres rejects NUL and invalid UTF-8 in `text`; `internal/db` scrubs every create/update, so never bypass GORM with raw inserts. Run events order by `seq` (timestamps tie at µs), never `created_at`. GORM `First` logs `record not found` as an error: use `Find` for lookups where absence is normal (worker auth misses, rule lookups where no row means the catalog default). Columns added to an existing table need `not null;default:…` so old rows are not NULL.

## Tests

- **Work test-first.** Most behaviour is covered by Go **feature tests** in `internal/app` that drive the real ConnectRPC API through `internal/apptest` with the scripted **dummy provider** (`internal/llm/dummy`): no tokens. Reach for a feature test before a white-box one; a test that needs a private helper usually means a missing seam. TESTING.md has the harness (`apptest.New`, `H.StartWorker` runs the real worker binary, `apptest.WithStdioBridge()` the real bridge) and the dummy's script format.
- `make test` needs `make db-up`. `dbtest.New(t)` gives each test an empty migrated schema in `silo_test` (pooled per process); never open a database by hand in a test.
- Tests in `internal/app` share package globals (the dummy's scripts), so they never use `t.Parallel`; the shards are separate processes.
- Live checks (build tag `live`, real providers, cost money) are named where the behaviour they pin is described. Re-run the relevant one after touching a prompt, schema or wire format it covers; never loop them.
- Web: `node --experimental-strip-types web/src/<dir>/<x>_test.ts` runs one unit test; `npx tsc --noEmit` in `web/` typechecks. `web/e2e/routes.spec.ts` walks every route without sending a message; run it after any `router.tsx` change (needs the running stack).
- Guard tests that fail when you forget a step: `TestEveryRPCChecksAccess` (a new RPC needs a line in `access.RPCs`), `TestBuiltinToolExposure` and `TestPythonToolsHaveHelpers` (a new tool), `TestPinnedKindsAreIndexed` (a new pinned automation kind), `TestHistoryIsAppendOnly` (anything that changes what a model is sent), `i18n_test.ts` (a new UI string), `TestProviderKinds` (a provider's model kinds), `TestScrapedSourcesAreLimited` (a new search source), `TestGrantsStayInSpace`.

## Checking in the browser

- Check major UI changes in the browser through your Chromium MCP, at `http://localhost:5173` (use `localhost`, not `127.0.0.1`: the dev setup does not work on the IP).
- Use only that MCP. Never launch another automation browser or install one (no `playwright install`, no browser in a scratch folder).

## Adding things: the checklist

- **An RPC:** `proto/silo/v1/*.proto` → `make proto` → a handler on the owning domain's `Service` (not on `App`) → a line in `access.RPCs` saying who may call it → a feature test.
- **A Bot tool:** one `tool.Def` in `App.toolDefs` (`internal/app/tools_defs.go`); with `ExposePython`, a `silo_runtime` helper named `Name`/`PyName`; its rule in the security catalog; exposure pinned in `TestBuiltinToolExposure`; documented for the model in SYSTEM.md or its feature's prompt section.
- **A config key:** the struct in `internal/config` with its default in `setDefaults` (`store.go`), `docs/CONFIGURATION.md`, `silo.yaml.example` when an operator would set it, and a field in its Admin → Settings category (`web/src/admin/fields.ts`; categories in `sections.ts`); never a new Admin tab for settings.
- **A UI string:** `t("English text")` and an entry in both `locales/pl.ts` and `locales/de.ts`.
- **A domain:** `internal/app/<domain>` with a `Service`, its RPCs and tools, a small `Host` interface for what it needs from the App, an exported field on `App`, embedded in `uiHandler`.
- **A page:** a route in `web/src/router.tsx` (lazy unless it is the chat), see Frontend.

# Architecture

## Processes and hops

- **Control Plane** (`cmd/silo`, `internal/app`): users, Bots, rules, the agent loop, every key and token. Bots never hold provider keys, OAuth tokens or connector credentials.
- **Worker** (`cmd/silo-worker`, inside each Bot box): dials the CP; runs file, shell, Python and desktop commands; tunnels VNC, the console PTY and HTTP tunnels.
- **Sidecars:** one STDIO MCP sidecar per STDIO connector grant (`cmd/silo-mcp-bridge`, `mcpimage/`), one drive sidecar per Bot (`cmd/silo-drive`, `driveimage/`), one egress gateway per engine (`cmd/silo-egress`, `egressimage/`). Each dials the CP; none publishes a port.
- **Frontend** (`web/`): Vite + React, talks ConnectRPC to the CP plus WebSockets for VNC, console and calls. **iOS** (`ios/`) is a SwiftUI client of the same API, behind the web.

Two hops matter:

1. **CP ↔ Worker:** ConnectRPC, Worker-initiated, bot token, concurrent RPCs. ConnectRPC bidi sends no headers until the first `Send`, so `Commands` heartbeats immediately or the CP treats the worker as offline until the 10 s ticker.
2. **Python ↔ Worker:** HTTP/JSON on `unix:///var/run/silo/worker.sock` (`get_secret`, `call`, desktop).

## Package layout

- `internal/app` is the runtime: the agent loop and run engine, Bot lifecycle, worker RPCs, the tool gateway with its rules and approvals, subagents. It wires the domains in `app.New`.
- Each domain is a `Service` in `internal/app/<domain>` that owns its RPCs and Bot tools: `access`, `space`, `account`, `approval`, `filter`, `models`, `workspace`, `connector`, `drive`, `channel`, `skill`, `artifact`, `knowledge`, `changes`, `memory`, `automation`, `dashboard`, `feed`, `quote`, `setup`, `proactivity`, `pause`, `command`, `tunnels`, `mailbox`, `voice`, `egress`, `audit`, `admin`, plus the shared `chats`, `toolarg`, `tool`, `host` and `run`.
- **A domain never imports package `app`.** It takes the concrete services it depends on (`models`, `workspace`) and declares what it needs from the App in a small `Host` interface (`host.Authorizer`, `host.Runs`, `host.Emitter`; `run.Engine` to start and steer runs) that `*App` implements.
- `handler.go` embeds every service into the one `uiHandler`, so their RPCs are promoted, not re-declared. Services are exported fields of `App` (`a.Knowledge`, `a.Models`, …) so tests and tick loops call them directly. Do not add methods to `App` for something a domain can own.
- Background work is a `tickLoop` per domain (named with its interval below).

## Configuration

- Koanf: **defaults → `silo.yaml` → `SILO_*` env**. Nested keys use `__` (`SILO_PROVIDERS__OPENROUTER__API_KEY` → `providers.openrouter.api_key`); some lists also read comma-separated env (`envLists`). Admin → Settings edits `silo.yaml` (a form per category plus a YAML editor); env still wins, and the UI warns and disables those fields.
- **Providers** carry `api_key`, `base_url`, `cache`, `cache_ttl`, `max_tokens`; prompt caching is on by default (`setDefaults` sets `providers.<id>.cache`). Provider ids: `openrouter`, `openai`, `anthropic`, `typesafe`, and `local` (any self-hosted OpenAI-compatible server: `base_url` required, key optional; Silo never hosts models). Model ids are `provider/model`.
- `providers.openrouter.ignore` (default `DeepInfra`) is sent as OpenRouter `provider.ignore`: some upstreams buffer tool-call arguments into one final chunk, which kills the live `tool_args_chunk` stream of exec_python/terminal/write input.
- **Models:** `models` is the allowlist of text models and `model` the default (unset: `openrouter/openai/gpt-5.6-luna`); `model_title`, `model_subagent`, `model_memory`, `model_voice` are text roles; `model_approval` and `model_filter` take a text or a decision model. Each other kind has its own allowlist (see Model kinds).
- `search.engine` picks the web search engine; unset is `builtin` (an old `duckduckgo_scraper` reads as it).

## Containers

- **Lifecycle is create / start / stop / inspect / remove / stats only**, for Bot boxes, STDIO sidecars, the drive sidecar, the egress gateway and their networks (`internal/dockerx`). **After create, never `exec` or `cp` into a container, and never publish its VNC port.**
- The container ID in the DB is the last box. `GetBot`/`ListBots` inspect the engine (and the `silo-{id}` name) and clear a vanished box. `StartBot` starts that ID if it still exists and creates only when there is no ID or the box is gone. Never trust a stored ID after a `podman rm`.
- An inspect **error** is not proof the box is gone: only not-found, or a box whose `SILO_BOT_TOKEN` hash ≠ `bots.token_hash`, clears the cached ID and `Drop`s. Persist a new token hash only after Create succeeds: a failed recreate plus `live()` adopting the leftover box is what makes a worker hammer 401s.
- `live` and `ensureRunning` reload the bot row under the lifecycle lock; acting on a row loaded before a concurrent create drops the just-made box as a token mismatch and writes the old hash back.
- `StartRun` always ensures the box (`ensureRunningBg`), confirming it with the engine even when a worker session exists: a session can outlive a container removed out of band. Worker-backed tools then wait for the worker (`Hub.WaitConnected`, 90 s), so a message to a stopped Bot starts it.
- **Stop** is `docker stop`, not rm; a stopped box keeps its ID. **`ResetContainer`** is stop + rm and clears the ID (the workspace bind stays; Start makes a new box). **`DeleteBot`** drops the box, the row and `data/bots/<id>`. Dangerous buttons take a second click, never `confirm()`.
- Desktop processes are fail-fast: if Xvfb, Openbox, x11vnc or the worker dies, the container exits and the `unless-stopped` policy restarts it.
- Replacing a worker session cancels any waiter on the old one. **Shutdown:** Ctrl+C runs `Hub.CloseAll` then `http.Server.Close`, never `Shutdown`: the hijacked hatch WebSocket makes a graceful shutdown wait for its timeout (`context deadline exceeded`), and `signal.NotifyContext` eats extra SIGINTs.

# The Bot's box

## Worker and image

- The image is `botimage/`: Openbox + Thunar + mousepad, an iron wallpaper, a dock (Files, Terminal, Editor, Chromium), Node.js LTS with `npm`/`npx`/`pnpm` (its own layer from `node:24-bookworm-slim`), and the document and OCR tools Knowledge uses.
- `start.sh` runs as root only to chown mounts and supervise. The worker, the X stack, the console PTY and the dock apps run as user `silo` (uid 1000) with passwordless sudo. It starts the worker before the X stack so the Bot is online without waiting for x11vnc. x11vnc uses `-speeds lan` (a localhost tunnel; skip the probe).
- `start.sh` mkdirs and chowns `/opt/silo/tools` and `/opt/silo/skills`; the worker writes them from `SyncTools`/`SyncSkills`. Empty those dirs, never rmdir them (`/opt/silo` is root's).
- The machine is **UTC** (`TZ=UTC` in `dockerx.botEnv`); the human's zone belongs to the Bot (see Time zones).
- The CP holds the VNC and console streams until a viewer attaches; only then does the worker dial x11vnc or open a PTY (in `/workspace`, via the worker, never `podman exec`). Each hatch/console WebSocket gets a viewer ticket, and closing an old socket must not clear a newer one (React Strict Mode remounts the hatch). VNC and console are separate lanes; both can stay up.
- A connected worker is **online** (pine lamp), not idle.
- Paths: user-facing files in `/workspace`, the Bot's scratch in `/workspace/bot`, chat uploads in `/workspace/tmp` (wiped on every container start: input only), drives at `/workspace/drives/<name>`.

## Python

- `exec_python` + `silo_runtime` + generated `tools.*`. Python is a tool, not the orchestrator.
- **A persistent interpreter per conversation** (worker `kernel.go` + the embedded `kernel.py`): the CP sends `ExecPythonCmd.session` = the chat id with the newest `/clear`/`/wipe` event id appended (`pySessionFor`); an automation firing uses its run id; empty is a throwaway `python3 -c`. At most 4 interpreters, closed after 30 idle minutes; a cell that starts in a new one opens its output with `[fresh Python session]` (SYSTEM.md explains it).
- One merged stdout/stderr pipe, a NUL-led end marker with a per-cell nonce, `SILO_RUN_ID` set per cell, stdin emptied. Stop sends SIGINT and kills the interpreter only if the cell ignores it for 3 s; only the interpreter is signalled, never its process group, so a server a cell started keeps running.
- A nonzero exit from `exec_python`/terminal returns the captured output (the traceback), never just `exit status 1`.
- `toolsgen` escapes `\` and `"` in generated docstrings (a description ending in `"` must not become `""""` and SyntaxError the whole package). `tools/__init__.py` is `toolsgen.RootInit` (lazy PEP 562 `__getattr__`), so `import tools; tools.<slug>.fn()` works without importing the subpackage. Docstrings name the snake_case kwarg the stub takes, not the MCP camelCase.

## Desktop and Chromium

- The desktop is 1600×900 X11. `look` / `click` / `type` / `key` / `scroll` are first-class tools (worker: `scrot`/`xdotool`); that is how the model works the machine. The same actions are on `silo_runtime` (`type_text`, not `type`) so a secret can be typed without a chat `type` call. `desktop.*` from Python is a grant; the worker acts and strips typed text before the RPC.
- Computer-use screenshots attach without `detail: high` (OpenAI-family tiling breaks xy).
- **Chromium** is a dock launcher, `silo-chromium`, not a supervised process: `--enable-low-end-device-mode`, a 128 MB disk cache, `--load-extension=/opt/silo/ubol`, site isolation on. Never launch raw `chromium`, and never also force-install uBOL from the Web Store (that duplicates it). Managed policy sets page zoom to ~67% and uBOL lists (ads + cookie/overlay). The profile is bound at `/home/silo/chrome-profile`.
- `silo_runtime.chrome_page()` (Playwright on the headed Chromium) is for page screenshots, changing displayed HTML and scripted runs, not the live click loop. When an `exec_python` cell mentions Playwright / `chrome_page` and :9222 is down, the worker starts headed `silo-chromium` on `DISPLAY=:1` (`chrome_page` also calls `desktop.chrome`, a `Local` grant).
- Do not ship `chrome_eval` or raw CDP helpers. SYSTEM.md forbids `xdotool`, raw CDP, a second browser and `playwright install`.
- **Pause** (`internal/app/pause`, table `desktop_pauses`, `Bot.desktop_paused`, `SetDesktopPaused`; its own table because the bots row is saved whole in places) is the owner taking the desktop over with the switch in the Desktop pane's header. While paused, `click`/`type`/`key`/`scroll`, `desktop.chrome` and an `exec_python` cell that `WantsChromium` are refused on both surfaces with `pause.ErrPaused`; `look` still works. It is a `tool.Def.Gate`, checked by `Engine.Run` before the Python `Local` grant and before any approval, so a paused desktop never raises a slip. Not covered: a Playwright page a cell kept in a variable from before the pause, driven later by a cell that does not mention Playwright/`chrome_page`.

## File tools

- **Five, and no sixth unless a real loop needs it:**
  - `read`: numbered lines (`N|` is the absolute line number); the worker slices `offset`/`limit`, rejects binaries and returns `next_offset`.
  - `write`.
  - `patch`: exactly one `old_text` match.
  - `delete`: recursive `Cmd_Remove`; refuses the workspace root and drive roots.
  - `grep`: ripgrep only, `include` glob, `max_hits` cap, deterministic `--sort path`, heavy dirs and `drives/` pruned; runs without the shell, so it emits no `tool_chunk`.
- A repeat guard short-circuits the 3rd identical `read`/`grep` in a run and resets on any mutating tool.
- `present` is a CP chat tool, not a worker file tool: it shows a workspace file in the thread via `browse_file` (up to 32 MB, `presentLimit`). A user path is a folio; `bot/…` is a collapsed "Looked at …" row. A presented png/jpg/webp/gif is attached as pixels on the next completion, so Chromium work goes Perceive → Reason → Act → Verify (never one-shot cookies + search with guessed labels). The model must not retype a presented file; persist fetched blobs from `exec_python` into `/workspace` and `present` them, never copy them through `write`.
- Uploads: the composer paperclip sends ConnectRPC `PutFile` (50 MB, `putLimit`) to `/workspace/tmp`, carried as `RunEvent.attachments` in `RunEvent.Meta`; `historyFromDB` tells the model the paths and it chooses to `read`/`present`. The Files tab previews at 2 MB (`browseLimit`) and uses `mkdir`/`remove`/`put_file`/`browse_file`. Recreate the box after those worker commands change.

# The agent loop

## Tools are one engine

- Every tool is a `tool.Def` (`internal/app/tool`): name, description, JSON-schema params, its `connector.action` (the rule that gates it and its address from Python), the handler, and where it is offered: `ExposeCompletion` (the model's tool list) and `ExposePython` (`silo_runtime.call(connector, action)`). The built-ins are one list, `App.toolDefs` in `internal/app/tools_defs.go`.
- **Two thin adapters, no other dispatch:** the chat loop's `execTool` (completion surface) and the worker RPC `CallTool` (Python surface: emits `call`/`call_result` rows and always answers JSON, wrapping prose as `{"result": text}`). Both call `Engine.Run`, which refuses a surface the tool is not on, runs the def's `Gate` and `Check`, authorizes `Connector.Action` through `AuthorizeAction` (unless `SelfGated`), runs the handler, and hands the result to the output filter. Chat tools and Python `CallTool`/`GetSecret` share `AuthorizeAction`.
- **Exposure is Python-first** (pinned by `TestBuiltinToolExposure`). A built-in is a completion tool only when it is the loop itself (the five file tools, terminal, `exec_python`, `present`, the desktop, `remember`/`recall`), chat-only by nature (`soul`, `skill`, `switch_model`, the agent tools, `sleep`), or asks the human by default (`create_automation`, `update_automation`, `open_tunnel`: an approval can outlast the worker's 5-minute command timeout, which a Python call sits under). On both by choice: `decide`, `artifact`, `ask_owner`, `offer_setup` and the desktop actions. Everything else (`web_search`, `feed`, `chrome`, the taskboard, `chats`, `channel`, mail, `search_docs`, `transcribe`, `forget`, widgets and dashboard cards, `set_proactivity`, `set_timezone`, `list_*`, `delete_automation`, `close_tunnel`) is `silo_runtime` only, documented in SYSTEM.md and the feature prompt sections.
- `tools.expose_completion` (a silo.yaml list, `all` for everything; `tool.Engine.Expose`) offers named Python-only tools to the model again. Tests that script one as a chat call use `apptest.WithChatTools()`.
- Other `Def` flags: `SelfGated` (the handler gates itself because the rule depends on the arguments: one rule per channel, `tunnels.public`, a slip that names the automation), `Local` (from Python the worker performs it and the engine only grants: the desktop, so typed text never reaches the CP), `LeadOnly` (left out of a subagent's list), `Writes` (takes the run's change snapshot and clears the repeat guard), `RepeatGuard` (`read`/`grep`), `Enabled` (offered only while a feature is on), `Gate` (refuse before any approval: pause), `Mode` (fallback decision), `OutMode` (fallback output rule), `Title` (the call row). Handlers get a `tool.Call` and use `c.Structured()` to give Python JSON where the model gets prose (`recall` → `{memories: [...]}`).
- **Connector tools are the same definitions**, supplied per Bot by `connector.Service` as a `tool.Source` (`Tools`/`Find` in `internal/app/connector/tools.go`; `connector.Service.Call` runs MCP or built-in). Always `ExposePython` (`tools.<slug>`); `ExposeCompletion` when the connector's **Expose completions directly** switch is on (`connectors.expose_completion`; HTTP, STDIO and built-in alike; a library preset's value is what a new copy starts with; `optional` on the update/add requests so an unrelated save keeps it). Exposed connector tools join the model's list after the built-ins (so the stable list stays a cache prefix), sorted by slug then action, named `<slug>__<action>` (`tool.CompletionName`: `[A-Za-z0-9_-]`, 64 max, a hash suffix when cut), described as `<Name> connector. <server text>`, gated by the same `slug.action` rule.
- SYSTEM.md nudges where the engine does not act: independent steps go in one Python cell (threads for network calls), because the loop does not run tool calls in parallel, and a cell prints only what the next step needs.

## The system prompt and context

- The loop is `internal/llm`: `openrouter`, `openai`, `local` speak the OpenAI-compatible API, `anthropic` the native Messages API, `typesafe` decisions only. The chat's model is `chats.model`, else the Bot's default, else `model`; Bots get `list_models`/`switch_model` under the `model` rule.
- **The system prompt is built once per run** (`internal/app/systemprompt.go`) in tiers ordered stable → volatile, each ending in a provider cache breakpoint: the base `SYSTEM.md` alone (the same bytes for every Bot, so with the tool list it is one cache entry they all share; the Bot's name is *not* in it), then the Bot's session tier (name, language, people, connectors, skills, channels, drives, knowledge, tunnels, mail, feature sections), then SOUL; after the last breakpoint come memories and the notes of the one conversation (channel, automation, subagent). A run that edits its own SOUL is told by the tool result; the *next* run reads the new prompt.
- Feature prompt sections are the same text for every Bot unless they say otherwise, so they stay in the cached prefix; a section that depends on config fills placeholders from operator config only.

### Context is append-only

`internal/app/agent_history.go`, `agent.go`. A provider's prompt cache holds only while each request starts with the previous one's bytes. `TestHistoryIsAppendOnly` holds the property (every request extends the previous one, within a run and across runs); a change that makes replay differ from the live run breaks it.

- What a turn adds is recorded so `replayEvents` rebuilds **the same messages byte for byte** in the next run:
  - a tool turn is a `turn` event (Body = what the model said, Meta = its calls with the provider's ids; replay prefers it to the streamed `tool`/`tool_args_chunk` events, which older runs only have);
  - the pixels a result came with leave a `seen` event (the text the turn reads as once the image is no longer sent);
  - the taskboard/subagent status is a `note` event, told **only when it changed** and kept in history (so it carries no durations or "latest step": `subagentState`, not `subagentLine`);
  - a message injected mid-run has its `user` event **re-sequenced** to where the run read it (`drainInbox` bumps `seq`; `inject` and the drain share `liveRun.injecting` so the event is written first).
- The history a run keeps is the text as the log stores it (`App.kept`: masked, valid UTF-8).
- `turn`, `seen`, `note` and `cleared` are `internalKinds`: persisted with `App.record`, never published, skipped by `StreamRun`.
- **Never put anything that changes per message or per turn into the system prompt or an earlier message.** This is why the time zone is frozen on each message and never in the prompt, and why memory dates in the prompt are UTC.
- The deliberate rewrites are clearing and compaction, and both record that they happened.

### Clearing stale tool results

`internal/app/clear.go`, tried before compaction at the same threshold. All but the newest tool results (at least 3, at most a tenth of the window) become a one-line placeholder, calls and pairing kept. It happens only when that frees at least a quarter of the trigger level *and* brings the conversation back under it; otherwise compaction runs on the untouched history, so the summary reads the real output. The freed estimate is scaled by the last turn's provider count over the engine's estimate of the same content. A `cleared` event (`Meta.results` = how many, counted from the start of the replayed window) lets `contextFromRuns` clear the same ones; `replayEvents` itself leaves the text alone because the memory collector reads it.

### Compaction

`internal/app/compact.go`. Never compact by deleting events.

- The window is `context.windows` (per-model override) → the provider's `llm.ContextWindower` (OpenRouter `/models` `context_length`, cached 6 h) → `context.window`.
- Before each turn `runLoop` takes the last turn's provider usage plus an estimate of what was appended (runes/3.5; the whole request on a run's first turn) and, at `context.compact_at` of the window, summarizes the history with the chat model (`prompts/COMPACT.md` over a flat, front-trimmed transcript), mid-run too with a continue note. A provider context-length error compacts once and retries the turn.
- A compaction is a persisted `compaction` event (body = summary, `tool` = auto/manual, `Meta.after` = last summarized event), opened by a `compacting` event. The thread keeps every event; `historyFromEvents` replays the last summary, then only events after its anchor (so a message injected while the summary was written survives), folding the next user turn into it. Diverge remaps the anchor.
- Usage events carry `window`; the composer's context meter (ring + %) shows it, and its click is `CompactChat`: a manual compaction run (origin `compact`, no user event), refused while a reply runs, for channel chats, or when the history is already just a summary. A message sent during it is injected and answered after.

## Thinking levels

`internal/llm/thinking.go`, `internal/app/models/thinking.go`. One neutral ladder on `llm.Request.Thinking`: `off`/`minimal`/`low`/`medium`/`high`/`xhigh`/`max`; `""` = the model's default, nothing sent.

- Which levels a model takes: `thinking.levels` in silo.yaml, then the optional `llm.Thinker` (OpenRouter `/models` `supported_parameters` has `reasoning`; Anthropic Models API `capabilities`, adaptive+effort or budget-only; OpenAI by family). `ListModels` carries them per option.
- The chat stores its choice (`chats.thinking`, `SetChatThinking`) and each turn fits it with `NearestThinking`, so it survives a model switch; the composer's picker shows the fitted level (`web/src/thinking.ts` mirrors the fit) and hides when the model lists none.
- Each provider maps the level itself: OpenRouter `reasoning.effort` (`off`→`none`), OpenAI/local `reasoning_effort`, Anthropic adaptive thinking (`display: summarized`) + `output_config.effort`, or a `budget_tokens` budget with `max_tokens` raised past it.
- Anthropic's signed thinking blocks come back as `EventThinkingBlock`, ride on the in-run assistant message (`Message.Thinking`/`ThinkingModel`, never persisted), and are replayed first in that turn only to the model that wrote them: a tool loop with thinking needs them.

## Model kinds

`internal/llm/kinds.go` is a registry: `text`, `decision`, `transcription`, `speech`, `embedding`, each with its interface (`llm.Implements`) and its silo.yaml allowlist (`models`, `decision_models`, `transcription_models`, `speech_models`, `embedding_models`).

- A provider's `Descriptor.Kinds` says what it serves, and `TestProviderKinds` holds that to the interfaces: OpenRouter serves every kind; OpenAI and `local` everything but decision; Anthropic text; TypeSafe decision.
- Validation (`validateModels`: an id on one list only, its provider serves the kind), `Config.ModelKind(id)`, `admin.modelRoles`/`checkRole`, `SetModels(kind)`, `Settings.allowed` and a provider's **List models** tabs all loop over the registry, so a new kind is a row, an interface and a list key.
- A role's model counts as allowed for its kind even when its list does not name it (`Config.KindModels`), which keeps old silo.yaml files working.
- Listing (`ModelInfo.Kind`): OpenRouter's default `/models` lists only text, so `openRouterClient.ListModels` makes one `/models?output_modalities=` query per non-text modality (`decisions`, `transcription`, `speech`, `embeddings`; a speech model's `supported_voices` come along) and keeps only entries whose `architecture.output_modalities` match (a proxy that ignores the query answers the text list again). OpenAI and `local` are labelled by family name (`llm.GuessKind`, a hint: the operator's list decides).
- `ListProviderModels` (admin only) asks the provider with its *saved* settings through the optional `llm.ModelLister` (the OpenAI-compatible providers share `GET {base}/models`, `fetchModels`; Anthropic pages its Models API). A provider failing to list is never `Unavailable` (that reads as the CP being down), and its error is masked of the key.
- Chats, Bots and `switch_model` only ever see `models`.

## Decision models

`internal/llm/decide.go`, `internal/app/models/decide.go`. A decision model (TypeSafe's Jev and the family that followed: Clef, Solar Decide, …) is shown a `state` and typed questions and answers each with probabilities, no text (`llm.Decider`: `DecisionRequest{State, Questions}` → `Answers`).

- The three question types keep the hosted APIs' names: `noul` (yes/no; the answer is P(yes)), `choice` (one of the caller's options), `score` (2 to 10 ordered levels). `llm.Question` marshals to the wire shape both APIs share; `DecisionRequest.Validate` refuses a bad one in words the Bot can act on. `DecisionResponse.check` fails a call whose answer is missing or of another type: callers branch on these numbers without reading them, so a zero value must never pass for an answer.
- **Providers:** `openrouter` posts to its Decisions API, which sits *beside* the OpenAI-compatible root (`…/api/alpha/decisions`, `openRouterDecisions(base)`, not under `/v1`); `typesafe` (`internal/llm/typesafe.go`) is TypeSafe's System One API (`POST {base}/systemone`, default base `https://api.typesafe.ai/v1`), decision-only, so its `Complete`/`Stream` return an error; its `GET {base}/models` is a bare list of `{name, description, release_date}`. They share one `decisionEndpoint` (same body and answer; errors from `error.message` or `detail.message`, key masked; 429/503/529 and network errors retried twice within 30 s). OpenAI's `/v1/decisions` and llama.cpp's typed-decision API are not wired: a new one is a `Decider` plus `Kinds`.
- **Config:** `decision_models` is the allowlist, `model_decision` the default (`Config.DecisionModel`: the setting while still allowed, else the first allowed, else none, so a stale default never blocks taking a model off the list). `SetModels` carries `kind`; `Settings.decision_models`, `Provider.kinds` and `ProviderModel.kind` feed the UI. Admin → Settings → Models has one allowlist per kind (`AllowedModels kind=…`), a **Default decision model** picker, and auto-approval/filter pickers that offer both kinds (`eitherKind`).
- **`decide`** (`models.Service.DecideTool`, rule `model.decide`, Allow) is on both surfaces: a chat tool for a judgment or two mid-turn, `silo_runtime.decide(state, questions, model=None)` for a loop over many items; it answers `{model, answers, usage}` as JSON. Its chat schema spells the question shape out (`questions` is an object whose `additionalProperties` is `{type: noul|choice|score, instructions, criteria}`; `state` an object of named fields; `criteria` described, not typed) and sticks to what every provider takes: no type unions, no array without `items`. A model that writes `questions` as a JSON string is read anyway (`rawQuestions`). It is `Enabled` only while a decision model is allowed, and so is its prompt section (`prompts/DECIDE.md`, `{default}`/`{models}` filled from operator config, the same text for every Bot), which says when to call the tool and when to loop in Python. The thread shows a call as Decision · the questions' names (`toolInfo.ts` `asked`). `list_models` adds `decision_models`/`default_decision`. `TestLiveDecideToolCall` (tag `live`) offers it to real chat models; re-run it after touching the schema, the description or the prompt section.
- Every decision goes through `models.Service.Decide`, which records it in the LLM debug log.
- **Dummy:** the dummy provider is also a Decider (`dummy/judge`): `Test_Yes_<q>`/`Test_No_<q>`, `Test_Pick_<option>`, `Test_Unsure`, `Test_Decide_Error`, and `Test_Approve`/`Test_Deny` on the gate's questions; `dummy.Decided()`/`Completed()` show what was sent.

# Runs and conversations

## Runs

- **One live run per conversation:** a message sent while a run is active is injected into that run's inbox (`App.StartOrInject`), never run in parallel. Parallel runs across different conversations are fine.
- Commands carry `run_id`; children get `SILO_RUN_ID`. A worker-side call (`silo_runtime`/`CallTool`/`GetSecret`) belongs to a chat only while that run is `running` on the same Bot (`callRun`). Otherwise (no id, the Console, a background process that outlived its command) it is an **orphan**: Bot rules still apply, its events go to the bus with no chat and are never persisted, `artifact` refuses, and its approval has no run (slip source "Background process").
- `StreamRun` persists every event, replays history, accepts `after_event_id` so the client reconnects without duplicates, and forwards only its own chat's events (the Bot-wide stream drops chats the viewer cannot read, `chatReader`).
- **Every string that is persisted or emitted is normalized to valid UTF-8 and capped on rune boundaries.** One invalid byte in a `RunEvent` makes protobuf replay fail, and the client then spins on an open run forever (surviving restarts) because it never sees the `done`. Interrupted runs get a synthetic `done` in `recoverOrphans`.
- Chat Stop is `StopRun` (that chat's live run + worker `CancelCmd`), not Stop Bot. Runs are capped by `runs.max_duration` (default 120m, `-1` unlimited; `runContext`).
- Bot status is derived from remaining running runs and pending approvals. `Bot.activity` is one row per live run (where it runs and the tool it is in: `liveRun.step`, set when a tool call starts); the sidebar's `ActivityStrip` shows it.
- **Sections:** the model ends a user-visible block with `<section_send />`; that finalizes a `section` event (its own bubble) and delivers it on a channel. A sentinel closed mid-tool-turn emits `section_live` (shown/delivered, not replayed as history). Channel runs deliver only sections; thinking and tool output stay in the log.
- `App.EndTurn` ends a run after that turn's calls (used by `ask_owner` in a web chat).

## Chats

- A chat's title starts as a short model-written name from the opening prompt (`model_title`, told the Bot's language by `lang.Title`), not the raw message; the human can rename (`RenameChat`). A `chat_title` stream event updates the list and is not drawn in the thread.
- **New chat** (`/bots/:id/run/new`, route `staticData.fresh`) has no row behind it; the model and thinking level picked there are held in `BotPage` (`ChatPick`), and the first `Send` carries them with `new_chat`: the server makes the chat and starts the run in one call, then the page moves to `/run/:chatId` (a refused send leaves no row). The web client no longer calls `CreateChat` (iOS still does).
- **Main chat** (`chats.main`, one per person on a Bot by the partial unique index `chats_main_person` on `(bot_id, user_id)`; `chats.Main(bot, user)` finds or makes it, so everyone has one from `CreateBot` or their first `ListChats`). It is where a Bot page opens (`useChatList` sends `/run` there), the target of a `Send` with no chat, pinned above the date groups, and never deleted or renamed (`errMainChat`; `/clear` and `/wipe` keep it light). Deleting the open chat returns to it.
- **Placement:** replies to what the Bot made (a Feed quote, a Dashboard ask's submit, a `hand` action, a mail wake) append to the main chat unless the request sets `new_chat` or **a reply is running there**, in which case they open a chat of their own, so a live run's history and the thread never disagree about order. Every placement goes through `run.Engine.Place` (`App.Place`, `internal/app/place.go`: a `run.Placement` with `Write`, an optional own-chat `Title`, `Own`, `Proactive`, `UserID`, the owner's `Message`), which holds the conversation lock across the choice, the write and the start, publishes what was written, and takes it back if the run cannot start. **Never check the main chat and then act on it.**
- `chats.Put` is the one way an event is written into a chat outside a live run (a finished run of its own, the Bot's zone, `updated_at` bumped); `chats.Web`/`WebScope` is the one test for a web chat. Automation and subagent logs are hidden chats (`chats.automation_id`, `chats.subagent_id`) that Send/Edit/Diverge/Delete refuse (`writableChat`).
- The sidebar folds chats into date groups (`bot/chatGroups.ts`: Today, Yesterday, Previous 7 days, Previous 30 days, then one per month; rows carry no date; fold state per viewer in `chatGroupsStore.ts`; landing on a chat opens its group).
- **Paging:** `StreamRun` replays only from the `pageTurns`-th newest user message and opens with a transient `earlier` event when there is more; `ListChatEvents(before_event_id)` is the page before. `foldEvents(events, first)` takes a negative start so a prepended page keeps the drawn blocks' keys.

## Several people on one Bot

A Bot with one person behaves byte for byte as before. **The Bot is the unit of trust:** everyone on a Bot shares its memory, files and connections, and the wall between people is separate Bots, so cross-chat tools (`chats`, the memory collector) are deliberately not narrowed per person.

- A chat has an author (`chats.user_id`; empty is the Bot's own: a mail wake, a channel, an automation's log). A run is its chat author's (`runs.user_id`; a subagent's log is its lead chat's author's). A `user` event records `user_id` and, only while the Bot has more than one person, a frozen `author` that `replayEvents` puts on its stamp (`[bob@… · Sun, …]`, `stampAuthored`).
- `access.Chat` reads a chat for its author, the Bot's managers, and anyone on the Bot for an automation's log (`access.CanRead`); writes are the author's, or a manager's in the Bot's own chats (`CanWrite`). A manager reads and stops someone else's chat, never writes in it. `ListChats` gives a user their own chats and a manager everyone's (`Chat.author`/`mine`; the sidebar's **Team** group).
- `Place` puts a placement in the presser's main chat (`Placement.UserID`), and the Bot's own doing in the main chat only while it has one person; with several it opens a chat of its own or waits on the Dashboard.
- **Approvals:** `ListApprovals` (oldest first, each with a `source`: chat/automation/channel/subagent) returns only what the caller may answer (`Approval.person`, `once_only`): a user answers their own runs' approvals with Allow once or Deny (`always` reads as `allow_once`), managers answer the rest, and an action marked `manager` in the security catalog (`security.ManagerOnly`: automations, `bot.soul`/`set_proactivity`/`set_timezone`, `tunnels.public`, channel sends) is the managers' whoever's chat asked. That is what stops a user having the Bot create an unwatched automation and approving it themselves; channel sends speak as whoever linked the channel. A rule set to Allow allows for whoever is chatting: it is the managers' policy.
- Read state is per person: the Feed's unread and the Dashboard's "since you last looked" use `bot_access.feed_read_at`/`dashboard_seen_at`.
- The session tier names the people (`peopleSections`) while there are several, and the time zone follows a device only while the Bot has one person. `Bot.people` lists them for the sidebar.

## Slash commands

`internal/app/command`, defs and handlers in `internal/app/commands.go`: one registry for every surface.

- `Send` parses the text (`Registry.Parse`: `/name` at the very start, an `@Bot` suffix allowed; an unknown `/name` or a `//`-escaped one is a message) and runs a command instead of starting a run. The response carries `command`, an English `notice` (what a channel gets back), a `value` the web words itself (`saidFor` in `bot/runActions.ts`), `confirm` for a command that destroys something (sent again with `confirmed`), and `new_chat`.
- A channel conversation runs commands through `run.Engine.Command` from `deliverInbound` and gets only the `Channel` ones (`/clear`, `/stop`, `/help`): the sender may be anyone in that conversation.
- `ListCommands` feeds the composer's `/` menu (`composer/slash.ts`, `SlashMenu.tsx`; summaries translated client-side).
- **`/clear`** is a `context_cleared` event in a run of its own (origin `command`): `replayEvents` starts after the last one (before any compaction cut), nothing is deleted, the memory collector skips the event and still reads what came before, the chat's taskboard and live subagents go, and the Python interpreter follows the boundary. Refused while a reply runs.
- **`/wipe [last|all]`** (default: since the last `/clear`) deletes events for good (`deleteChatEvents`: events, emptied runs and their settled approvals), leaves a `wiped` marker (body = how many), never touches memories, and asks first. Artifacts no longer shown anywhere go on the next `SweepBot`.
- `/remember` runs the memory collector now; `/onboard` starts the interview; the rest (`/compact`, `/model`, `/thinking`, `/stop`, `/new`, `/rename`, `/help`) are what they say.

# Rules and safety

## The security engine and rule layers

- `internal/security` is the catalog of `connector.action` → title, fields, default mode; `*` covers files/desktop; each secret is `secrets.<name>` (not `secrets.get`); an unknown MCP action gets a generic prompt. Reserved connector slugs: python, terminal, files, desktop, bot, secrets, skills, web, artifact, channels, chats, model, automations, agents, tasks, tunnels, mailbox, drives.
- Call modes are Allow / Auto / Ask / Deny; `allow_once` is a valid vote. The approval slip never dumps `args_json` (and redacts `desktop.type` text). Connector tokens and extra headers stay on the CP.
- **Three layers**, all applied by `layer` (`internal/app/operator.go` over `internal/app/rules.go`), which takes the stricter of the Bot's value and every floor:
  - **Operator** (`operator_rules`, Admin → Settings → Rules, admin-only RPCs): a **locked** row is a floor the owner may tighten but never loosen (`SetRule` refuses; `security.Stricter`/`Looser` in `internal/security/layers.go`; an unknown value ranks as ask/check); an **unlocked** row is only a default the owner overrides. The operator's policy text `rules.approval_policy`/`rules.output_policy` is joined first.
  - **Workspace guardrails** (`space_rules`, `SetSpaceRule`, Workspace admins, Workspace → Rules; `internal/app/space_rules.go`): always a floor, the least strict call or output mode any Bot of the Workspace may use (Allow and Pass mean none and delete the row), looked up through the Bot's `space_id` (`App.spaceRule`). `ListSpaceRules` lists the same sections as a Bot's Rules page with the floor as each value. `spaces.approval_policy`/`output_policy` are joined after the operator's text and before the Bot's (`approval.JoinPolicies`).
  - **The Bot's own rows** (`rules`), edited on its Rules page. `ListRules` carries the operator's value + lock and `space_decision`/`space_output`, so the page shows the lock or "Set by the workspace" and stops offering a looser mode.
- Detaching a connector or deleting a secret prunes its rules so ghosts do not stay; renaming a connection moves every granted Bot's rules to the new slug (`App.RenameRules`).

## Approvals and auto-approval

`internal/app/approval`. `approval.Service.Judge` is called by `AuthorizeAction` for a rule set to **Auto** and builds one `approval.Request` whichever kind of model judges: the policy, the action (`security.Describe` of the redacted arguments), where it came from, and **the human's latest message in that conversation** (`lastHuman`: the newest `user` event with no sender tag, so a lead's brief or a quoted mail is not it; a subagent gets its lead chat's).

- An automation, an orphan call or a chat nobody wrote in has no such message, and **nothing is put in its place**: the gate is told `Automations: …` or `Unknown: …` (`Request.from`), and the automation's prompt is never passed off as the human's (`TestAutoApproveFromAutomationHasNoHumanMessage`).
- A text model gets `prompts/APPROVAL.md` + the policy as the system prompt and the request as one user message with the human's words and the action fenced as data, and answers one word (`parseVerdict`: anything unrecognised is ask).
- A decision model gets the request as `state` and two `noul` questions, `allowed` and `forbidden` (two, so a silent policy answers no to both); `verdict` holds them to `approval.Sure`/`Unsure` (0.9/0.1): deny when forbidden is sure, approve only when allowed is sure *and* forbidden unsure, otherwise ask.
- A model error, a 30 s timeout or an empty policy is ask, never allow. An approval the gate fell back to is marked (`approvals.auto`, `Approval.auto`): its slip offers only Allow and Deny plus a link to Rules, and `DecideApproval` reads `always` on it as `allow_once`, so answering one call never turns the Auto rule into Allow.

## Output rules

`internal/app/filter`, `internal/app/filter_hook.go`, `internal/security/output.go`. The call rule says whether an action may run; the **output rule** says what happens to its result before the Bot reads it: `pass`, `flag` (always framed as untrusted, no model asked), `check` (the filter model judges) or `withhold`.

- It is `rules.output` on the same row (`''` = the default; a row may hold only an output rule, `ruleDecision` skips an empty `Decision`), looked up by `App.ruleOutput` with the call rule's precedence (the action's row, the connector's `*` row, the catalog's `spec.output` via `security.DefaultOutput`, then `Def.OutMode`). `SetRule` carries `optional output`; an output with an empty decision changes the output side alone.
- **Defaults:** what comes from outside is checked (`web.search`, `mailbox.list`/`read`, `chats.read`, `bot.transcribe`, and every connector action: `connector.toolDef` sets `OutMode: check`); everything else passes; every row is the owner's to change (`python.run`/`terminal.run` set to Check is how content a script fetched itself gets judged). Secrets, channel sends, `tunnels.public` and `artifact.app_network` have no output side (`outputApplies`; `Rule.output` is empty and the Results view drops the row).
- **One hook:** `tool.Engine.Run` hands what every handler returns to `Engine.Filter` (`tool.ResultFilter`, implemented by `App.FilterResult`), so both surfaces and every connector go through it. A handler's error is filtered too (an MCP `IsError` body is its server's text); the gate's own `denied`/`canceled` and the Python-`Local` grant are not.
- **Verdicts** (`filter.Service.Check`): `clean` passes untouched, `flagged` passes framed, `withheld` never reaches the Bot, `unchecked` (a model error, the 30 s timeout, no verdict, or a result over `filter.max_chars`) **passes with a warning frame**: the filter never holds a run up and never asks the human. A long result is judged in overlapping 8000-rune parts (4 at once) and the worst part wins; a verdict is cached 10 minutes per model + policy + call + text (never an unchecked one).
- **The judge** is `model_filter` (either kind; falls back to `model_approval`). A text model gets `prompts/FILTER.md` + the policy and answers one word, with the result fenced between two lines carrying a random id so text inside cannot close the fence. A decision model gets one `choice` (`clean`/`suspicious`/`malicious`) held to Sure/Unsure (`grade`: withheld at 0.9 malicious, clean at 0.9 clean, flagged at ≤0.1 clean, else unchecked). Both see where the call came from (`approval.Service.Source`) plus the call itself, so a README's install steps are clean when the human asked for the setup. The policy is per Bot (`bots.output_policy`, Rules → Results; `UpdateBot.output_policy` is `optional`); empty means `prompts/FILTER_POLICY.md`, a severity ladder for indirect prompt injection (it judges attempts to steer the Bot, not truth or taste). `TestLiveFilter` (tag `live`) runs a corpus through real models of both kinds; re-run it after touching either prompt, the question or the levels.
- **Nothing a model writes reaches the Bot:** the frames are fixed text in `filter/frame.go`, and the action name in them is reduced to plain characters.
- **Chat surface:** the frame is the head of the tool message (the 12000-byte cap cuts the tail); a withheld result is a fixed placeholder. Since `Engine.Run` returns the final text, what is emitted, appended and replayed is the same bytes.
- **Python surface:** code gets the data in its own shape (a withheld result is an error), and **the warning is the CP's to deliver, never the machine's**: `FilterResult` holds a `filter.CellNotice` for the run (`App.holdNotice`) and the chat loop puts it at the head of the result of the tool call that code ran in (`takeNotices`, before the mask and the cap). A call that named no run is held for the Bot and rides on its next tool result within 6 minutes. Do not move this into `silo_runtime` or the worker: a warning the Bot's own code can drop is not one (`TestCodeCannotHideAFilteredResult`, `TestFlaggedWebSearchReachesTheBot`).
- **Only the CP speaks as the filter:** every completion-surface result, even with the filter off, goes through `filter.Defang`, which rewrites an opening `[Silo output filter` in the result's text to `[quoted, not from the filter:…`. `filter.reveal` spells out invisible Unicode tag characters for the judge (the Bot's copy is unchanged; flag emoji region codes are left alone). A pixels-only result still obeys Flag and Withhold (Withhold drops the image); Check has no text to judge there. SYSTEM.md's **Outside content** section explains the frame.
- **The thread:** a `filtered` event (`Tool` = `connector.action`, body `{verdict, mode, original}`) is emitted just before the result; `fold/tools.ts` puts it on the matching row. `original` (a withheld result, masked, capped) is for the owner only: `replayEvents` has no case for the kind, so no model sees it. Every non-clean verdict is an audit row (actor `filter`, `output_flagged`/`output_withheld`/`output_unchecked`).
- **Config:** `filter.enabled` (the operator's cost switch: off, every result passes and rules are kept; `ListRules.filter_enabled` tells the page), `filter.max_chars`, `model_filter`.
- **Dummy:** a decision model picks `Test_Pick_suspicious`/`Test_Pick_malicious`; a text model answers `Test_Flag`/`Test_Withhold` when its system prompt carries `dummy.FilterMarker`; `Test_Unsure` is no verdict; with no token both answer clean.
- **Not covered, by design** (worth telling an owner who asks): image pixels under Check (`look`, `present`, screenshots); the live `tool_chunk` stream the human watches; messages that are not tool results (channel inbound, a mail that wakes the Bot); and data that code kept (a flagged result stored in a variable or file and printed in a later cell is warned about in the first cell only; setting `python.run`/`terminal.run`/`files.*` to Check covers that).

## Egress gateway

The network filter between every Bot box and STDIO sidecar and the internet. Gateway `internal/egress` (`cmd/silo-egress`, `egressimage/`, `make egress-image`); CP side `internal/app/egress`, `internal/dockerx/egress.go`, `internal/db/egress.go`; config `egress.*` (on by default; docs/CONFIGURATION.md).

- **Shape:** one `silo-egress` per engine. It dials the CP's `EgressHost.Session` with its own token and gets the whole `EgressApply` on every connect and change. `Service.Apply` only marks the session dirty and the sender renders the newest state: never block on the gateway or push a state you rendered yourself.
- **Networks:** every Bot box (`silo-egress-bot-<bot>`) and STDIO sidecar (`silo-egress-mcp-<grant>`) gets its own `--internal` /24 from `egress.subnet_pool` (`10.213.0.0/16`), with the gateway always at `.2` (`GatewayAddr`), so a recreated gateway keeps every client's address. The gateway never forwards (`egressSysctls`, `TestEgressGatewayNeverForwards`). A client is identified by both ends of its connection (`State.ClientOf`). A `ClientNetwork` failure refuses to start the client: never an unfiltered box. `Enabled()` is false on a plain Docker engine (Podman only, for now). `Reconcile` ticks every 30 s and drops the gateway when no clients are left.
- **Reaching it:** no `HTTP_PROXY` variables (they would drag the h2c CP link through the proxy). Podman ignores `--dns` on a user network, so `start.sh` (and `mcpbridge.InstallDNS`) write `SILO_EGRESS_DNS` into resolv.conf; the gateway answers every name with itself and serves 80/443 transparently (Host/SNI). The worker's `SILO_CP_URL` is `http://<gw>:8443`, a TCP forward for clients only. Other protocols use the SOCKS5 door on `:1080`: `start.sh` always writes proxychains4, the ssh `ProxyCommand` and `SILO_SOCKS_PROXY`, and the gateway decides per connection (`bots.other_protocols`, `SetOtherProtocols`, off by default; off, it refuses the CONNECT and logs an `other_protocols` block).
- **TLS:** everything is decrypted except Pass-through hosts (spliced; the lists, feeds and internal-address check still apply). The connection to the origin is re-made with utls, mirroring the box's own TLS hello, and verified against the system roots (502 if it does not verify). WebSockets are spliced after the 101.
- **CA:** one per installation (`egress_ca`), handed to clients in the env (`SILO_EGRESS_CA`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `PIP_CERT`); `start.sh` installs it in the system store and the `silo` NSS db for Chromium. The env is fixed at create, so after `RotateEgressCA` a stale container (`StaleCA`, `dockerx.State.CAHash`) is dropped and recreated by `ensureRunning`/`ensureStdio` on its next start.
- **Surrogate secrets** (`secrets.mode` surrogate|plain, `hosts`, `surrogate`, `swap_body`; `applySecretMode`): with no mode and no hosts a secret is plain. A surrogate needs hosts, never a public suffix or a CIDR (`checkSecretHost`). `egress.NewSurrogate` keeps only a vendor marker and the length, with at least 8 random positions. `GetSecret` hands out the stand-in only when the box is on its client network (`Egress.Filters`), else the real value. The gateway puts the real value in only towards an allowed host over verified HTTPS (headers; bodies only with `swap_body`) and swaps it back in the response. Elsewhere a stand-in is a `surrogate_leak` block, and over plain HTTP `surrogate_insecure`. STDIO sidecars and `${secrets.NAME}` connector values get the real value; channel secrets are never sent.
- **Verdicts:** a block (lists, feeds, private/loopback/metadata addresses checked after resolving and again at dial) is a plain `403 Blocked by the Silo network filter.`; flags are silent (exfil sinks, secret shapes, plain secret values, random domains, DNS shapes, query entropy, a 50 MB/h upload budget, beaconing, executables). There is no Ask or Auto at the network layer.
- **Lists:** `egress.block`/`trust`/`pass` are the operator's locked floor; owners add up to 200 of their own (`AddHostPattern`, Rules → Network). Threat lists come from `egress.feeds` (five built in; naming any feed replaces them).
- **Audit:** gateway reports go to `internal/app/audit` → `audit_events` and per-minute `egress_traffics` (`audit.detail_days` 7, `traffic_days` 30). An event is put on a run only when exactly one run is live. `bots.audit_unseen` drives the badge; Admin has `/admin/audit` and Settings → Network (`GetEgressStatus`).
- **Not covered:** drive sidecars, the CP's own connections, a rootful engine's `.1` bridge (host services bound on `0.0.0.0` are reachable), TLS inside the SOCKS door, and DNS-over-UDP identity (source address only).
- **Tests:** `internal/egress/*_test.go` (`hardening_test.go`), `feature_egress_test.go`, `feature_egress_container_test.go` (real engine), `feature_audit_test.go`.

## Outbound connections from the CP

`internal/netguard`, `config.Outbound`, `Config.OutboundPolicy()`. Some connections the CP makes itself, to an address **a user typed**, from inside the operator's network.

- `outbound.block_private` (off by default; `outbound.allow` lists IPs/CIDRs, each optionally with one port, that stay reachable) refuses internal addresses for exactly those: an HTTP connector's URL (`mcpx.Dial.Base`) and the OAuth endpoints its server names (`AuthorizationCodeHandlerConfig.Client`), the Email and Calendar built-ins (`builtin.Config.Net`, which every dial and HTTP client in a built-in must use), a skill's download (`skills.InstallURL` takes the client) and a drive provider's sign-in (`drive.Service.httpClient`: pCloud's API host arrives as a callback parameter).
- The check is `net.Dialer.Control`, on the literal address being connected to: after DNS, so a name resolving inside, a redirect leading inside and DNS rebinding are the same refusal. **Never check a hostname before dialing instead.** `netguard.Internal` judges an IPv6 address carrying an IPv4 one (mapped, NAT64, 6to4) by the one inside.
- **The operator's own targets are exempt** for HTTP connectors and their OAuth (`connector.Service.outbound`/`operatorTarget`): a library preset, or a Bot's copy that still points where its preset points (`sameTarget` on both sides resolved), connects unrestricted, which keeps Lightpanda on localhost working. Re-pointed, it is the user's word again. The Email/Calendar built-ins always follow the policy.
- Not covered, on purpose: model providers, search, OIDC (the operator's). What a box or sidecar reaches is the egress gateway's job.
- **A new feature that connects somewhere a user names takes its dialer or client from `OutboundPolicy()`.**

## Other people's bytes in our origin

Pinned by `feature_hardening_test.go`. The console's origin is where a signed-in owner's cookie works, so nothing a Bot, a sender or another user wrote may act as a page there.

- `/artifacts/download` opens in place (`inline=1`) only a type that cannot script (`workspace.Passive`: raster images, PDF, audio, video, plain text); HTML, SVG and anything unknown is always an attachment, and `workspace.Untrusted` adds `nosniff` and a sandbox policy. The preview overlay reads bytes with `fetch`, so it never needs the page.
- A connector's mark is an image by its **bytes** (`connector.imageType`; the upload's claimed type is not believed, and `ServeImage` asks the bytes again for old rows). HTML made from a document (`DocxView`; mammoth does not clean links) goes through `web/src/safeHtml.ts`. A mail's `.eml` is always an attachment with `nosniff`.
- `/vnc`, `/console` and `/voice/call` check the `Origin` themselves (`socketOrigin`: the request's host or `public_url`; none at all is a native client). CORS does not hold a WebSocket back, and a tunnelled app on a sibling subdomain is same-site, so the cookie alone is not the gate.
- A connector's OAuth callback finishes only in the browser of the user who started it (`oauthWait.user`; a refusal does not spend the state), since the authorize link can be sent to anyone. Drives are not bound, because the iOS flow ends in Safari.
- **A library preset's header values, STDIO environment and OAuth client secret are the operator's:** a Bot's copy keeps them only while it talks to what the preset talks to (`sameTarget`: same URL, or same command, arguments and image); re-pointing a copy, or creating one already pointed elsewhere, keeps only what that request supplied (`keepOnlyGiven`).
- **`auth.host_cookie`** (off by default; `Config.HostCookies()`, true only while `public_url` is https, since a browser drops a `__Host-` cookie set over http) is for tunnels under Silo's own registrable domain (`silo.example.com` + `*.tunnels.example.com`): any host under `example.com` can plant a `silo_session` for the parent domain and sign a visitor into another account, but none can set a `__Host-` one. On, the session is `__Host-silo_session` and the OIDC round trip `__Host-silo_oidc` (`Path=/`), and **the plain names are never read**: every `auth.SessionFromRequest`/`UserFromRequest`/`EndSession` takes `hostOnly` from the config, so a new cookie-authed route cannot forget it. Flipping it signs everyone out once; `ClearSession` clears both names.
- STDIO sidecars share an npm directory per Bot (`data/bots/<id>/mcp-npm`, `dockerx.stdioCacheDir`), never across Bots: npx runs what is in `~/.npm/_npx`, and a sidecar runs its owner's choice of package as root.
- A known ceiling: `docker inspect` can still read a Bot's token and a STDIO sidecar's environment.

# People and access

## Workspaces and access

`internal/app/access`, `internal/app/space`. A **Workspace** (code `space`, UI "Workspace") holds Bots and the people who use them. Every Bot is in one (`bots.space_id`); `bots.created_by` is only who made it. The model never hears the word "Workspace" (`/workspace` is its box), and a Workspace with one person shows no team UI.

- **Roles** are two tables: `space_members.role` (`owner|admin|member|guest`, one owner per Workspace by the `space_owner` index) and `bot_access.role` (`manage|use`; whoever makes a Bot manages it). A guest is never Can manage, because managing means granting the Workspace's resources. Instance admins get nothing extra here and cannot open another user's Bot either.
- **Every check goes through `access`** (who is asking and what they may do: user and session on the context, `RowByToken`, `PublicURL`, `SafeReturn`, and the checks):
  - `access.Bot(ctx, db, id, access.Use|Manage|Administer)`: Use = anyone on the Bot; Manage = its managers, for anything that widens what it may do; Administer = a manager or a Workspace admin who is not on it, for delete/revoke only. An admin never opens someone else's Bot.
  - `access.Row[T]` for one row of a Bot, `access.Chat(ctx, db, botID, chatID, Read|Write)`, `access.Space(ctx, db, id, View|Build|Admin|Own)`.
  - A caller who may not see a thing gets NotFound with the access layer's own message (`access.NoBot`/`NoChat`/`NoSpace`); one who may see it but not do this gets PermissionDenied with a sentence.
  - The plain HTTP routes (`/vnc`, `/console`, `/voice/call`, private tunnels, app views) re-check `access.CanUse` on every request.
- **`access.RPCs` declares who may call every UI RPC.** A new RPC is a line there. `TestEveryRPCChecksAccess` fails on a missing one and calls every Bot-, chat- and Workspace-scoped RPC as a stranger (who must get the access layer's NotFound, never one of the handler's making), as the owner (never refused), and as a member who uses the Bot, a guest and an admin who are not on it.
- A Bot with no enabled manager is **suspended** (`access.Suspended`/`SuspendedBots`): no runs, channels or tunnels.
- `ListSpaces` makes a user's first Workspace (`space.Service.Home`), so everyone owns one; `CreateBot` with no `space_id` lands there. A Workspace admin's `ListBots` carries `others`: the Bots they are not on (people, grant count, Delete; never a link).
- **People** (`internal/app/space/people.go`, `invites.go`): an admin makes an invite link (`CreateSpaceInvite`, `/join/$token`, single use, 7 days, only the hash kept; admins invite members and guests, only the owner makes admins). It is a bearer, never matched by email, and joins whoever opens it signed in (`JoinSpace`; `GetSpaceInvite`/`JoinSpace` are public procedures that still learn the caller, `seenRPCs` in `app.go`); it makes an account for a visitor only while `spaces.invite_signup` is on (`account.Service.SignUp`). `SetSpaceRole` follows the role table (making someone a guest turns their Can manage into Can use, refused while that leaves a Bot with no manager); `TransferSpace` hands the Workspace to an admin.
- **A Bot's people:** `ListBotPeople`/`AddBotPerson`/`SetBotRole`/`RemoveBotPerson` keep at least one manager; a guest only uses; adding someone names the secrets another person set (`secrets.set_by`) before a second, confirmed call. New Bot sends what it may use (`connector_ids`, `drive_ids`, `skills_off`) and who else uses it (`user_ids`), all checked before the Bot exists.
- **Lending** (`access/lend.go`): a connection or drive with a `lent_by` carries that person's identity and is personal unless its lender shares it (`SetLendShared`, the lender only). A personal one may only be in Bots whose people are exactly its lender: `access.CheckLend` (grant, `CreateBot`), `CheckAdd` (a person joining a Bot), `CheckSignIn` (a sign-in or typed credential makes a new lender; `StartConnectorAuth`/`BeginDriveAuth` take `shared`) and `CheckUnshare` hold that. `access.LenderOK` refuses a disabled lender's identity (connector calls, drive mounts). `lent_by` stays empty when no person's credential is in a connection (no auth, operator preset values, `${secrets.NAME}`), so such a connection is never personal.
- **Removing a person** (or leaving, or deleting a user) is `space.Service.Remove`: the Bots only they manage go by a plan (another manager, the remover takes it, or delete; `PlanSpaceRemoval` shows the choices), what they lent leaves with them (personal deleted, shared signed out through each `space.Lending`), and their access ends at once: `App.Gone` (`access.Watch`) closes their run streams, desktop/console sockets and calls.
- **Moving a Bot** to another Workspace (`PlanMoveBot`/`MoveBot`, `internal/app/move.go`; a manager of the Bot who may build in the target; Settings → General) keeps what is its own and drops what was its Workspace's: every grant, its Workspace skills, and the people who are not in the target.
- **Activity:** Workspace events (joins, leaves, role changes, Bots made and deleted, grants and revokes, sign-ins, Personal/Shared) are audit rows with `space_id` and `actor_user` (`access.Activity`), read by its admins in Workspace → Activity (`ListSpaceActivity`). A Workspace admin sees that a grant happened, never what the Bot did with it.

## Accounts

`internal/app/account`, primitives in `internal/auth`.

- **Bootstrap:** `bootstrap.*` makes the first admin and acts at start only while **no enabled admin exists** (`auth.EnsureBootstrap`: promote the user with that email, else create them), never otherwise: emails can change, and whoever holds the bootstrap address later must not be promoted.
- **Invites:** everyone else comes from an invite link (`CreateInvite` → `{public_url}/invite/<token>`, single use, 7 days) or a Workspace invite. The same row with a `UserID` is a 24 h password-reset link. Only the token's hash is kept, so a link is returned once and replaced, never read back. `AcceptInvite` signs a new account in; a reset does not (a second factor still stands) and ends that user's sessions.
- **Public RPCs** are a set in `app.go` (`publicRPCs`: `SignIn`, `AuthOptions`, `GetInvite`, `AcceptInvite`); every other one gets the user and the session on its context (`access.Session`). The backend returns `Unavailable`, not `Unauthenticated`, when the session store fails (`sessionError`).
- **Sessions** are keyed by `ids.Hash(cookie)`, never the cookie (`Migrate` rehashes rows from before, marked by `created_at IS NULL`, with their tunnel grants). They carry user agent, client address and method; `last_seen_at` is touched at most every 5 minutes; `auth.EndUserSessions` (password change, reset, disable, "sign out everywhere") also drops the tunnel grants made from them. `SignOut` deletes the `Session` row (`auth.EndSession`), not just the cookie.
- **Email** is the sign-in name, stored lower-cased. A user changes their own with `ChangeEmail`, with no confirmation (Silo sends no mail), which sets `users.email_self_set`; an admin setting it (`UpdateUser.email`) clears the flag. **OIDC must never match an account by a self-set email** (a user could take a colleague's address and be handed their identity and admin group).
- A wrong *current* password is `InvalidArgument`, never `Unauthenticated`: the web client reads `Unauthenticated` as the session having ended.
- **Two-factor** is hand-rolled RFC 6238 (`auth/totp.go`, ±1 step) for password sign-in only. `SignIn` with a right password and no code answers `needs_code` and signs nobody in; the client resends email + password + code (no pending state on the server). A used time step is stored (`users.totp_step`) with a conditional update, so a code cannot be replayed or raced; recovery codes are rows of `hash(userID:code)` crossed off the same way.
- **Throttling** (`auth.Limiter`, in memory) counts failures per account+address (5, then a wait doubling 30 s → 15 min), per address (20 / 15 min) and per account (50 / h), for passwords, codes and invite tokens. The address is `auth.ClientIP`: the peer, unless it is in `auth.trusted_proxies`, then the right-most `X-Forwarded-For` hop that is not itself trusted. **Never read that header anywhere else.**
- **OIDC** is one provider (`oidc.*`; on when issuer and client id are set) behind `/auth/oidc/start` and `/auth/oidc/callback` (go-oidc + PKCE + nonce; state in memory for 10 min and in an HttpOnly cookie, so a callback from another browser is refused). A sign-in resolves to the user linked to (issuer, subject); else the user with that email **only if `email_verified`**, not linked elsewhere and not `email_self_set` (linked now); else a new passwordless user when `oidc.auto_create` and `allowed_domains` allow; else nobody. `oidc.admin_group` sets Admin at each sign-in but never demotes the last enabled admin. Failures redirect to `/signin?error=<code>` and the page words the code (`web/src/signinFlow.ts`): never put free text in that redirect. The landing path goes through `access.SafeReturn`. `auth.password=false` is honoured only while OIDC is on (`Config.PasswordSignIn`). Discovery is cached per issuer and the other trailing-slash spelling is tried; `CheckOIDC` (admin) re-discovers and is never `Unavailable`. Tests use `internal/auth/oidctest`; dev has Dex on `:5556`.
- **Disable** (`users.disabled`) is `ErrAuth` in `SessionFromRequest`. It suspends the Bots the user leaves with no enabled manager (`access.Suspended`): `account.Host.SuspendUser` stops their channel workers (`channel.Service.Suspend`), runs and boxes (`haltBot`), `StartRun` refuses them (`errOwnerDisabled`; automations, channel inbound and subagent wakes all pass through it), `Reconcile` skips their channels, and the tunnel proxy answers 404 even for public tunnels. A Bot with another enabled manager keeps running.
- **Delete** is `DropUserBots`: the Workspaces the user is alone in go with their Bots (`App.dropBot`, the body of `DeleteBot`) and skills, and they are taken off every other one.
- **An admin cannot demote, disable or delete themselves**, which is what keeps one admin. Do not add a path around that.

# Connectors

## Connections and grants

`internal/app/connector`. **A connector a Bot uses is a Workspace's connection granted to it** (`grants.go`).

- The connection is a `custom` row with `space_id` (made from a library preset or a custom MCP), defined once. A `bot_connectors` row grants it to one Bot of the same Workspace (`grant` refuses any other; `TestGrantsStayInSpace`).
- **On the connection** (the same for every Bot): the definition, a built-in's config, and the OAuth sign-in (`connectors.token_json`, a `storedToken`: the token plus the token endpoint and client that refresh it).
- **On the grant** (the Bot's own): its MCP session (`s.mcp` keyed by grant id), its STDIO sidecar (one process never serves two boxes), the tools its session listed (`ToolsJSON`) and its status. These stay per grant because `${secrets.NAME}` in a connection resolves per grant from that Bot's own secrets (`Resolve(c, botID)`), so two Bots' sessions on one connection can reach different accounts.
- **Token refresh:** every session on a connection shares one `connToken`; a refresh happens once, under the connection's lock, from the token as stored now, so two sessions meeting an expired token make one refresh and a provider that rotates refresh tokens strands neither (`TestSharedTokenRefreshesOnce`). Stored tokens refresh after a restart too.
- Names (and so `tools.<slug>`) are unique per Workspace (GitHub, GitHub 2).
- RPCs: `AttachConnector` with a preset makes a new connection and grants it, with a connection grants it. `CreateBotConnector` adds to the Bot's Workspace (or `space_id` from the Workspace page) and grants to `bot_id` and `bot_ids`. `GrantConnector`/`RevokeConnector` (and `DetachConnector` by grant id) give and take. Deleting a connection (whoever added it, or a Workspace admin: `canEdit`) revokes it everywhere; a Bot's delete drops its grants only; a Workspace's delete drops its connections.
- `created_by` is who added it; `lent_by` whose identity it carries (who signed it in, or typed a credential into its headers, environment or a built-in's secrets); `shared` its lender's say-so (see Lending).
- **Choose Bots** on the Workspace page's Connectors tab is the only place a Bot is given a connector; a Bot has no Customize page of its own.

## The library

- Presets seed from `internal/catalog` (`connectors.json` + images; insert-if-absent by `seed_key`). Library rows are templates. Admin → Connectors has Re-add defaults and row remove; default mode allow/ask/deny.
- Every preset has an `identifier` (`catalog.Identifier`: lowercase ASCII letters and digits, any other run one `_`, so fal.ai is `fal_ai`; unique by a partial index; only library rows have one). The admin form fills it from the name (`web/src/connectors/form/ident.ts`) and the server normalises again; `catalog.Seed` gives an old row its catalog identifier if free, else its own id.
- A preset carries a `prompt` (extra system-prompt guidance, injected only once the connector is authorized) and `auto_attach` (default false). `CreateBot` grants flagged presets exactly once (the Workspace's connection from that preset when there is one, so two Bots share one Lightpanda and keep a session each), so a preset the human removes from a Bot is never re-added.
- `autoenable_connectors` (silo.yaml list or comma-separated `SILO_AUTOENABLE_CONNECTORS`; Admin → Settings → Connector options) names presets by identifier that every new Bot gets as well. `connector.Service.defaults` is the one query behind both (`auto_attach OR identifier IN …`); an unknown identifier is logged and skipped.
- The `lightpanda` preset is the primary web **reader**: one shared Lightpanda (dev compose, HTTP MCP on :9223, each MCP session its own browsing context) at `${LIGHTPANDA_URL}/mcp` (an operator connector variable), `auto_attach`; its prompt says `markdown(url=…)` over Chromium for reading.
- The add form is shared by the Admin library, the Workspace's Connectors tab and the setup-offer modal. Clicking a library preset shows the mark + large name, a bindery-edged "Before you add" well, and collapsed Advanced settings; submit is `CreateBotConnector` with `source_id`. Catalog `guide` is display-only copy on the add screen, not stored on the row.
- The Connectors prompt section says which connectors are also chat tools; the thread shows such a call as connector · action with the connector's mark.

## MCP over HTTP and STDIO

- **`internal/mcpx` is a thin wrapper over the official go-sdk client. Do not hand-roll the transport** (handshake, sessions, SSE, `Mcp-Method`/`Mcp-Name` headers all live in the SDK). Connect tries Streamable HTTP (± trailing slash), then the legacy 2024-11-05 HTTP+SSE transport (Cloudflare-style `/sse` URLs need it).
- Connector headers and OAuth (bearer + Authorize-on-401 + one retry via `GetBody`) live in one `RoundTripper` so both transports share them.
- **OAuth** opens `{public_url}/oauth/callback`. The SDK tries CIMD, then a pre-registered `client_id`/`client_secret` on the connector, then DCR (GitHub has no `registration_endpoint`, so the form takes an optional OAuth Client ID and Secret).
- MCP URLs keep their query (`?codemode=false` is real config: it turns off Cloudflare's code-mode `execute` wrapper), but the query and fragment are stripped from the request handed to OAuth `Authorize`, because the SDK derives the resource identity (`resource=`, `.well-known` lookups) from it and Cloudflare validates that strictly (issuer `https://mcp.cloudflare.com`).
- Cloudflare and similar advertise RFC 9207 `iss` but omit it on the callback: fill it from the authorize URL's origin. A 401 with an empty body is a challenge; do not swallow the OAuth error behind `initialize: http 401: (empty)`.
- **STDIO sidecars:** one isolated container per STDIO grant; `silo-mcp-bridge` **dials the CP** over ConnectRPC `MCPHost.Tunnel` with a per-grant bridge token (`bridge_token_hash` on `bot_connectors`) and raw-pumps JSON-RPC to its child. A curated image or a generic Node/`npx` command; structured argv, never a shell; no published port.

## Built-in connectors

`internal/builtin`, transport `builtin`: connectors written in Go on the CP. A descriptor declares config fields (`Advanced` ones fold under "More settings"), tools (JSON-schema `Params`, per-action `Mode`) and a `Check` login, and registers from `init()` (blank-imported in `internal/app/connector/builtin.go`).

- They use the connector engine unchanged (catalog preset `"builtin": "<key>"`, Workspace connection, cached `ToolsJSON` per grant, `pushTools` stubs, Rules, prompt section), except `refreshTools` runs `refreshBuiltin` and `CallTool` runs `connector.Service.RunBuiltin`. Per-action modes are the `AuthorizeAction` fallback (`connector.BuiltinMode`).
- Config is on the connection (the time zone is the calling Bot's): `ConfigJSON` plain, `SecretsJSON` secret (never returned; a blank secret on update keeps it; library rows hold none). A required field unset is `needs_auth` with a "Fill in …" detail, and the UI shows **Set up** instead of Authorize. Secrets are masked from results and errors.
- The descriptor `Prompt` (terse, code-owned, `{slug}` becomes the copy's slug, shows the exact call shape) is appended after the row's catalog prompt, so it stays current on old copies.
- Tools touch the workspace only through `builtin.Env` (worker `browse_file`/`put_file`; no `..`). Every dial and HTTP client goes through `builtin.Config.Net`.
- **Email** (`internal/builtin/email`): IMAP via go-imap v2, SMTP via go-smtp, provider presets (Gmail/Outlook skip the Sent APPEND), attachments by index from `read`. `emailtest` runs an in-memory IMAP + capturing SMTP server; dev smtp4dev is on `:1025`/`:1143`. It shares nothing with the Bot's own Mail beyond `internal/htmltext`.
- **Calendar** (`internal/builtin/calendar`): CalDAV via go-webdav/go-ical; provider presets or a URL (manual `/.well-known/caldav` redirect: Go drops the PROPFIND body on 301). The home set is read by hand and the session moves to its host (iCloud answers with an absolute `pNN-caldav.icloud.com` URL and its front host returns no events to a REPORT; go-webdav keeps only the path). The event REPORT is hand-built with plain `<calendar-data/>`; hrefs without data are GET; unreadable objects surface as `skipped_unreadable`; discovery is cached 5 min per account. Recurrences are expanded client-side (servers treat the time-range filter loosely); timed events are written with the zone TZID + a generated VTIMEZONE; PUT carries `If-None-Match`/`If-Match` itself (`PutCalendarObject` has none). The zone falls back to the Bot's (`builtin.Config.TimeZone`). `caldavtest` serves go-webdav's handler in memory; dev Radicale is on `:5232` (`silo`/`silo`).

# Channels

`internal/channels` (adapters), `internal/app/channel` (the domain). Built-in adapters only: Telegram (gotd MTProto), WhatsApp (whatsmeow), Discord (discordgo).

- One adapter instance is a `Channel` row (per Bot, unique name). Channel conversations are `Chat` rows tagged `channel_id` + `external_id` (web chats keep `channel_id=''`).
- Adapters own config (per-channel secrets are `channel.<id>.<key>` Secret rows, hidden from the Secrets tab and `secrets.*`), dynamic state (`State`: info/QR/select for QR logins and chat pickers), lifecycle, interactive `Setup` actions (`pick`/`run`/`qr`) and an embedded `GUIDE.md`.
- The Channels page has sub-routes `/bots/:id/channels[/new[/:adapter]|/:channelID[/setup]]` so browser back works.
- `requires_target` adapters (all three) bind the row to exactly one conversation picked in Setup (`set_target` → `external_id`/`target_title`), and only that one is read or written. A channel that still needs its target shows a blinking **Set up**. `reply_mode` gates groups/servers; DMs always answer.
- Channel workers start from `channel.Service.Reconcile`. **Adapter `Start` is live-only: never backfill missed messages.** A channel with `inbound=false` is send-only (tools only).
- **Tools:** the `channel` tool sends (default the origin channel; rule `channels.<channelID>`, manager-only); `chats` reads history through the adapter for channel conversations and the DB for web chats (rule `chats.read`); Python: `silo_runtime.send_channel`/`read_chats`/`feed`. When an adapter cannot give history (Telegram bot accounts get `BOT_METHOD_INVALID`; WhatsApp always errors) it falls back to the local run log, and the adapter flags `noHistory` per channel and stops retrying.
- `present`/`artifact` on a channel attach the real bytes (`workspace.Service.Attachment`; a pinned folder is zipped by `artifact.Service.Attachment`).
- Shared helpers: `channels.Chunk` (rune-aware cut at paragraph/line/word that closes and reopens a code fence across a split) and `Seen` (bounded id set for redelivery and echoes). `channels.Remover` is an optional hook that `channel.Service.Delete` calls *before* stopping the worker (so `DeleteBot` runs it too); its failure is logged and never blocks the delete. `Host.DatabaseURL()` is for libraries that keep a session in SQL; it carries the password, never log it.
- The Setup page adopts the polled state only while it is a pairing state (`qr`/`auth`), because Telegram/Discord publish value-only states that must not replace the picker list under the user.
- **Telegram:** history is `messages.getHistory`. Bot accounts cannot enumerate dialogs (`messages.getDialogs` → `BOT_METHOD_INVALID`), so the picker lists chats the bot has seen (persisted in channel state) and accepts a typed `@username`/`t.me` link/id. Files upload with `uploader.FromBytes` + `.File`.
- **WhatsApp** is whatsmeow as a *linked device* on the owner's account (the unofficial protocol: GUIDE.md says to use a spare number), so the account is the Bot and there are no fields beyond `reply_mode`.
  - The session lives in the CP Postgres (`whatsmeow_*` tables via the pgx `database/sql` driver), backed up with the rest. A device is found again by the JID saved in channel state (`Values["jid"]`, published on `PairSuccess` before anything else can fail); a JID with no row pairs fresh.
  - Pairing is a QR (`rsc.io/qr` → PNG data URL in `StateQR`, status `pending_auth` = "Needs linking") that the library rotates; a timeout does not loop, the run waits for **Link device** (`run.relink` is unbuffered on purpose: a press nobody waits for is dropped). `LoggedOut` clears the JID and waits for Link device; `StreamReplaced`/`ClientOutdated`/`TemporaryBan` end the run as errors.
  - Chats match by user+server; a direct chat can arrive as a phone number or a LID: use `SenderAlt` for a message from them and `RecipientAlt` for one the owner sent (never the owner's own alt, or a message to Alice reads as a note to self), then the library's LID→number map. `IsFromMe` is ignored except in the "message yourself" chat, and there the Bot's own sends are ignored too (`client.sent`: the id is remembered *before* `SendMessage`, because the echo can beat its return). Messages older than `liveSince` (start − 5 s) are dropped: the server delivers an offline queue on connect.
  - Event handlers run one at a time on the library's queue, so the read receipt and "typing…" go through `client.spawn`. Outbound Markdown becomes WhatsApp markup (`format.go`); files go as image (png/jpeg/webp), video, audio or document by mime (GIF/SVG are documents); inbound media is a placeholder plus caption, not downloaded; `Outbound.ReplyTo` is unused. `Remove` logs the device out and deletes its keys.
- **Discord:** the gateway for inbound, REST for send, history and the picker. The target is a channel id (a `discord.com/channels/…` link or `<#id>` is accepted). **Pick a channel** lists every text/news channel the bot can write in plus the DMs it has seen (`dm:<channelID>` state values); **Invite link** builds the OAuth URL. Intents are guilds + guild/DM messages + the privileged Message Content; gateway close `4014` retries without it and runs *limited* (DMs and @mentions only) with a warning, `4004` is a bad token. In a server it answers an @mention or a reply unless `reply_mode=always`; other bots, webhooks and system messages are ignored. Sends use `allowed_mentions: users only` (a model-written `@everyone` must not page a server), chunk at 1900 runes, and put files (10 per message) on the last chunk.
- **Tests** drive adapters without a network: Discord through a fake `http.RoundTripper` plus direct calls of the inbound handler, WhatsApp through a `waAPI`/`directory` seam over the client and the real dev Postgres for the session store.

# Features

## Memories and SOUL

- Memories are pgvector rows (`memories`, `vector(1536)`, per Bot, with `chat_id`) behind `remember`/`recall`/`forget` (rules `bot.*`, Allow). `embedding_model` must be OpenAI-compatible (`llm.Embedder`; Anthropic cannot embed).
- They reach the model through the prompt, **never through a search made while the human waits** (`internal/app/memory/prompt.go`, `memory.in_prompt`): while their text totals at most `memory.InjectMax` (6000 characters) every memory is listed, oldest first; past that a **digest** stands in, a briefing `memory.Service.SweepDigests` (a `tickLoop`) writes with `model_memory` (`prompts/MEMORY_DIGEST.md`) into `memory_digests` (its own table: the bots row is saved whole in places), keyed by a hash of the store so an unchanged store is not summarized again, rewritten at most every 30 minutes. Until the first digest exists, the newest memories that fit are listed. The section sits after the last system cache breakpoint.
- `recall` is the embedding search. Vector `ORDER BY` goes through `Clauses(clause.OrderBy{Expression: …})`: GORM silently drops `Order(clause.Expr)`.
- The Memories page is `ListMemories` (newest first) with search (`SearchMemories`: embeds the query and ranks by cosine, shows a match %, never bumps `last_used_at`) and an armed delete (`DeleteMemory`). Humans do not add or edit memories; the Bot does with `remember`.
- **SOUL** lives in Postgres (`bots.soul`), not on the box, and is in the system prompt every run. Tool `soul` (rule `bot.soul`, manager-only) writes the DB (no worker hop); Settings edits it too. `ListBots` omits the body; `GetBot`/`UpdateBot` include it.

### Memory collector

`internal/app/collect.go`, prompt `prompts/MEMORY.md`. It saves what the Bot forgot to `remember`.

- It reads a chat's events after its watermark (`chats.memory_seq`, a `run_events.seq`) as a flat transcript (tool output capped short, failures kept longer), and one tool-less completion with `model_memory` (default: the title model) answers JSON `save` / `update` / `forget`. The model is shown the 15 closest existing memories and may `update`/`forget` only those ids. Saves go through `memory.Service.Save` (the `remember` dedupe).
- The watermark advances after a read, including an unreadable reply, but never on a provider/embed error, so every event is read once. Chats older than the column start at their newest event (`Migrate`).
- The sweep (a `tickLoop`, 5 min, `memory.collect`) reads web and channel chats (never automation or subagent logs) whose newest new event is over 10 min old and that have no live run, at most 5 per tick; it pauses 15 min after a provider error, and a chat whose collection fails rests 15 min, doubling up to 24 h (`restChat`). A delta over 12k tokens is split into at most 3 calls and the oldest excess dropped.
- The composer's brain button (`MemoryCollect.tsx`, `CollectMemories`) and `/remember` run it now for one chat.

## Knowledge (RAG)

`internal/rag`, `internal/app/knowledge`, worker `knowledge.go`. The owner picks workspace folders (drives included) and the Bot searches them with `search_docs` (rule `bot.search_docs`, Allow; offered only while the Bot has a folder and `knowledge.enabled`).

- Files stay on the box; `knowledge_folders` / `knowledge_sources` / `knowledge_chunks` (`vector(1536)` + generated `tsv`, HNSW + GIN) live in Postgres per Bot, separate from `memories`.
- **Worker commands** (read-only): `Walk` (path/size/mtime, recursive, skips hidden and heavy dirs and symlinks, skips `drives/` unless the root is in one; **a missing or unreadable root is an error, never an empty list**) and `Extract` (text + sha256 of the bytes: text as is, PDF `pdftotext -layout` with form feeds as pages, docx/odt/rtf/epub/html `pandoc -t gfm`, `.doc` `catdoc`; binary or over 50 MB is `skipped`; the converter is looked up before the file is read, so a missing tool costs no drive download).
- **Sync** (`knowledge.Service.SyncFolder`, one per folder under a lock) is **size+mtime first, sha256 only for changed candidates**: same hash = refresh mtime, no embed; a vanished path whose hash shows up at a new path is a rename and keeps its chunks; a changed `embedding_model` re-embeds (`embed_model` is on the source); an error source retries after 1 h. An empty listing of a `drives/` folder that had an index is a disconnected drive (error, nothing deleted).
- Chunks come from `rag.Split` (form-feed pages, markdown heading path, ~2400 chars with overlap; the embedded text is prefixed with file + heading).
- **Search** is hybrid: top 30 by cosine (dropped past 0.85 distance) + top 30 keyword (`plainto_tsquery('simple')`, all-words matches first, stopwords stripped), fused by reciprocal rank in one SQL. It runs on the raw ConnPool with `$n` args because GORM `Raw` mishandles `@@`, and sets `hnsw.iterative_scan` (pgvector 0.8) behind a savepoint so the per-Bot filter still returns k rows.
- **The sweep** (a `tickLoop`, `knowledge.Tick` = 30 s; `knowledge.sync_interval` default 15m, drives ×4) syncs a folder when it is stale or `dirty_at` is 15 s old (set by the Bot's `write`/`patch`/`delete` and the Files tab via `knowledge.Service.Dirty`), skips Bots with no worker (never starts a box), at most 2 per tick, pauses 15 min on a provider error.
- Adding refuses the workspace root, `bot/`, `tmp/`, the bare `drives` root, anything missing, and any folder nested in or holding another. Caps: 5000 files and 2 MB of text per file.
- **OCR** (`knowledge.ocr`, default on; worker `ocr.go`): after `pdftotext`, only pages with under 20 non-space characters are rasterized (`pdftoppm -r 200`) and read with tesseract (every installed language, English first; the image ships eng + pol), 3 pages in parallel at one thread each, at most 100 pages and 4 minutes per file; image files (png/jpg/tif/bmp/gif/webp, ≥8 KB) go straight to tesseract. Recognized text must be ≥60% letters/digits or it is dropped as photo noise. With OCR off the worker words a scan `OCR is off`, the source is recorded as skipped with that detail, and `sourceUnchanged` re-reads such files once OCR is on. A missing tesseract fails that file only.
- The worker tests that need the image's tools skip on a host and run for real in the image (TESTING.md); `TestContainerKnowledgeAllFormats` is the end-to-end proof.
- The Knowledge page (`/bots/:id/knowledge`) has a folder picker (dirs only, drive disclaimer, `NeedMachine` when the worker is down), per-folder status / Sync now / armed remove, the not-indexed list, and a try-a-search panel (`SearchKnowledge`). The prompt lists folder paths only (counts would bust the cache tier). Snippets can lag edits: the tool tells the model to `read` the cited path before relying on one.

## Changes

`internal/app/changes`, worker `history.go`. Diffs of what changed in a Bot's workspace. **It compares state, not actions**: a file a script wrote is seen like one `write` wrote, so never track the file tools instead.

- **The store:** a shadow git repository **outside the workspace** (`/var/lib/silo/history`, bound from `data/bots/<id>/history`, so Files, grep and Knowledge never see it and it outlives a container reset; `GIT_DIR`/`GIT_WORK_TREE`, the user's and system git config ignored), used as a snapshot store only. A **checkpoint** is a parentless commit under its own ref (`refs/silo/cp/<unix nanos>`), so any two diff and forgetting one is deleting a ref; an unchanged tree makes no checkpoint.
- **What keeps it from swallowing the workspace:** `info/exclude` holds `/drives/` (FUSE remote data must never be listed), `/tmp/`, `/bot/` and `grepPruneDirs`, and excluded directories are not descended into; the workspace's own `.gitignore` files are honoured; a file over `changes.max_file_mb` is never hashed (the tree gets a **stub** blob of size + mtime through a throwaway index, because a stub in the real index would make git hash the file to refresh it); a nested repository is one gitlink; one checkpoint adds at most 20k files / 512 MB (a huge workspace is indexed over several, marked `partial`, and a change set whose base was partial is the index catching up, not a change); checkpoints expire by count (300), `changes.keep_days` and a 1 GB budget.
- `git add` runs with `--ignore-errors` (an unreadable file must not cost the checkpoint) and is retried once when a listed path vanished; a stale `index.lock` from a cancelled git is removed under the worker's history mutex. A tracked path under a folder that became a link or a file is dropped with `update-index --force-remove`, never handed to `git add` (it dies on "beyond a symbolic link").
- **Worker commands:** `Restore`, `Checkpoint` (carries the CP's opaque `note`), `Changes` (consecutive pairs newest first, plus **pending**: the working tree against the last checkpoint, uncommitted; takes the baseline or the next partial slice itself), `ChangeFiles` and `ChangePatch` (ids must be 40–64 hex: they go to git as arguments). **Nothing is in Postgres**: the pane needs the machine up.
- **Attribution:** `changes.Service.Begin` runs before a run's first tool whose `Def.Writes` is set (terminal, exec_python, write, patch, delete, and the desktop's click/type/key) and `End` after `finish` (in a goroutine). A change set is attributed to **every run that has begun changing things on that Bot** in that stretch (the workspace is per Bot, so concurrent chats share a diff and the pane says so); what a run's opening snapshot finds is "Outside a run" (the owner in Files or the Console, a background process). A snapshot never fails a tool. An old worker (`unknown cmd`) or an image without git reads as `ListChanges.state = outdated` and the pane asks for a container reset. `GetChangePatch` masks secrets like `ReadFile`.
- **Restore** (`RestoreChange`, worker `Restore`) puts back one file or every file of a change, as before that change; the owner's button only, not a Bot tool. The worker checkpoints first (`before_restore`), acts on the difference between the wanted snapshot and that checkpoint, then checkpoints again (`restore`, titled "Restored by you"), so a restore loses nothing and is undone like any change. **Acting only on that difference is the safety:** a path the history never tracked (a drive, `bot/`, an ignored folder) cannot be removed whatever the caller names. It skips and reports what could not be taken back: over the cap or a nested repository on either side (`large`/`repo`) and a path with a link, file or non-empty folder in its way (`blocked`; `realParents` keeps a write from following a symlink out of the workspace). Files are written by `git checkout-index` from a throwaway index of the old tree. It refuses while the workspace is still being indexed and marks Knowledge dirty (`workspace.Service.Changed`).
- **Drives get a journal, not snapshots** (`internal/drivehost/journal.go`, `internal/app/changes/drives.go`): listing a drive is network calls and reading one downloads the owner's data, but everything that writes to a drive crosses its FUSE mount, so the sidecar reads each change off rclone's own log (which catches a script; a folder is `objectType` `*mount.Dir`). rclone logs an upload at INFO (`Copied (new)` / `Copied (replaced existing)`) but a delete or folder rename **only at DEBUG** as the mount layer's call and its result (`Remove: name="x"` then `>Remove: err=<nil>`), so mounts run `--log-level DEBUG --use-json-log` (reserved flags a spec cannot change). `logSink` decides on the raw bytes, parses only the lines that matter, and passes on only notices/errors/non-JSON as rclone's plain log line, so `CleanError` and the container log read as before. Calls on one directory are matched to results first in, first out; a failed call is nothing. `TestJournalReadsRcloneLines` pins a capture and `TestDriveEngine` (`-tags engine`) checks the image's rclone: re-check both when bumping rclone.
- A file written and removed before rclone uploads it never shows; an upload shows when it reaches the provider. Changes leave the sidecar in batches (`DriveUp.changes`, 200 a frame, a 300 ms gather; frames queued while the CP is away can overflow and are lost). The CP files them as `drive_changes` rows (`Seq` orders them; newest `changes.DriveKeep` = 2000 per Bot; the drive's name is on the row; what a sidecar sends is cleaned, not believed) through `drive.Service.OnChange` → `changes.Service.RecordDrive`, stamped with the runs at work **or ended within 45 s** (`driveGrace`). No content is kept and there is no restore (the pane points to the provider's version history). `ListDriveChanges` needs no worker.
- **The pane** (`web/src/Changes.tsx`, helpers in `changeset.ts` because `changes.ts` would clash on a case-insensitive disk) is a right-rail pane with a **Files | Drives** switch (Drives shown once the Bot has a drive, readable while it is stopped, which is why it keeps its own header). Rows open into files, files into the diff; it polls only while visible, since every look snapshots the workspace. Config: `changes.enabled`/`max_file_mb`/`keep_days`. `DeleteBot` drops the journal (`changes.Service.Drop`).

## Web search

`internal/search`, `internal/app/websearch.go`. Python only: `silo_runtime.web_search` / `web_search_many` under `web.search`. The model picks the language per query (`language`, optional `country`; `region()` fills in the other); `queries` (max 10) is a batch in one call.

- **Keyed engines** (`internal/search/keyed.go`): **Brave Search** (`brave`, `api.search.brave.com`, `X-Subscription-Token`) and **Exa** (`exa`, `POST api.exa.ai/search`, `x-api-key`, highlights as the snippet), each with a secret `search.<id>.api_key`. Cached 5 minutes with one flight per query, a 429 retried once, 401/403/402 worded as the operator's problem, the key never in an error. A failure is an error, not a `blocked` note. Brave retries without `country`/`search_lang` on a 422; Exa takes only the country.
- **The Built-in Scraper** (`builtin`, the default) is a keyless metasearch over sources: `duckduckgo`, `mojeek`, `brave`, `startpage`, and the APIs `wikipedia`, `marginalia` (`search.builtin.sources` narrows the list). Two things rule it:
  - **Speed:** `meta.run` never waits for a stuck source: each has 2.5 s, once 3 have answered the rest get 300 ms, after 1.2 s any results in hand are enough, 4 s is the ceiling (constants head `meta.go`).
  - **Manners:** the CP is one address to a search site however many Bots it serves, and a site asked too often blocks it for everyone. Every scraped site has a token `bucket` (one request per 6 s, 2 at once; shared package state), and a search asks the APIs plus at most `fanout` (2) scraped sites: the one with the most budget left, and a second only while it is *idle*, so a burst spreads thin. The rest are a reserve, one asked for each that fails. With every budget spent a search queues up to `queueMax` (8 s); past that the site is `busy`. **Do not add a scraped source without a `limit`** (`TestScrapedSourcesAreLimited`), and do not loop the live test: it spends the same budgets from the same address as the running CP.
- Lists merge by reciprocal rank fusion on a canonical URL (`fuse.go`: no scheme, `www.`, fragment, trailing slash or tracking parameters); `Hit.engines` is how many providers returned the page.
- **Blocked vs empty:** a source answers `errBlocked` for a refusal, a captcha, or a page with neither results nor the site's own "no results" notice; a true empty page is `nil, nil`. The `breaker` backs a failed source off (30 s doubling to 30 min; a rate-limited refusal, 429/DuckDuckGo's 202/503, rests at least 2 min or its `Retry-After`; a source cut short because the search was done gets no verdict). `Result.blocked` names who did not answer, and a result empty because of them carries a `note`, so the model does not conclude nothing exists. Answers are cached 5 minutes per text+language+country (never an empty-because-blocked one); identical concurrent queries share one flight.
- **The browser the sites see** (`http.go`) is Chrome 145 on macOS in every layer: utls's Chrome 133 TLS hello (still what 145 sends), Chrome's HTTP/2 SETTINGS and window, pseudo-header and header order (`chromeOrder`), and the headers of the navigation it claims (`navigation`). It is built by hand on `imroc/req`, not with `ImpersonateChrome`, whose preset mixes versions: a client that is Chrome in one layer and not another is what bot detection looks for. `TestFingerprint` (live) compares it with known hashes; re-run it when moving to a newer Chrome, and copy a real one's values rather than guess. No cookie jar. The two APIs are asked under our own name (Wikipedia refuses a client that only looks like a browser).
- DuckDuckGo html and lite are one source (lite only when html is broken, never when rate-limited). Wikipedia is a *title* search (`generator=prefixsearch` with extracts, disambiguation dropped). Google and Bing are not scraped.
- Source tests replace `fetch` and read captured pages in `testdata/`; `SILO_SEARCH_LIVE=1 go test ./internal/search -run 'TestLive$' -v` runs two real searches (`SILO_SEARCH_ONLY=brave` asks one source past its budget: sparingly).

## Artifacts

`internal/app/artifact`, worker `artifacts.go`. The chat tool and `silo_runtime.artifact` share `artifact.Service.Tool` (rule `artifact`, Allow).

- Each emitted file or tree is pinned into the worker's content-addressed store (`/var/lib/silo/artifacts`, bound from `data/bots/<id>/artifacts`, mode 700, crash-safe tmp+fsync+rename, verified by SHA-256 on every CP read), recorded as `Artifact` + `ArtifactVersion` rows keyed by `(bot_id, chat_id, path)`, so repeated emits become v2, v3, … on the same card with an inline update row. An emit-time preview is captured (text excerpt, CSV rows, or a JPEG thumbnail via ImageMagick/`pdftoppm`).
- `artifact` peeks `SKILL.md` (that directory becomes a skill card) or stats a file (a downloadable card with type icon, download and preview hatch). A skill does not install until **Save skill** on the card (`SaveSkill`) copies the pinned version into the Bot's Workspace.
- Downloads: `/artifacts/download` (one version: a file, or a folder as a zip; cookie auth) and `/artifacts/skill.zip`. The Bot's Artifacts page is `/bots/:id/artifacts`.
- **Live HTML apps** at `app-<name>.<content.host>` (`internal/app/artifact/content.go`, `ServeApp`; gated by `artifact.app_network` Ask when `network: true`). The sandbox has no `allow-same-origin` on purpose, so an app has no storage: with an origin it could plant cookies for the parent domain and leave a service worker serving old versions. The tool text, `silo_runtime` and SYSTEM.md tell the Bot so.
- **Public shares** at `share-<name>.<content.host>` (`ServeShare`) are copied to `data/shares/<id>` on the CP so they work while the Bot is stopped.
- Deleting a chat forgets unreferenced versions; a background sweep enforces `artifacts.max_mb` (default 2048 MB per Bot).

## Skills

## Dashboard

`internal/app/dashboard`, `web/src/dashboard/` (the page is `Dashboard.tsx`; the question card the thread and the board share is `web/src/ask/`). The owner's board per Bot, the top row of the sidebar: **widgets** the Bot keeps current and **asks** it needs decided.

- **The model writes a widget once and code keeps it current.** `put_widget` (rule `bot.widget_put`) stores a kind, title, size (`s`/`m`/`l` = a quarter, half, the row of a 4-column grid; `rows` 1–2), a `spec` (kind settings plus `actions`) and either pushed `data` or a `probe` (Python that sets `result`) with an interval `every`. `set_widget` (rule `bot.widget_set`) pushes data from any cell with no model and no approval.
- `Sweep` (a `tickLoop`, `dashboard.Tick` = 20 s) runs due probes on the box through `Host.RunPython` (a throwaway `ExecPythonCmd` outside any run, 60 s, at most 4 at once, never starts a box, a claimed `next_at` so a slow probe is not started twice). A new probe runs at once inside `put_widget` so the Bot sees its `data` or `probe_error`. A stopped Bot's due probes are moved on (`offlineRetry`) without touching their data.
- **Code in a widget** (its probe and every `run` action) goes through `AuthorizeAction(python.run)` **once, when it is put**, and only that code runs later (`ApprovedHash` over the probe and actions; a change is a new approval; a rule now at Deny stops it). `harness` binds `ARGS`/`STATE`/`DATA` from base64 and reports `result` on a nonce-marked line. The page never receives action code (`publicSpec`).
- Kinds are a closed set Silo draws itself (`dashboard.Kinds`: note, stat, chart, list, table, timeline, status, checklist, progress, ideas, app; data shapes in SYSTEM.md and `web/src/dashboard/widgets.ts`). An **app** widget is a live-app artifact in the hatch, loaded on its own origin through `OpenArtifactApp` only once scrolled into view. **Ideas** (`{items: [{title, prompt}]}`) put the prompt in the main chat's composer, unsent (`dashboard/Ideas.tsx`); until a Bot has one the board shows `StarterIdeas`, a translated set shaped by what is connected and written by no model.
- **The owner acts in place:** a checklist's checks are widget state (`SetWidgetState`, no run; the Bot reads it in `list_dashboard`); a `run` action executes the stored code with `ARGS` = the row or `{}` (`RunWidgetAction`), may return `{"receipt", "data"}`, re-runs the probe otherwise, and leaves a receipt; a `hand` action quotes the widget as it stood into a chat with the press as the owner's turn ("I pressed **X** on it."). `ArrangeDashboard` sets `owner_placed`, after which the Bot's `size`/`rows` are ignored.
- Widget writes name their columns (`dataColumns`, `Select`), never `Save` the row: an approval can wait on the owner while they check items or arrange.
- `ListDashboard` also carries the unread Feed posts (shown for the visit as "Since you last looked"; `MarkDashboardRead` reads them, the asks and the changed widgets: `changed_at` vs `seen_at`) and the pinned Dashboard automation's last/next run. `Bot.dashboard_asks` (`dashboard.Service.Open`) is what the sidebar's Dashboard row reads, with pending approvals, for its Needs you; it never loads the board.
- **The ask bar** (`AskDashboard`) sends the owner's words, with a picked widget, to the Dashboard automation's log via `automation.Service.Ask` (joins a live run or starts one), so changing the board never adds a chat.
- **Asks** are `DashboardCard` rows (tools `upsert_dashboard_card`/`remove_dashboard_card`, rules `bot.dashboard_upsert`/`dashboard_remove`): display blocks and form controls whose submit quotes the ask into a chat with the values as the owner's turn ("I chose **X** with: …"); dismissing with "Don't suggest this again" saves a memory.
- **The curator:** the model touches the board only in `dashboard.Curator`, a pinned automation the dashboard package registers itself (`automation.Service.Pin` in `dashboard.New`; the automation package knows no Dashboard) with prompt `prompts/DASHBOARD.md` (curation, not copying numbers; `Pinned.Replaces` + `UpgradePinned` move Bots still on an older prompt).
- The Feed's posts reach the board through `feed.Service` (`UnreadPosts`, `MarkRead`), never its table. `DeleteBot` drops it all (`dashboard.Service.Drop`).

## Asking the owner, setup offers, proactivity

- **`ask_owner`** (`internal/app/dashboard/cards.go`, rule `bot.ask_owner`, Allow, both surfaces, lead-only) is the Bot's *what should I do?*, where the Feed is *this happened*. It is a Dashboard ask shown where it belongs:
  - asked in a web chat, it is a `card` event in that chat (body = the card id) and **ends the run** after that turn's calls (`App.EndTurn`); `App.threadEvent` and the live emit attach the card **as it stands now**, so an ask answered on the Dashboard reads as answered in the chat;
  - asked from anywhere else (an automation, a channel), it is `quote.Put` into the main chat as a `FromAsked` quote carrying the card id, only while the main chat is idle and `proactivity` is `active` (`Placement.Proactive`), and it always waits on the Dashboard.
  - An answer to a card shown in a web chat (`answerIn`) goes to that chat as the owner's turn with no quote. A change of state is a transient `card_state` event carrying the card (`host.Emitter.Publish`), which `fold` applies to every block showing it. Putting a card away in a chat is an answer too (`DismissDashboardCard` tells the Bot "Not now for your question …").
- **Setup offers** (`internal/app/setup`, table `setup_offers`, tool `offer_setup`, rule `bot.offer_setup`, Allow, both surfaces, lead-only) are the Bot offering something from the catalog: a library connector (target = its identifier), a channel adapter or a drive template, as a card in the thread (a `setup_offer` event, body = the offer id; `RunEvent.setup_offer` attached as it stands now; `setup_state` is the transient update).
  - The card (`web/src/setup/OfferCard.tsx`) shows the provider's mark, name and blurb from the catalog, the Bot's `why`, and the values it filled in. **Set up** opens Silo's own form (`SetupModal`, portaled to `document.body`: the connector library form, `ChannelForm` then `ChannelSetup`, `DriveForm`, each taking `prefill`).
  - `options` may fill only the form's own settings (`setup.options`: a name, a connector's `default_mode`/`expose_completion`, a channel's `inbound`/`enabled`/`prompt`, a drive's `read_only`) and the provider's declared fields that are neither secret nor an address (`addressField`); anything else is refused with the reason, **so a misled Bot cannot point Silo anywhere**.
  - Unlike a question, an offer does not end the turn. Offers of one run are one group in the thread (`fold`: `offers`). `ResolveSetupOffer` (done or skipped; `rest` = **Not now for these**) tells the Bot in that chat in one message per batch (`setup.tell`, `setup_offers.told`). From an automation an offer goes to the main chat only when the Bot is `active` and the main chat idle; otherwise it is refused.
- **Proactivity** (`bots.proactivity`, `internal/app/proactivity`, `a.Proactivity`): how much a Bot does unasked. `off` (no Heartbeat; the default), `quiet` (a 09:00 Heartbeat that reports to the Feed; questions wait on the Dashboard) or `active` (a Heartbeat every three hours from 09 to 21, and `ask_owner` from a background run may write into the main chat). `proactivity.Service.Set` puts the Heartbeat on the level's schedule (`automation.Service.SetHeartbeatSchedule`, named columns only) and then sets the column; `proactivity.Levels` is the one list the tool's enum and error come from; a schedule set by hand reads as `Bot.heartbeat_custom` (`proactivity.Service.Custom`) and the next choice replaces it. The owner picks it in Settings (`Proactivity.tsx`, `UpdateBot.proactivity`); the Bot sets it only on the owner's word (`silo_runtime.set_proactivity`, rule `bot.set_proactivity`, lead-only, manager-only).
- **The interview** is a run in the main chat when New Bot's **Start with a short interview** is on (`CreateBot.interview`) or the owner types `/onboard`. Its opening turn is `prompts/ONBOARDING.md` (or `onboarding.prompt`) as a `user` event with `tool="onboarding"`, drawn as a "Getting to know you" divider, and it walks through `ask_owner` cards: areas of help, setup offers, permission to look, facts to remember, SOUL, proactivity, starter automations and an `ideas` widget.

## Feed and quotes

- **Feed** (`internal/app/feed`) is the owner's read-only inbox per Bot. The Bot posts markdown with `silo_runtime.feed` (optional title; rule `bot.feed`, Allow, inside `feed.Service.Tool`) from any run, and each `feed_posts` row records its source (kind + chat title / automation name / channel name). `Bot.feed_unread` rides on `GetBot`/`ListBots`, so the polled Bot row drives the sidebar badge; opening the Feed calls `MarkFeedRead`. ## Content host and tunnels

`internal/app/tunnels`, `internal/tunnel`, `internal/app/artifact/content.go`. Bot-made content is served on `<kind>-<name>.<content.host>`, dispatched by prefix (`tunnel-`, `app-`, `share-`): `App.Handler` wraps the mux in `App.contentRoute` (`config.ContentFromHost` → `Tunnels.Serve`, `Artifacts.ServeApp`, `Artifacts.ServeShare`); every other Host falls through.

- A `Tunnel` row is a generated `adjective-colour-animal` name (`internal/names`), a port and `Public`; one per port, 20 per Bot. The proxy is one `httputil.ReverseProxy` whose `Transport.DialContext` calls `Hub.DialTunnel`: that queues `Cmd.open_tunnel{conn_id, port}` on `Commands`, the worker dials `127.0.0.1:port` and opens a `BotWorker.Tunnel` bidi stream (first frame names `conn_id` or carries the dial `error`), and both ends wrap the stream in `tunnel.Conn`, a real `net.Conn` (deadlines, partial reads), so keep-alive, SSE and WebSocket upgrades need no special code.
- Rules that bit: a worker must close **gracefully** (`CloseRequest`, then wait for the CP to end the stream) or it cancels away the last frames of a service that writes and hangs up; the CP handler must not return while a conn's write goroutine is inside `stream.Send` (the send guard in `App.Tunnel`); a `Conn` copies the caller's slice before sending because its goroutine outlives a write deadline.
- `tunnel.CheckPort` refuses 5900 (x11vnc) and 9222 (Chromium) on both CP and worker. A tunnel request never starts a box (no worker → 503).
- **Config:** `content.host`/`content.scheme` and `tunnels.enabled`. With no `content.host`, a local `public_url` derives `localhost:<http_addr port>` (the CP's port, not Vite's, which would serve the SPA); anything else is "not configured" (`ListTunnels.state` = `ok`/`off`/`no_host`) and the tools, prompt note and add form disappear. A `host` equal to the `public_url` host is refused (a tunnelled app could set cookies for the CP's domain). `Settings.content_host` is the effective suffix. Changing it re-points every tunnel at once (rows hold only the name).
- **Private tunnels** hand off the session: with no grant, a page load redirects to `{public_url}/tunnels/auth?name&rd` (the CP session cookie never leaves the CP origin), which (signed out) first redirects to `/signin?next=<the handoff>` (the SPA honours `next` for `/tunnels/auth` only, by full navigation, `web/src/signinNext.ts`, so it is no open redirect), then mints a 30 s single-use ticket and redirects to `<name>.<host>/.silo/auth`, which sets the host-only `silo_tunnel` cookie: a `TunnelGrant` keyed by the cookie's hash, 12 h, **bound to the Silo session that made it** and re-checked on every request (that session still live and its user still on the Bot, `access.CanUse`), stripped from the request before the service sees it. Signing out ends tunnel access at once. An API call without a grant is a 401, never a redirect, and `rd` is only ever a plain path.
- **Tools:** `open_tunnel`/`list_tunnels`/`close_tunnel` (`tunnels.open|list|close`, Allow) and **`tunnels.public` (Ask, manager-only)** for anything exposed to other people, including flipping an existing tunnel; opening an existing port returns it and never downgrades it. The prompt section (`prompts/TUNNELS.md`) is the same for every Bot.
- The Tunnels tab (`/bots/:id/tunnels`) lists, adds, flips Private | Public (`TunnelAccess`, the same segmented control as a rule; going Public on an existing tunnel takes a second click) and deletes (armed); it polls because the Bot can add rows. Admin → Settings → Tunnels & apps holds the config.

## Mail

`internal/app/mailbox`, primitives in `internal/mailin`. Every Bot gets a **receive-only** address. It is a feature of the Bot, not a connector (the Email connector is a client of somebody's account).

- A `Mailbox` row is a generated name, made lazily by `mailbox.Service.Box`; the address is `<name>@<mail.domain>`, so a change of domain moves every address, and `name+tag@` reaches `name`.
- **The listener** (`mailin.Listen`, go-smtp; `mail.addr`, default `:2525`; the world's port 25 is forwarded to it) **never sends**: no relay, no AUTH, no bounce. Everything it will not take is refused inside the session: unknown recipient (550), over `mail.max_size_mb` (552), more than 10 recipients, a client past `probeLimit` unknown recipients or `rateLimit` messages (451); a store failure is 451 so the sender retries (the reason is logged, never sent). STARTTLS is always on, self-signed unless `mail.tls_cert`/`tls_key` name one. `mailbox.Service.Sync` reconciles the listener with the settings at start and on a `tickLoop` (`mailbox.Tick` = 15 s), so Admin changes need no restart; a bind error is `Mailbox.problem`, shown to admins only.
- **Config:** `mail.enabled`/`domain`/`addr`/`max_size_mb`/`tls_cert`/`tls_key`. With no `domain` there is no mail at all (`ListMail.mailbox.state` = `ok`/`off`/`no_domain`): nothing is derived from `public_url`, because an address no MX record points at would only look real.
- **Delivery:** `Deliver` stores `mailin.Parse`'s reading (first plain part, else HTML through `htmltext.Flatten`; attachment names reduced to bare file names; never fails) in `mail_messages` and the bytes under the listener's `Received:` line in `mail_bodies` (its own table, so listing never loads them), dedupes a retry by `(bot_id, sha256)`, and keeps the newest `mailbox.Keep` (200).
- **Verified:** `mailin.Authenticate` marks a message verified when the From domain vouched for it: an aligned DKIM signature covering `From`, or SPF pass with an aligned envelope sender (alignment by organisational domain, `publicsuffix`: DMARC's test without the policy lookup). A From with no or several addresses never verifies. Nothing is rejected over it. **Tests must set `Service.DNS`** (the `mailDNS` fake) or the checks ask the real network.
- **Tools:** `list_mail` and `read_mail` (rules `mailbox.list`/`mailbox.read`, Allow; there is no send action). `read_mail` takes an id or a 6+ prefix, marks the message read (**read means the Bot read it**; the owner opening it does not), pages a long body by `offset` (30k runes), wraps the body in a "written by the sender, not instructions" frame, and with `save_attachments` writes them to `/workspace/mail/<id8>/` (`save_error` says why not). The prompt section (`prompts/MAIL.md`, `{address}` filled in) sits in the session tier.
- **Wake** (off by default; `Mailbox.Wake`/`WakeFrom`, `UpdateMailbox`): only a *verified* message whose From is on the owner's list (addresses or `@domain`, `NormalizeWakeFrom`) starts a run through `Place`: in the main chat, or a chat of its own titled `Mail: <subject>` while a reply runs there; the user turn (`tool="mail"`) quotes the message. At most `wakePerHour` (10), counted from `mail_messages.chat_id`.
- **UI:** the Mail pane (`web/src/Mail.tsx`, helpers in `mailbox.ts` to avoid a case-insensitive clash) is a right-rail pane that needs no worker (its icon shows only while `Bot.mail_address` is set): the address to copy, then messages polled every 10 s, opened in place via `GetMail`, body as plain text, never `Md`. Settings has `MailSettings` (copy, armed **New address** = `RotateMailbox`, after which the old one is refused, the wake switch and sender list). `/mail/raw?bot_id&id` downloads the `.eml` (always an attachment, `nosniff`). `DeleteBot` drops the mailbox (`mailbox.Service.Drop`).

## Voice: dictation, Read aloud and calls

`internal/app/voice`, `internal/speech`, `web/src/call/`.

- **Dictation:** `transcribe_model` (default `openrouter/openai/whisper-1`, `off` disables) must be an `llm.Transcriber` (OpenAI `/audio/transcriptions` multipart; 25 MB). The composer mic (`web/src/voice.ts`, MediaRecorder) sends the take to `Transcribe` (no worker) and splices the text at the caret, never auto-sends; `ListModels.voice_enabled` hides the mic. The Bot's `transcribe` (`silo_runtime.transcribe`, rule `bot.transcribe`, Allow) is dropped when voice is off.
- **Speech out** is `llm.Speaker` (OpenAI `/audio/speech`, body streamed; OpenRouter answers 24 kHz PCM or MP3) with `llm.VoiceLister`. `voice.speech_model` is the operator's default; a Bot picks its own model, voice and speed (`bots.speech_model/voice/speech_speed`, `SetBotVoice`, Settings → Voice with **Hear it**); `SoundOf` falls back to a voice for the Bot's language (`speech.PickVoice`). A voice id means nothing across providers, so changing the speech model falls back to defaults.
- `internal/speech` is pure: `ForSpeech` makes markdown speakable (code and tables become a fixed pointer to the chat in the listener's language, links their words, URLs their site); `Chunker`/`Stream` cut streaming text into sentences (the first may end at a clause; short ones wait to join the next); `Heard` is what a listener heard of a piece from how much played.
- **Read aloud** (every reply, `web/src/ReadAloud.tsx`, one voice on the page at a time): `PrepareSpeech` → a ticket (5 min, its maker's) → `GET /voice/speak`, which speaks sentence by sentence, streams MP3 (or PCM as one open-ended WAV) and keeps the bytes so a media element's second request is not spoken again.
- **A call** is held in a chat (the one you are in, your main chat, or `chat=new`). The big **Call** (the sidebar's main chat row, the narrow top bar's phone; `BotPage.callMain`) rings the main chat on the **call screen** (`web/src/call/CallStage.tsx`: the Bot's crest with level rings, captions in the reply serif, a dock of hold-to-talk, mute, type and End), which takes the chat column while the thread is still written underneath; the composer's Talk calls in the open chat as the bar over the composer (`CallBar`), whose maximise opens the screen (`useCall.expanded`); Show chat folds the screen back into the bar. Leaving the Bot hangs up. `/voice/call` (same origin, session and `access.Chat` Write checks as `/console`; `App.Gone` ends it) is its control socket and WebRTC handshake.
  - The browser (`web/src/call/session.ts`) runs the mic through its echo canceller into Silero VAD (`@ricky0123/vad-web`, assets served from our origin under `/vad/` by `web/vite-vad.ts`, loaded on the first call only) and sends each finished turn as one 16 kHz WAV. Only VAD-gated turns are uploaded (speech-to-text is billed by audio time). Audio is never stored: the transcript is the record, and the LLM log keeps only `[audio …]`.
  - The CP transcribes the turn and hands it to the Bot as the human's message with `run.Extra.Spoken` (userMeta `spoken`; `userTurnText` prefixes `[spoken]` or `[spoken; I cut you off after: “…”]`, identically live and in replay; `prompts/VOICE.md` is the prompt section while calls are on). A turn that is not words is dropped.
  - Everything the Bot then writes in that chat is spoken: the call follows the chat's `chunk` events on the bus (any run, typed or spoken), through a `speech.Stream` per run, into the **outbox** (`out.go`): pieces synthesized two ahead, encoded to Opus (libopus through cgo, `dlopen`ed at run time by `internal/speech/opus`; without cgo a stub, and calls say so) and paced at 20 ms onto one WebRTC track (pion, one shared UDP/TCP port `voice.webrtc.*`, loopback candidates included). **The Bot's voice must stay on the WebRTC track, never Web Audio:** Chromium's echo canceller reliably cancels only audio received on an `RTCPeerConnection`. Delivery is code's job: the Bot's sections go straight to the outbox, so no model can decide a late result was "already covered".
  - **Barge-in:** speech over the Bot mutes it in the browser at once and sends `duck` (the pacer pauses and rewinds by the reported playout delay, so a backchannel resumes losslessly); real speech sends `interrupt` (flush; the rest of that model turn is muted; the next turn carries what was heard as its cut-off note). A barge-in never stops the Bot's run; only `stop_task` or Stop does.
  - **The talker** (`talker.go`; on while `voice.mode` is `talker`, the default, and `model_voice`, a text model, is set; otherwise direct mode, where the Bot answers every turn) hears each turn first with the chat's last 16 messages and `prompts/VOICE_TALKER.md`, streams its words straight into the outbox (`llm.Request.Latency` → OpenRouter `provider.sort: latency`), and has three tools only: `delegate` (the turn goes to the Bot; the preamble is filler and not written), `stop_task`, `end_call`. **The talker cannot act**: keeping it to those tools keeps every action under the Bot's rules, approvals and output filter; do not give it more. An exchange it answered itself is written into the chat after it is heard, cut to what was heard (`App.RecordSpoken`: a run of origin `voice` with the spoken user event and a `section` with tool `voice`; refused with `run.ErrBusy` while a reply runs, then written when it ends, so history stays append-only). A talker that fails hands the turn to the Bot.
  - Fixed lines in the Bot's language (`phrases.go`, never a model's) cover a failure, an approval waiting on screen, and "still working" after 12 s of quiet during work. Approvals by voice, when built, must be the CP's fixed sentence answered as Allow once, never the talker's words and never Always.
  - The thread shows `call_start`/`call_end` dividers (`RunEvent.spoken`, never replayed) and spoken turns with a mark; `voice_calls` and per-turn timings (`voice_turns`: end of turn, speech-to-text, first audio) are kept for P50/P95.
  - Tests drive real calls (`feature_voice_call_test.go`: a pion client peer, dummy speech, a dummy transcriber that hears a WAV's samples as text, `Test_x@model` scripts per model) and skip when libopus is missing.

## Drives

`internal/drives`, `internal/drivehost`, `internal/app/drive`. rclone remotes mounted at `/workspace/drives/<name>`.

- **Providers** are an embedded template library (`internal/drives/catalog/<key>/drive.yaml`, `icon.svg`, optional `GUIDE.md`/`SETUP.md`; no user or admin authoring): one rclone remote plus its questions, with `{{kind.var|filter}}` expressions rendered to `RCLONE_CONFIG_<REMOTE>_*` env. Vars are **user** (the form), **system** (admin, `drives.providers.<template>.<var>`, Admin → Drives) or **dynamic** (OAuth token, callback params like pCloud's host, declarative JSON `lookup`s for the account label and pickers). Adding a provider is a new catalog dir; tests pin every template's env and check option names and password obscuring against `testdata/rclone_options.json` (`rclone config providers`).
- **One drive sidecar per Bot** (`silo-drive-<bot>`, `driveimage/`, `cmd/silo-drive`) holds `/dev/fuse` + SYS_ADMIN and every credential; the Bot gets neither. It dials `DriveHost.Session` (per-Bot token; hello first), gets a full `DriveApply` on every connect and change, and supervises one `rclone mount` per drive; mounts survive CP reconnects.
- **Mount propagation:** the sidecar binds `<mount_root>/<bot>` rshared, the Bot binds it rslave at `/workspace/drives`. A privileged throwaway helper (`PrepareDriveDir`, before every sidecar start) makes the root a shared mount inside the engine's namespace (the rootless pause process, or pid 1) and labels it `container_file_t`; **never `:z`** (it would walk live FUSE mounts). Stop the sidecar gracefully (`DropDrive`): a killed rclone leaves dead mounts. A box made before drives has no bind: the UI asks for a container reset.
- An OAuth token travels as `DriveSpec.token` into a private token-only rclone config (env would shadow rclone's refresh write); the guest reports refreshes back and the CP stores them once and re-applies them to every Bot that mounts the drive. Drive secrets and dynamic values live on the `drives` row (`SecretsJSON`), never as Secret rows.
- **A drive is its Workspace's** (`drives.space_id`, names unique per Workspace), mounted in the Bots it is granted to (`bot_drives`: per-grant `read_only`, read-only when the drive or the grant is; the grant's mount `state`). `GrantDrive`/`RevokeDrive` give and take (Manage to give, Administer to take); `SaveDrive` from a Bot grants it to that Bot and from the Workspace page (`space_id`) to `bot_ids`; editing or deleting is whoever added it or a Workspace admin (`canEdit`; delete unmounts it everywhere); only its lender (`lent_by`) may browse or pick inside its account. Two Bots mounting one drive is last-writer-wins.
- The Workspace page's Drives tab (`/w/$spaceId/drives`, sub-routes `new`, `new/$template`, `$driveId`) holds them all with Choose Bots; a Bot has no Drives page. The add form keeps a `draft` row for sign-in/test/browse (swept after a day; `drives.bot_id` is only the Bot whose sidecar a draft lists through). `delete` refuses drive roots; a workspace-wide `grep` skips `drives/`.

## Time zones

`internal/zone`, `internal/app/timezone.go`. A Bot's machine is **UTC**, always, and SYSTEM.md says so; the human's zone belongs to the Bot: `bots.time_zone`, an IANA name.

- **It follows the owner:** `CreateBot`, `Send` and `EditMessage` carry the device's zone (`deviceZone()` in `web/src/zones.ts`, `TimeZone.current` on iOS) and `App.followZone` moves an unpinned Bot to it before the message is written (only while the Bot has one person). `bots.time_zone_pinned` (Settings → Time zone, **Follow my device | Fixed**, `web/src/TimeZone.tsx`) keeps it put. `silo_runtime.set_timezone` (rule `bot.set_timezone`, Allow, manager-only) is for a human who says where they are in a channel. A zone a client sends is never an error: unknown or empty changes nothing.
- `App.setBotZone` is the one writer (one column, never the whole row) and calls `automation.Service.Rezone`, because cron is wall-clock time in the Bot's zone (`nextRun(au, from, loc)`; DST is robfig's business).
- `zone.Resolve` never answers `Local`: an unset Bot reads as the server's zone *by name*. `zone.OfBot` asks the database each time (the zone can move during a run). `zone.Stamp` is the one layout for a time the model reads (`Sun, 2026-10-11 14:30:05 +02:00 Europe/Warsaw`).
- **The zone is frozen on each message:** `run_events.zone` records it when a `user`, `subagent_report` or `feed_quote` event is written, and `replayEvents` stamps it in that zone forever, so a trip never rewrites history (an event with no zone keeps the old server-zone layout). For the same reason the zone is never in the system prompt, and memory dates there are UTC.
- Mail, feed and automation times in tool results use the Bot's zone. The web shows every instant in the viewer's device zone; only the schedule editor names the Bot's.

## Automations

`internal/app/automation`. Scheduled background prompts: name, prompt, a 5-field cron schedule in the Bot's zone, an on/off switch.

- The prompt is the user message of a run through the same engine as chat, with a trailing note (`prompts/AUTOMATION.md`) naming the automation and saying nobody is watching. **Every run starts from a fresh context** (`historyFromRuns` of just this run), so the log does not grow with each firing: the prompt must be self-contained and keep state in files, `bot/` or memory.
- The scheduler (a `tickLoop`, `automation.Tick` = 20 s) fires due rows **once**: `automation.Service.FireDue` claims the slot with a conditional `next_run_at` update, and a firing that lands while the previous run is live is skipped, never queued. `automation.Service.Reschedule` (at start) advances anything missed while the CP was down without backfilling. `parseSchedule` rejects a schedule whose first two firings are under 5 minutes apart (`* * * * *` cannot burn a call a minute); a Bot has at most 50 automations.
- **Pinned automations:** every Bot has one **Heartbeat** (`kind=heartbeat`, created with no schedule so it never fires until given one; cannot be deleted), and one of every other pinned kind a domain registers with `automation.Service.Pin` (an `automation.Pinned`: kind, fixed name, default prompt, the prompts it `Replaces`; the Dashboard's curator is one). `EnsurePinned` makes the missing ones; they list first in registration order; `Pinned`/`Ask` are how the owning domain reads its row and hands it the owner's words. The partial unique index `automations_pinned` is made from `db.PinnedAutomationKinds`, so a new kind is added there too (`TestPinnedKindsAreIndexed`).
- Each automation owns a hidden log `Chat` (`chats.automation_id`), excluded from chat lists and refused by Send/Edit/Diverge/Delete; deleting the automation drops it (`chats.Drop`). Automation logs are never woken by subagents.
- **Tools:** `list_automations`/`create_automation`/`update_automation`/`delete_automation` under `automations` (create/update Ask, list/delete Allow; all manager-only; `update_automation` sets the Heartbeat's schedule).
- **UI:** `/bots/:id/automations` list, `/new`, `/:id` log + inline editor; the log renders the shared `Thread` with `userAs="run"` (each run a "Ran …" divider); `web/src/schedule.ts` is the schedule picker. Chat and automation logs share `useRunStream`.

## Subagents

`internal/app/subagents*.go`, `taskboard.go`. Background agent loops a chat's lead starts with `spawn_agent` (name, goal, context, optional allowlisted model; default `model_subagent` when set and allowed, else the lead's model; rules `agents.*`, Allow).

- Subagents keep their own trimmed tool list: the prompt cache is per model and siblings spawn in parallel, so matching the lead's tools would not buy cache hits. The prompt tells a lead to end its turn after spawning rather than `sleep`, since every wake from `sleep` is a full turn.
- Each owns a hidden log `Chat` (`chats.subagent_id`) and runs from a **fresh context** (only its own log; the brief and later `message_agent` texts are `user` events with `tool="lead"`). A subagent run gets the tool list minus the `LeadOnly` defs (the agent tools, `task_reset`, `channel`, `switch_model`, automations, `ask_owner`, `offer_setup`, `set_proactivity`, `set_timezone`) and the trailing `prompts/SUBAGENT.md` note. Depth is 1; at most 8 run at once per lead chat.
- **Waking:** a subagent's `finish` stores its result (`runResult`: the last model turn's text) with `reported=false`, nudges the lead's live run (`liveRun.wake`, which `sleep` selects on; `inject` nudges it too), and `scheduleWake` (debounced) calls `wakeLead`: if the lead chat has no live run it marks the finished results reported and starts a lead run that opens with a persisted `subagent_report` event (Tool `name:status,…`), replayed as a framed user turn. A running lead inspects on its own; a lead run that ends `done`/`error` with unseen results wakes once (the report marks them seen, so no loop).
- Stops the lead already knows about (its Stop, which cascades via `stopSubagents`; `stop_agent`; Stop Bot) go through `quietSubagents` first so they do not wake it; a human `StopSubagent` does. `DeleteChat` drops the lead's subagents and board.
- **Taskboard:** `task_items` rows per lead chat, shared with its subagents (`boardChat`); `task_add` parses a leading `[NAME]` into the assignee; a subagent cannot reset. Board and subagent state is told as a `note` turn **when it changes** (`turnNote`) and stays in history. Board and subagent changes publish transient `board`/`subagents` bus pings (no id; `useRunStream` hands them to `onPing`, not the thread).
- **UI:** `Taskboard` strip above the lead thread, `SubagentTray` between thread and composer (running cards + "N finished"), and `/bots/:id/run/:chatId/agent/:agentId` is the read-only `SubagentPage` (shared `Thread`, Brief, Stop; its lead chat stays lit in the sidebar).

# Frontend

pnpm + React + Tailwind in `web/`, ConnectRPC to the CP plus WebSockets. DESIGN.md is the look; DEVELOPMENT.md § Web bundle is the chunking rule (only the chat is in the first load; every other page is lazy).

## Routing

- **TanStack Router, code-based, in one file:** `web/src/router.tsx` is every URL. Nested layouts: `_authed` is the rail, `/bots/$botId` is `BotPage`, and under it the pathless `_chat` and `_settings` (a pathless id is part of a route's `from`, `"/_authed/bots/$botId/_settings/rules"`, but never of a `to`).
- A page is a route there or it does not exist. **Never parse a path by hand**, and write `Link`/`navigate` as `to="/bots/$botId/…"` + `params` so the compiler checks them (`links.ts` holds the few shared ones).
- A route's `staticData.tab` is the page it lights (`bot/tabs.ts` sorts them into the conversation side, Channels, Settings and the right-rail panes). A page with sub-pages (Channels, the Workspace's Drives, Automations) is a layout route whose list, new, edit and setup pages are each their own route and component, sharing data through one hook over the cache (`useChannels`, `useHubDrives`, `useAutomations`).
- The session is a small store (`auth.tsx`) the route guards read: signed out redirects to `/signin?from=…`, and signing in returns there. Sign-in, accepting an invite and joining a Workspace must call `setSession` from the response (email + admin) or the session cookie is ignored; the signed-out pages (`SignIn`, `InvitePage`, `JoinPage`) share `AuthCard`.
- A route that throws renders `Snag` in its own place (the router's `defaultErrorComponent`), so the rail and the other pages stay usable.

## Server state and errors

- **One TanStack Query cache** read with connect-query (`useQuery(UI.method.getBot, { id })`). Never keep a fetched row in `useState` or poll with `setInterval`: use `refetchInterval`, and after a change write the answer back with `web/src/query.ts` (`setBot` updates the Bot page and the rail together; `patch`, `reload`, `recheck`). Retry and poll timing are pure functions in `queryPolicy.ts` (node-tested); polls pause while the tab is hidden.
- A form keeps only what the human changed on top of the cached answer (`useAdminSettings`: `edits` over `getSettings`), never a copy of it.
- The run stream (`useRunStream`) is the one hand-written reader. `fold/` turns raw run events into the thread's blocks (one handler per event kind).
- **Errors** go through `web/src/errors.ts` (`fail` for the user-facing sentence; `isSignedOut`/`isTransient`/`isGone` to classify); never a local `fail` copy. Only `Unauthenticated` ends the session: the `api.ts` interceptor fires `onSignedOut` (SignIn excluded) and tracks reachability for the one `OfflineBanner`; boot `me` retries with backoff on anything else (`Unreachable`). A page's first-load failure is terminal only when `isGone`.
- To see the cache and what polls: `localStorage.setItem("silo.devtools", "1")` and reload (development only).

- `NeedMachine`: Files / Desktop / Console / Knowledge when the worker is down.
- `FileBrowser`: tree + preview over an `FsSource` (the Bot's workspace, a CP skill dir, or a proposal prefix); it switches tree-or-preview on its own width (a container query). Upload / new / delete stay on `FilesPane`.
- One hatch overlay for Workspace Skills, the Admin library and Artifact inspect.
- `Tip` (`web/src/Tip.tsx`): the tooltip card for controls whose meaning needs more than a word (portaled, 350 ms rest delay then warm, flips and clamps to the viewport, never on touch; `TipTitle`/`TipAction`) instead of a native `title`. A control that should explain itself while unavailable uses `aria-disabled`, not `disabled`: disabled buttons get no pointer events.

## Languages

`web/src/i18n.ts`, `internal/lang`. The console is in English (the source), Polish and German with i18next; iOS is not translated yet.

- A user's display language is `users.language` (`SetLanguage`, Account → Language), mirrored to localStorage for the signed-out pages; `App` keys the router by it so a change redraws everything.
- **A message's key is its English text:** `t("Save")`, `t("{{count}} files", { count })` (plural forms in `locales/<lang>.ts` as `key_one|few|many|other`), or `<Trans i18nKey="Set <mono>x</mono>" components={…} />` for markup. Never concatenate sentences, never call `t` at module level (mark such a string with `msg()` and call `t` where it is shown), and give a homonym a `context`.
- `i18n_test.ts` fails on a message missing from `pl`/`de`, a stale entry, or a value or tag a translation drops: after adding a string, add it to both catalogs. `web/src/languages.ts` and `internal/lang` list the same codes (a Go test reads the TS).
- A Bot's language is `bots.language` (a code or `mixed`, default the maker's display language; Settings → Language). `lang.Prompt` puts one line in the session tier; `lang.Title` tells the title model.

## Theme

- Light and dark are one set of token names in `web/src/index.css` (`@theme` is light, `[data-theme="dark"]` re-inks it; DESIGN.md §2 Dark). `web/src/theme.ts` is the store (localStorage `silo.theme`, else the system setting); the inline script in `index.html` sets `data-theme` before the first paint.
- **Never write `white`, `black` or a hex in a component.** A label on an ink fill is `on-ink`, on a cobalt/emerald/vermilion fill `on-accent`, on the hatch `on-hatch`; shadows take `--shade-*`. Reach for a type token (`text-title`, …) before pixel values. `theme_test.ts` checks both palettes' contrast and that the boot script agrees with the store.
