# Silo Agent

Token-conserving multi-user agent. Each **Bot** is a durable container with a GUI. Architecture: `docs/Description.md`. UI: `DESIGN.md`.

How to build and run: [DEVELOPMENT.md](DEVELOPMENT.md). The DB is Postgres 17 + pgvector (`database_url`, default the dev compose on `localhost:5433`); `docker-compose.dev.yml` runs only Postgres, never the CP. `Makefile` is the command surface — `make help` lists every target. Never start the dev servers yourself; see Dev below.

Operator config: [docs/CONFIGURATION.md](docs/CONFIGURATION.md). Koanf **defaults → `silo.yaml` → `SILO_*` env**. Nested keys use `__` (`SILO_PROVIDERS__OPENROUTER__API_KEY` → `providers.openrouter.api_key`). Admin Settings edits `silo.yaml` (form + YAML editor). Env still wins; the UI warns and disables those fields. Providers carry `api_key`/`base_url`/`cache`/`cache_ttl` (prompt caching is on by default: `setDefaults` sets `providers.<id>.cache`); `local` is any self-hosted OpenAI-compatible server (required `base_url`, optional key; Silo never hosts models); `models` is the allowlist of text models, `model` the default (`provider/model`), `model_title` the title model; `decision_models` is the separate allowlist of decision models and `model_decision` their default (see **Decision models** below). `providers.openrouter.ignore` (default `DeepInfra`) is sent as OpenRouter `provider.ignore`: some upstreams buffer tool-call arguments into one final chunk, which kills the live `tool_args_chunk` stream of exec_python/terminal/write input. Default model when unset: `openrouter/openai/gpt-5.6-luna`. Default search engine when unset: `builtin` (the Built-in Scraper; an old `duckduckgo_scraper` reads as it).

The project should follow test-driven-development. For now end to end testing is not yet to be fully implemented, but the unit tests in Go should test as much as possible using the dummies.

## Shape

- **Package layout:** `internal/app` is the runtime (agent loop and run engine, Bot lifecycle, worker RPCs, the tool gateway with its rules and approvals, subagents) and wires the domains in `app.New`; each domain is a `Service` in `internal/app/<domain>` that owns its RPCs and Bot tools: `access` (who is asking and what they may do: user and session on the context, `Bot`/`Row`/`Chat`/`Space` checks, `RPCs`, `RowByToken`, `PublicURL`, `SafeReturn`; see **Workspaces and access** below), `space` (Workspaces: the rows of `spaces`, `space_members`, `bot_access` and the Workspace RPCs), `approval` (the auto-approval gate: what an Auto rule's model is shown and how either kind of model's answer becomes allow/ask/deny), `account` (who may sign in: passwords, sessions, two-factor, OIDC, invite links, the admin's users), `models` (provider clients, model choice, embeddings, thinking, the LLM log), `workspace` (the Bot's files through the worker), `connector`, `drive`, `channel`, `skill`, `artifact`, `knowledge`, `changes`, `memory`, `automation`, `feed`, `tunnels`, `mailbox`, `voice`, `admin`, plus `chats`, `toolarg`, `host` and `run`. A domain never imports package `app`: it takes concrete services it depends on (`models`, `workspace`) and declares the few things it needs from the App in a small `Host` interface (`host.Authorizer`, `host.Runs`, `host.Emitter`; `run.Engine` for starting and steering runs) that `*App` implements. `handler.go` embeds every service into the one `uiHandler`, so their RPCs are promoted instead of re-declared; services are exported fields of `App` (`a.Knowledge`, `a.Models`, …) so tests and tick loops call them directly. A new domain follows the same shape; do not add methods to `App` for something a domain can own.
- **Control Plane (Go):** users, bots, secrets, skills (bodies on `data/skills/`; enablement in Postgres; `ListSkillFiles`/`ReadSkillFile` walk the CP volume, no worker), **security engine** (`internal/security` — catalog of connector.action → title/fields/default; `*` for files/desktop; each secret is `secrets.<name>` not `secrets.get`; unknown MCP actions get a generic prompt), **rules layers** (`internal/app/operator.go` over `internal/app/rules.go`: the installation's `operator_rules` sit over each Bot's rows — a **locked** row is a floor the owner may tighten but never loosen (`SetRule` refuses, `security.Stricter`/`Looser` in `internal/security/layers.go` take the stricter mode, an unknown value ranks as ask/check), an **unlocked** one is only a default the owner overrides; `ListRules` carries the operator's value + lock so the Rules page shows the lock and stops offering a looser mode, and the operator's policy text `rules.approval_policy`/`rules.output_policy` is joined before the Bot's own by the auto-approval gate and the output filter — admin-only RPCs behind Admin → Settings → Rules), **HTTP MCP client** (`internal/mcpx` — streamable HTTP over a URL or an injected transport), **STDIO MCP sidecars** (one isolated container per attached STDIO connector; `silo-mcp-bridge` **dials the CP** over ConnectRPC `MCPHost.Tunnel` with a per-attachment bridge token and raw-pumps JSON-RPC to its child; curated image or generic Node/`npx` command; structured argv, never a shell; no published port), **agent loop** (the modular `internal/llm` engine: providers `openrouter`/`openai` speak the OpenAI-compatible API, `anthropic` the native Messages API; model ids are `provider/model`; operator allowlist `models`, default `model`, chat override `chats.model`; the system prompt is a base `SYSTEM.md` plus ordered session providers in `internal/app/systemprompt.go`; blocks are ordered stable→volatile with provider cache breakpoints — see **Context is append-only** below; bots get `list_models`/`switch_model` under the `model` rule), **web search** (`internal/search` — engine registry on the CP, Python only: `silo_runtime.web_search` / `web_search_many` under `web.search`; see **Web search** below), Docker lifecycle = create/start/stop/inspect only (bots and STDIO sidecars). Chat tools and Python `CallTool`/`GetSecret` share `AuthorizeAction`. Approval slip never dumps `args_json` (and redacts `desktop.type` text). `allow_once` is a valid vote. Connector tokens and extra headers stay on the CP. Reserved connector slugs: python, terminal, files, desktop, bot, secrets, skills, web, artifact, channels, chats, model, automations, agents, tasks, tunnels, mailbox. **Channels** are built-in adapters (`internal/channels`, Telegram via gotd MTProto) that talk to a Bot. One adapter instance is a `Channel` row (per bot, unique name); channel conversations are `Chat` rows tagged `channel_id`+`external_id` (web chats keep `channel_id=''`). Adapters own config (per-channel secrets live as `channel.<id>.<key>` Secret rows, hidden from the Secrets tab and `secrets.*`), dynamic state (`State`: info/QR/select for QR logins and chat pickers), and lifecycle. The Channels tab adds/edits them from adapter-declared fields, with sub-routes `/bots/:id/channels[/new[/:adapter]|/:channelID[/setup]]` so browser back works; `requires_target` adapters (Telegram) bind the row to exactly one chat picked in the Setup menu (`set_target` → `external_id`/`target_title`), and only that chat is read or written. Telegram bot accounts cannot enumerate dialogs (`messages.getDialogs` → `BOT_METHOD_INVALID`), so the picker lists chats the bot has seen (persisted in channel state) and accepts a manually entered `@username`/`t.me` link/id. Adapters declare interactive `Setup` actions (`pick`/`run`/`qr`) and an embedded `GUIDE.md`; a channel that still needs its target shows a blinking **Set up**. The `chats` tool asks the adapter for a channel conversation's history (Telegram `messages.getHistory`) so the Bot can see older messages; bot accounts are refused (`BOT_METHOD_INVALID`), so it falls back to the local run log (adapter flags `noHistory` per channel and stops retrying). `present`/`artifact` on a channel attach the real bytes (`workspace.Service.Attachment`; a skill directory is zipped by `artifact.Service.ZipAttachment`), and the Telegram adapter uploads them with `uploader.FromBytes` + `.File`. A channel with `inbound=false` is send-only (tools only). Channel workers start from `channel.Service.Reconcile`; adapter `Start` is live-only — never backfill missed messages. The `channel` chat tool sends (default the origin channel; rule key `channels.<channelID>`); `chats` reads history through the adapter for channel conversations and the DB for web chats (rule `chats.read`); `silo_runtime.send_channel`/`read_chats`/`feed` are the Python paths. **Tools are one engine** (`internal/app/tool`): every tool is a `tool.Def` — name, description, JSON-schema params, its `connector.action` (the rule that gates it and its address from Python), the handler, and where it is offered: `ExposeCompletion` (the model's tool list) and `ExposePython` (`silo_runtime.call(connector, action)`). **Exposure is Python-first** (pinned by `TestBuiltinToolExposure`): a built-in is a completion tool only when it is the loop itself (files, shell, Python, the desktop, `remember`/`recall`), chat-only by nature, or asks the human by default (`create_automation`, `update_automation`, `open_tunnel`: an approval can outlast the worker's 5-minute command timeout, which a Python call sits under); `decide` is on both by choice, since one judgment mid-turn should not cost a Python cell. The rest (`web_search`, `feed`, the taskboard, `chats`, `channel`, mail, `search_docs`, `transcribe`, `forget`, `list_*`, `delete_automation`, `close_tunnel`) is `silo_runtime` only, documented for the model in SYSTEM.md and the feature prompt sections; `tools.expose_completion` (a silo.yaml list, `all` for everything; `tool.Engine.Expose`) offers named ones to the model again, and tests that script one as a chat call use `apptest.WithChatTools()`. SYSTEM.md nudges where the engine does not act: several independent steps go in one Python cell (threads for network calls) — the loop does not run tool calls in parallel — and a cell prints only what the next step needs. The built-ins are one list, `App.toolDefs` in `internal/app/tools_defs.go`; adding a tool is adding one `Def` there (plus a `silo_runtime` helper named `Name`/`PyName` when it has `ExposePython` — `TestPythonToolsHaveHelpers` fails without it, and `TestBuiltinToolExposure` pins who is exposed where). There are two thin adapters and no other dispatch: the chat loop's `execTool` (completion surface) and the worker RPC `CallTool` (Python surface: emits the `call`/`call_result` rows and always answers JSON, wrapping prose as `{"result": text}`); both call `Engine.Run`, which refuses a surface the tool is not exposed on, runs the def's `Check`, authorizes `Connector.Action` through `AuthorizeAction` (unless `SelfGated`: the handler gates itself because its rule depends on the arguments — one rule per channel, `tunnels.public`, a slip that names the automation), then runs the handler. Other `Def` flags: `Local` (from Python the worker performs it and the engine only grants: the desktop, so typed text never reaches the CP), `LeadOnly` (left out of a subagent's list), `Writes` (takes the run's change snapshot and clears the repeat guard), `RepeatGuard` (`read`/`grep`), `Enabled` (offered only while a feature is on: voice, tunnels, mail, an indexed folder, an allowed decision model), `Mode` (fallback decision), `Title` (the call row). Handlers get a `tool.Call` and use `c.Structured()` to give Python JSON where the model gets prose (`recall` → `{memories: [...]}`). Completion-only by default: the worker-command tools (`terminal`, `exec_python`, the five file tools, `present`), `soul`, `skill`, `switch_model`, the agent tools and `sleep`; everything else is on both. **Connector tools are the same definitions**, supplied per Bot by `connector.Service` as a `tool.Source` (`Tools`/`Find` in `internal/app/connector/tools.go`; `connector.Service.Call` runs MCP or built-in): always `ExposePython` (`tools.<slug>`), and `ExposeCompletion` when the connector's **Expose completions directly** switch is on (`connectors.expose_completion`; HTTP, STDIO and built-in alike; a library preset's value is what a new copy starts with; `optional` on the update/add requests so an unrelated save keeps it). An exposed connector's tools join the model's list after the built-ins (so the stable list stays a cache prefix), sorted by slug then action, named `<slug>__<action>` (`tool.CompletionName`: `[A-Za-z0-9_-]`, 64 max, a hash suffix when cut), described as `<Name> connector. <server text>`, and gated by the same `slug.action` rule as the Python path; the Connectors prompt section says which connectors are also chat tools, and the thread shows such a call as connector · action with the connector's mark. `artifact` is one engine (`internal/app/artifact`, worker `artifacts.go`): the chat tool and Python `silo_runtime.artifact`/`CallTool` share `artifact.Service.Tool`, which pins each emitted file or tree into the worker's content-addressed store (`/var/lib/silo/artifacts`, bound from `data/bots/<id>/artifacts`, mode 700, crash-safe tmp+fsync+rename, verified by SHA-256 on every CP read), records `Artifact` + `ArtifactVersion` rows in Postgres (keyed by `(bot_id, chat_id, path)` so repeated emits become v2, v3, … on the same card with an inline update row), captures an emit-time card preview (text excerpt, CSV rows, or JPEG thumbnail via ImageMagick/`pdftoppm`), serves downloads at `/artifacts/file`, `/artifacts/skill.zip` and `/artifacts/tree.zip` (cookie auth), serves live HTML apps (`app-<name>.<content.host>`, gated by `artifact.app_network` Ask when `network: true`), and serves owner-created public shares (`share-<name>.<content.host>`, copied to `data/shares/<id>` on the CP so they work while the Bot is stopped); deleting a chat forgets unreferenced versions and a background sweep enforces `artifacts.max_mb` (default 2048 MB per Bot).
- **Worker (Go, inside Bot):** dials the CP. Local Unix-socket HTTP for Python tools (`get_secret`, `call`, desktop). `desktop.*` CallTool is a grant; the Worker runs look/click/type/key/scroll and strips type text before the RPC. Writes `/opt/silo/tools` from `SyncTools` and `/opt/silo/skills` from `SyncSkills` (empty those dirs; do not rmdir them — `/opt/silo` is root). `start.sh` mkdir+chowns both. Tunnels VNC and a console PTY. Desktop is Openbox + Thunar + mousepad + iron wallpaper (`botimage/`). Dock: Files, Terminal, Editor, Chromium. `start.sh` is root only to chown mounts and supervise; the worker, X stack, console PTY, and dock apps run as user `silo` (uid 1000) with passwordless sudo. `start.sh` starts the worker before the X stack so the bot is online without waiting for x11vnc. ConnectRPC bidi does not send headers until the first `Send` — `Commands` must heartbeat immediately or the CP treats the worker as offline until the 10s ticker. x11vnc uses `-speeds lan` (localhost tunnel; skip the link-speed probe). Double-click text in Thunar opens the editor.
- **Python in the Bot:** `exec_python` + `silo_runtime` + generated `tools.*`. Not the orchestrator. `exec_python` runs in a **persistent interpreter per conversation** (worker `kernel.go` + the embedded `kernel.py` driver): the CP sends `ExecPythonCmd.session` (the chat id; an automation firing uses its run id; empty = a throwaway `python3 -c`, as an old worker always does), the worker keeps at most 4 interpreters, closes one after 30 idle minutes, and a cell that starts in a new one opens its output with `[fresh Python session]` (SYSTEM.md tells the model what that means). One merged stdout/stderr pipe, a NUL-led end marker with a per-cell nonce, `SILO_RUN_ID` set per cell, stdin emptied; Stop sends SIGINT and kills the interpreter only if the cell ignores it for 3 s; only the interpreter is ever signalled, never its process group, so a server a cell started keeps running. The box also has Node.js LTS with `npm`/`npx`/`pnpm` (copied from `node:24-bookworm-slim` in its own `botimage/Containerfile` layer; `SYSTEM.md` tells the model so). `toolsgen` escapes `\` and `"` in generated docstrings — a description ending in `"` must not become `""""` and SyntaxError the whole package import. `tools/__init__.py` is `toolsgen.RootInit` (lazy PEP 562 `__getattr__`), so `import tools; tools.<slug>.fn()` works without importing the subpackage; docstrings name the snake_case kwarg the stub takes, not the MCP camelCase. A nonzero exit from `exec_python`/terminal returns the captured output (the traceback) as the result; never just `exit status 1`. Desktop GUI is first-class `look` / `click` / `type` / `key` / `scroll` (1600×900 X11; worker uses `scrot`/`xdotool`) — that is how the model clicks the machine. The same actions are on `silo_runtime` (`type_text`, not `type`) so a secret can be typed without a chat `type` call. `silo_runtime.web_search` is the Python path for CP web search (same `web.search` gate as the chat tool). Playwright `silo_runtime.chrome_page()` is page screenshots, mutating displayed HTML, and automated scripts — not the live click loop. The worker opens `silo-chromium` when `exec_python` mentions Playwright / `chrome_page` (and `chrome_page` calls `desktop.chrome` again: a `Local` grant the worker acts on by opening the browser). Do not ship `chrome_eval` / raw CDP helpers or `pyautogui`. SYSTEM.md must forbid the model `xdotool`, `pyautogui`, `playwright install`, and `apt` for a GUI driver. Computer-use shots attach without `detail: high` (OpenAI-family tiling breaks xy). **Pause** (`internal/app/pause`, table `desktop_pauses`: its own table because the bots row is saved whole in places; `Bot.desktop_paused`, `SetDesktopPaused`) is the owner taking the desktop over with the switch in the Desktop pane's header: while a row exists, `click`/`type`/`key`/`scroll`, `desktop.chrome` and an `exec_python` cell that `WantsChromium` are refused on both surfaces with `pause.ErrPaused` ("your owner … is in control"); `look` still works. It is a `tool.Def.Gate`, which `Engine.Run` checks before the Python `Local` grant and before any approval, so a paused desktop never raises a slip. Not covered: a Playwright page a cell kept in a variable from before the pause, driven in a later cell that does not mention Playwright/`chrome_page`.
- **Frontend:** pnpm + React + Tailwind. ConnectRPC + VNC websocket. **Routing** is TanStack Router, code-based, in one file: `web/src/router.tsx` is every URL (nested layouts: `_authed` is the rail, `/bots/$botId` is `BotPage`, and under it the pathless `_chat`, `_customize` and `_settings` — a pathless id is part of a route's `from` (`"/_authed/bots/$botId/_customize/drives/$driveId"`) but never of a `to`). A page is a route there or it does not exist — never parse a path by hand, and write `Link`/`navigate` as `to="/bots/$botId/…"` + `params` so the compiler checks them (`links.ts` holds the few shared ones). A route's `staticData.tab` is the page it lights (`bot/tabs.ts` sorts them into the chat side, Customize, Settings and the right-rail panes); a page with sub-pages (Channels, Drives, Automations) is a layout route whose list, new, edit and setup pages are each their own route and component, sharing data through one hook over the cache (`useChannels`, `useDrives`, `useAutomations`). `BotPage` owns what must survive a page change and hands it to the thin adapters in `bot/routes.tsx` through `useBotPage()`. A Bot page has no top bar: `BotSidebar` (name, status, New chat, the conversation-side pages, Customize, chats, Settings) on the left of every page, the `<Outlet>`, then `SidePane` and `MachineRail` on the right. Files, Desktop, Console, Changes and Mail are one `SidePane` that `BotPage` renders itself — docked beside a chat-side page (`bot/paneStore.ts`: which pane and its share of the row, localStorage) or, on `/files|/desktop|/console|/changes|/mail`, as the page with the sidebar hidden — and each stays mounted (hidden) once opened, because an `<Outlet>` or a remount would drop the desktop and console sockets. Mail is the one pane that needs no worker (its rail icon shows only while `Bot.mail_address` is set). Customize and Settings never take a docked pane (their pages lay out against the window width); a rail press there returns to the chat with it docked. Below 960 nothing docks and `BotStrip` carries every page. `FileBrowser` switches tree-or-preview on its own width (a container query), not the window's. The session is a small store (`auth.tsx`) that the route guards read: signed out redirects to `/signin?from=…`, and signing in returns there. **Server state** is one TanStack Query cache read with connect-query (`useQuery(UI.method.getBot, { id })`): never keep a fetched row in `useState` or poll with `setInterval` — use `refetchInterval`, and after a change write the answer back with `web/src/query.ts` (`setBot` updates the Bot page and the rail together; `patch`, `reload`, `recheck`). Retry and poll timing are pure functions in `queryPolicy.ts` (node-tested); polls pause while the tab is hidden. A form keeps only what the human changed on top of the cached answer (`useAdminSettings`: `edits` over `getSettings`), never a copy of it. The run stream (`useRunStream`) is the one hand-written reader. Errors go through `web/src/errors.ts` (`fail` for the user-facing sentence, `isSignedOut`/`isTransient`/`isGone` to classify) — never a local `fail` copy. Only `Unauthenticated` ends the session: the `api.ts` interceptor fires `onSignedOut` (SignIn excluded) and tracks reachability for the one `OfflineBanner`; boot `me` retries with backoff on anything else (`Unreachable`), and the backend returns `Unavailable`, not `Unauthenticated`, when the session store fails (`sessionError`). A page's first-load failure is terminal only when `isGone`. A route that throws renders `Snag` in its own place (the router's `defaultErrorComponent`), so the rail and the other pages stay usable. Right-side “Needs you” panels (permission vote and MCP OAuth) share `NeedYouSlip` — do not hand-roll a second folio drawer. Files / Desktop / Console when the worker is down share `NeedMachine` — do not hand-roll a second offline well. Files tree + preview is `FileBrowser` (`FsSource`: bot workspace, CP skill dir, or a workspace proposal prefix). Skill Hub / Admin library / Bot Skills / Artifact inspect share one hatch overlay. `artifact` is Allow and emits a thread `artifact` card (skill or file); a skill does not install until **Save skill** on the card (`SaveSkill`) copies the pinned version into the Bot's Workspace (Use on the Bot and Build in the Workspace; recorded in `space_skills` as installed by the presser). Files show a type icon, subtitle, download, and a preview hatch. `Seeded` is embed library names only (`catalog.SeededName`); a Workspace skill never gets the catalog chip.

**Workspaces and access** (`internal/app/access`, `internal/app/space`; the plan is `docs/workspaces-handoff.md`). A **Workspace** (code `space`, UI "Workspace") holds Bots and the people who use them; every Bot is in one (`bots.space_id`) and `bots.created_by` is only who made it. Who may do what is two role tables: `space_members.role` (`owner|admin|member|guest`, one owner per Workspace by the `space_owner` index) and `bot_access.role` (`manage|use`; whoever makes a Bot manages it). Every check goes through `access`: `access.Bot(ctx, db, id, access.Use|Manage|Administer)` (Use = anyone on the Bot; Manage = its managers, for anything that widens what it may do; Administer = a manager or a Workspace admin who is not on it, for delete/revoke only — an admin never opens someone else's Bot), `access.Row[T]` for one row of a Bot, `access.Chat(ctx, db, botID, chatID, Read|Write)`, and `access.Space(ctx, db, id, View|Build|Admin|Own)`. A caller who may not see a thing gets NotFound with the access layer's own message (`access.NoBot`/`NoChat`/`NoSpace`), one who may see it but not do this gets PermissionDenied with a sentence. The plain HTTP routes (`/vnc`, `/console`, private tunnels, app views) re-check `access.CanUse` on every request. A Bot with no enabled manager is **suspended** (`access.Suspended`/`SuspendedBots`): no runs, channels or tunnels. **`access.RPCs` declares who may call every UI RPC**: a new RPC is a line there, and `TestEveryRPCChecksAccess` fails on a missing one and calls every Bot-, chat- and Workspace-scoped RPC as a stranger (who must get the access layer's NotFound, never a NotFound of the handler's making) and as the owner (who must never be refused). `ListSpaces` makes a user's first Workspace (`space.Service.Home`), so everyone owns one; `CreateBot` with no `space_id` lands there. The web reads the current Workspace from the route (`/w/$spaceId/…`, or the open Bot's `space_id`), else `localStorage` `silo.space`, else the first (`web/src/space/`); the rail's top tile is the Workspace switcher and the crests are that Workspace's Bots. **People** (`internal/app/space/people.go`, `invites.go`): an admin makes an invite link (`CreateSpaceInvite`, `/join/$token`, single use, 7 days, only the hash kept; an admin invites members and guests, only the owner admins); it is a bearer, never matched by email, and joins whoever opens it signed in (`JoinSpace`; `GetSpaceInvite`/`JoinSpace` are public procedures that still learn the caller, `seenRPCs` in `app.go`), and makes an account for a visitor only while `spaces.invite_signup` is on (`account.Service.SignUp`). `SetSpaceRole` follows the role table (making someone a guest turns their Can manage into Can use, refused while that leaves a Bot with no manager); `TransferSpace` hands the Workspace to an admin. `ListBotPeople`/`AddBotPerson`/`SetBotRole`/`RemoveBotPerson` keep at least one manager on a Bot, a guest only uses, and adding someone names the secrets another person set (`secrets.set_by`) before a second, confirmed call. **Lending** (`access/lend.go`): a connection or drive with a `lent_by` is personal unless its lender shares it (`SetLendShared`, the lender only); a personal one may only be in Bots whose people are exactly its lender, which `access.CheckLend` (grant, `CreateBot`), `CheckAdd` (a person joining a Bot), `CheckSignIn` (a sign-in or typed credential makes a new lender; `StartConnectorAuth`/`BeginDriveAuth` take `shared`) and `CheckUnshare` hold; `access.LenderOK` refuses a disabled lender's identity (connector calls, drive mounts) until they are enabled again. **Removing a person** (or leaving, or deleting a user) is `space.Service.Remove`: the Bots only they manage go by a plan (another manager, the remover takes it, or delete; `PlanSpaceRemoval` shows the choices), what they lent leaves with them (personal deleted, shared signed out through each `space.Lending`), and their access ends at once: `App.Gone` (`access.Watch`) closes their run streams and desktop/console sockets, and the plain routes recheck `access.CanUse` on every request. A Workspace admin's `ListBots` carries `others`, the Bots they are not on (people, grant count, Delete; never a link). New Bot sends what it may use (`connector_ids`, `drive_ids`, `skills_off`) and who else uses it (`user_ids`), all checked before the Bot exists. `TestEveryRPCChecksAccess` runs every Bot- and Workspace-scoped RPC as a member who uses the Bot, a guest and an admin who are not on it.

**Languages** (`web/src/i18n.ts`, `internal/lang`). The console is translated into English (the source), Polish and German with i18next; a user's display language is `users.language` (`SetLanguage`, Account → Language), mirrored to localStorage for the signed-out pages, and `App` keys the router by it so a change redraws everything. A message's key is its English text: write `t("Save")`, `t("{{count}} files", { count })` (plural forms in `locales/<lang>.ts` as `key_one|few|many|other`) or `<Trans i18nKey="Set <mono>x</mono>" components={…} />` for markup; never concatenate sentences, never call `t` at module level (mark such a string with `msg()` and call `t` where it is shown), and give a homonym a `context`. `i18n_test.ts` fails on a message missing from `pl`/`de`, a stale entry, or a value or tag a translation drops: after adding a string, add it to both catalogs. `web/src/languages.ts` and `internal/lang` list the same codes (a Go test reads the TS). A Bot's language is `bots.language` (a code or `mixed`, default the maker's display language; Settings → Language); `lang.Prompt` puts one line in the Bot's session tier of the system prompt and `lang.Title` tells the title model. iOS is not translated yet.

## Two hops

1. **CP ↔ Worker:** ConnectRPC, Worker-initiated, bot token. Concurrent RPCs.
2. **Python ↔ Worker:** HTTP/JSON on `unix:///var/run/silo/worker.sock`.

File tools stay five: `read` (numbered lines; the Worker slices `offset`/`limit`, rejects binaries, and returns `next_offset`; displayed `N|` is the file's absolute line number), `write`, `patch` (exactly one `old_text` match), `delete` (recursive `Cmd_Remove`, refuses the workspace root), `grep` (ripgrep-only, `include` glob, `max_hits` cap, deterministic `--sort path`, heavy dirs pruned; runs without the shell so it emits no `tool_chunk`). A repeat guard short-circuits a 3rd identical `read`/`grep` in a run and resets on any mutating tool. Do not add a sixth unless a real loop needs it. `present` is a chat tool on the CP (shows a workspace file in the thread via `browse_file`); it is not a fifth worker file tool. A presented image is also attached as pixels on the next model turn so Chromium work can Perceive → Reason → Act → Verify — do not oneshot cookies+search with guessed labels. Scratch lives in `/workspace/bot`; user-facing files in `/workspace`. Chat uploads go to `/workspace/tmp` via the composer paperclip (ConnectRPC `PutFile`, 50 MB cap), carried as a `RunEvent.attachments` list persisted in `RunEvent.Meta`; `start.sh` wipes `/workspace/tmp` on every container start, session_start etc, so it is input only. The model is told the paths in `historyFromDB`; it chooses to `read`/`present`. `present` asks `browse_file` for up to 32 MB (worker `presentLimit`), while the Files tab previews at 2 MB (`browseLimit`) and uploads cap at 50 MB (`putLimit`). `present bot/…` is a collapsed “Looked at …” row, not a folio. The Files tab is a human browser (`mkdir` / `remove` / `put_file` / `browse_file` on the worker). Recreate the box after those worker cmds change.

Memories are pgvector rows (`memories`, `vector(1536)`, per bot) behind `remember`/`recall`/`forget` (rules `bot.*`, default allow); `embedding_model` must be OpenAI-compatible (`llm.Embedder`; Anthropic cannot embed). They reach the model through the prompt, **never through a search made while the human waits** (`internal/app/memory/prompt.go`, `memory.in_prompt`): while their text totals at most `memory.InjectMax` (6000 characters) every memory is listed, oldest first; past that a **digest** stands in — a briefing `memory.Service.SweepDigests` (a `tickLoop`) writes with `model_memory` (`prompts/MEMORY_DIGEST.md`) into `memory_digests` (a table of its own: the bots row is saved whole in places), keyed by a hash of the store so an unchanged one is not summarized again, and rewritten at most every 30 minutes; until the first digest exists the newest memories that fit are listed. `recall` is the embedding search. The section sits after the last system cache breakpoint. Vector `ORDER BY` goes through `Clauses(clause.OrderBy{Expression: …})`: GORM silently drops `Order(clause.Expr)`. SOUL lives in Postgres (`bots.soul`), not on the box. Injected into the system prompt every run. Tool `soul` (rule `bot.soul`) writes the DB (no worker hop). Model may write it; Settings edits SOUL. ListBots omits the body; GetBot/UpdateBot include it.

**Memory collector** (`internal/app/collect.go`, prompt `prompts/MEMORY.md`) saves what the Bot forgot to `remember`. It reads a chat's events after its watermark (`chats.memory_seq`, a `run_events.seq`) as a flat transcript (tool output capped short, failures kept longer), and one tool-less completion with `model_memory` (default: the title model) answers JSON `save` / `update` / `forget`. The model is shown the 15 closest existing memories, and may `update`/`forget` only those ids. Saves go through `memory.Service.Save` (the `remember` dedupe). The watermark advances after a read, including an unreadable reply, but never on a provider/embed error, so every event is read once. Chats older than the column start at their newest event (`Migrate`). The sweep (a `tickLoop`, 5 min, `memory.collect`) reads web and channel chats (never automation or subagent logs) whose newest new event is over 10 min old and that have no live run, at most 5 per tick, and pauses 15 min after a provider error. A delta over 12k tokens is split into at most 3 calls and the oldest excess dropped. The composer's brain button (`MemoryCollect.tsx`, `CollectMemories` RPC) runs it now for one chat. Memories carry `chat_id`.

**Context is append-only** (`internal/app/agent_history.go`, `agent.go`). A provider's prompt cache holds for exactly as long as each request starts with the previous one's bytes, so: (1) the system prompt is built **once per run**, in tiers that each end in a breakpoint — the base `SYSTEM.md` alone (the same bytes for every Bot, so with the tool list it is one cache entry they all share; the Bot's name is *not* in it), the Bot's session (name, connectors, skills, channels, drives, knowledge, tunnels, mail), SOUL — then, with no breakpoint of their own, memories and the notes of the one conversation (channel, automation, subagent); a run that edits its own SOUL is told by the tool result and the *next* run reads the new prompt. (2) What a turn adds to the history is recorded so that `replayEvents` rebuilds **the same messages byte for byte** in the next run: a tool turn is a `turn` event (Body = what the model said, Meta = its calls with the provider's ids — replay prefers it to the streamed `tool`/`tool_args_chunk` events, which older runs only have), the pixels a result came with leave a `seen` event (the text the turn reads as once the image is no longer sent), the taskboard/subagent status is a `note` event told **only when it changed** and kept in history (so it carries no durations or "latest step": `subagentState`, not `subagentLine`), and a message injected mid-run has its `user` event **re-sequenced** to where the run read it (`drainInbox` bumps `seq`; `inject` and the drain share `liveRun.injecting` so the event is written first). The history a run keeps is the text as the log stores it (`App.kept`: masked, valid UTF-8). `turn`, `seen`, `note` and `cleared` are `internalKinds`: persisted with `App.record`, never published, and `StreamRun` skips them. `TestHistoryIsAppendOnly` holds the property (every request extends the previous one, within a run and across runs); a change that makes replay differ from the live run breaks it. The deliberate rewrites are clearing and compaction, and both record that they happened. Do not put anything that changes per message or per turn into the system prompt or into an earlier message.

**Main chat** (`chats.main`, one per person on a Bot by the partial unique index `chats_main_person` on `(bot_id, user_id)`; `chats.Main(bot, user)` finds or makes it, so everyone has one from `CreateBot` or their first `ListChats`). It is where a Bot page opens (`useChatList` sends `/run` there), the target of a `Send` with no chat, pinned above the pages in the sidebar (the date groups are the other, side chats), and it is never deleted or renamed (`errMainChat`; `/clear` and `/wipe` keep it light). Replies to what the Bot made land in it by default: a Feed quote, a Dashboard ask's submit, a `hand` action and a Mail wake append to the main chat (`quote.Put`: the quote in a run of its own, then the owner's turn) unless the request sets `new_chat` (the Feed's second button, Ctrl/⌘-click on the Dashboard) or **a reply is running there**: then they open a chat of their own as before, so a live run's history and the thread never disagree about order. Every such placement goes through `run.Engine.Place` (`App.Place`, `internal/app/place.go`: a `run.Placement` with a `Write`, an optional chat-of-its-own `Title`, `Own`, `Proactive` and the owner's `Message`), which holds the conversation lock across the choice, the write and the start, publishes what was written, and takes it back if the run cannot start; never check the main chat and then act on it. `chats.Put` is the one way an event is written into a chat outside a live run (a finished run of its own, the Bot's zone, `updated_at` bumped), and `chats.Web`/`WebScope` the one test for a web chat.

**Several people on one Bot** (phase 6 of `docs/workspaces-handoff.md`; a Bot with one person behaves byte for byte as before). A chat has an author (`chats.user_id`; empty is the Bot's own: a mail wake, a channel, an automation's log); a run is its chat author's (`runs.user_id`, from the chat, since only the author writes there; a subagent's log is its lead chat's author's), and a `user` event records `user_id` and, only while the Bot has more than one person, a frozen `author` that `replayEvents` puts on its stamp (`[bob@… · Sun, …]`, `stampAuthored`) and the collector therefore reads. `access.Chat` reads a chat for its author, the Bot's managers, and anyone on the Bot for an automation's log (`access.CanRead`); writes are the author's, or a manager's in the Bot's own (`CanWrite`): a manager reads and stops someone else's chat, never writes in it. `ListChats` gives a user their own chats and a manager everyone's (`Chat.author`/`mine`; the sidebar's **Team** group), and the Bot-wide `StreamRun` drops events of chats the viewer cannot read (`chatReader`). `Place` puts a placement in the presser's main chat (`Placement.UserID`), and the Bot's own doing in the main chat only while it has one person; with several it opens a chat of its own or waits on the Dashboard. **Approvals:** `ListApprovals` returns only what the caller may answer (`Approval.person`, `once_only`): a user answers their own runs' approvals with Allow once or Deny (`always` reads as `allow_once`), managers answer the rest, and an action marked `manager` in the security catalog (`security.ManagerOnly`: automations, `bot.soul`/`set_proactivity`/`set_timezone`, `tunnels.public`, channel sends) is the managers' whoever's chat asked. **Read state** is per person: the Feed's unread and the Dashboard's "since you last looked" use `bot_access.feed_read_at`/`dashboard_seen_at`. The session tier names the people (`peopleSections`) while there are several, the time zone follows a device only while the Bot has one person, and `Bot.people` lists them for the sidebar.

**Proactivity** (`bots.proactivity`, `internal/app/proactivity`, `a.Proactivity`) is one choice of how much a Bot does unasked: `off` (no Heartbeat; the default), `quiet` (a 09:00 Heartbeat that reports to the Feed; questions wait on the Dashboard) or `active` (a Heartbeat every three hours from 09 to 21, and `ask_owner` from a background run may write into the main chat). `proactivity.Service.Set` puts the Heartbeat on the level's schedule (`automation.Service.SetHeartbeatSchedule`, named columns only) and then sets the column; `proactivity.Levels` is the one list the tool's enum and its error come from; a Heartbeat schedule set by hand reads as `Bot.heartbeat_custom` (`proactivity.Service.Custom`) and the next choice replaces it, even of the same level. The owner picks it in Settings (`Proactivity.tsx`, saved on its own through `UpdateBot.proactivity`); the Bot sets it only on the owner's word with `silo_runtime.set_proactivity` (rule `bot.set_proactivity`, Allow, lead-only). **The interview** is a run Silo starts in the main chat when New Bot's **Start with a short interview** is on (`CreateBot.interview`) or the owner types `/onboard`: its opening turn is `prompts/ONBOARDING.md` (or the operator's `onboarding.prompt`) as a `user` event with `tool="onboarding"`, drawn as a "Getting to know you" divider, and it walks through `ask_owner` cards — areas of help, setup offers, permission to look, a checkbox card of facts to remember, SOUL, proactivity, starter automations and an `ideas` widget. **Ideas** are a widget kind (`{items: [{title, prompt}]}`) whose press puts the prompt in the main chat's composer, unsent (`dashboard/Ideas.tsx`); until a Bot has one, the board shows `StarterIdeas`, a translated set shaped by what is connected and written by no model. **Activity**: `Bot.activity` is one row per live run (where it runs and the tool it is in: `liveRun.step`, set when a tool call starts), so the sidebar's `ActivityStrip` under the Bot's name shows what it is doing and links to it.

**Asking the owner** (`ask_owner`, `internal/app/dashboard/cards.go`, rule `bot.ask_owner`, Allow, on both surfaces) is the Bot's *what should I do?*, where the Feed is *this happened*. It is a Dashboard ask (`DashboardCard`, the same table, blocks and form controls) shown where it belongs: asked in a web chat it is a `card` event in that chat and **ends the run** after that turn's calls (`App.EndTurn`: the question is the turn's last word, and the owner's answer starts the next run) (body = the card id; `App.threadEvent` and the live emit attach the card **as it stands now**, so an ask answered on the Dashboard reads as answered in the chat); asked from anywhere else (an automation, a channel) it is `quote.Put` into the main chat as a `FromAsked` quote carrying the card id — only while the main chat is idle and the Bot's `proactivity` is `active` (`Placement.Proactive`) — and it always waits on the Dashboard. An answer to a card shown in a web chat (`answerIn`) goes to that chat as the owner's turn with no quote; otherwise the old quote flow. A change of state is a transient `card_state` event carrying the card (published with `host.Emitter.Publish`, as is an offer's `setup_state`), which `fold` applies to every block showing it. Putting a card away in a chat is an answer too: `DismissDashboardCard` tells the Bot there ("Not now for your question …").

**Setup offers** (`internal/app/setup`, table `setup_offers`, tool `offer_setup`, rule `bot.offer_setup`, Allow, both surfaces, lead-only) are the Bot offering something from the catalog to add — a library connector (target = its identifier), a channel adapter or a drive template — as a card of its own in the thread (a `setup_offer` event, body = the offer id; `App.threadEvent` and the live emit attach `RunEvent.setup_offer` as it stands now, and `setup_state` is the transient update). The card (`web/src/setup/OfferCard.tsx`) shows the provider's mark, name and blurb from the catalog, the Bot's `why`, and the values it filled in; **Set up** opens Silo's own form (`SetupModal`, portaled to `document.body`: the connector library form, `ChannelForm` then `ChannelSetup`, `DriveForm`, each taking `prefill`). An offer with only a target leaves the form at its defaults; `options` may fill in the form's own settings (`setup.options`: a name, a connector's `default_mode`/`expose_completion`, a channel's `inbound`/`enabled`/`prompt`, a drive's `read_only`) and the provider's declared fields that are neither secret nor an address (`addressField`); anything else is refused with the reason, so a misled Bot cannot point Silo anywhere. Unlike a question, an offer does not end the turn, so the Bot can say what it offers. Offers of one run are one group in the thread (`fold`: `offers`, two to a row from `sm`, the `offer_setup` rows hidden like an artifact's). `ResolveSetupOffer` (done or skipped; `rest` skips the run's other open offers too: **Not now for these**) tells the Bot in that chat in one message per batch (`setup.tell`, `setup_offers.told`): a setup at once, with what is still open; a "not now" only once none of that run's offers are open. From an automation an offer goes to the main chat only when the Bot is `active` and the main chat idle; otherwise it is refused.

**Slash commands** (`internal/app/command`, defs and handlers in `internal/app/commands.go`) are one registry for every surface: `Send` parses the text (`Registry.Parse`: `/name` at the very start, `@Bot` suffix allowed, an unknown `/name` or a `//`-escaped one is a message) and runs a command instead of starting a run; the response carries `command`, an English `notice` (what a channel gets back), a `value` the web words itself (`saidFor` in `bot/runActions.ts`), `confirm` for a command that destroys something (sent again with `confirmed`), and `new_chat`. A channel conversation runs commands through `run.Engine.Command` from `deliverInbound` and gets only the `Channel` ones (`/clear`, `/stop`, `/help`): the sender may be anyone in that conversation. `ListCommands` feeds the composer's `/` menu (`composer/slash.ts`, `SlashMenu.tsx`; summaries are translated client-side). **`/clear`** is a `context_cleared` event in a run of its own (origin `command`): `replayEvents` starts after the last one (before any compaction cut), nothing is deleted, the memory collector skips the event and still reads what came before it, the chat's taskboard and live subagents go, and the Python interpreter follows the boundary (`pySessionFor` = chat id + the newest clear/wipe event id). Refused while a reply runs. **`/wipe [last|all]`** (default: since the last `/clear`) deletes events for good (`deleteChatEvents`: events, emptied runs and their settled approvals), leaves a `wiped` marker (body = how many), never touches memories, and asks first; artifacts no longer shown anywhere go on the next `SweepBot`. **Threads page**: `StreamRun` replays only from the `pageTurns`-th newest user message and opens with a transient `earlier` event when there is more; `ListChatEvents(before_event_id)` is the page before. `foldEvents(events, first)` takes a negative start so a prepended page keeps the drawn blocks' keys.

**Clearing stale tool results** (`internal/app/clear.go`) is tried before compaction, at the same threshold: all but the newest tool results (at least 3, at most a tenth of the window) are replaced with a one-line placeholder, calls and pairing kept. It happens only when that frees at least a quarter of the trigger level *and* brings the conversation back under it (otherwise compaction runs on the untouched history, so the summary reads the real output); the freed estimate is scaled by the last turn's provider count over the engine's estimate of the same content. A `cleared` event (`Meta.results` = how many, counted from the start of the replayed window) lets `contextFromRuns` clear the same ones; `replayEvents` itself leaves the text alone because the memory collector reads it.

**Compaction** (`internal/app/compact.go`) keeps a conversation inside the model's context window. The window is `context.windows` (per-model override) → the provider's `llm.ContextWindower` (OpenRouter `/models` `context_length`, cached 6 h) → `context.window`. Before each turn `runLoop` takes the last turn's provider usage plus an estimate of what was appended (runes/3.5; the whole request on a run's first turn) and, at `context.compact_at` of the window, summarizes the history with the chat model (`prompts/COMPACT.md` over a flat, front-trimmed transcript) — mid-run too, with a continue note. A provider context-length error compacts once and retries the turn. A compaction is a persisted `compaction` event (body = summary, `tool` = auto/manual, `Meta.after` = last summarized event), opened by a `compacting` event; the thread keeps every event and `historyFromEvents` replays the last summary then only events after its anchor (so a message injected while the summary was written survives), folding the next user turn into it. Diverge remaps the anchor. Usage events carry `window`; the composer's context meter (ring + %) shows it and its click is `CompactChat` — a manual compaction run (origin `compact`, no user event) refused while a reply runs, for channel chats, or when the history is already just a summary; a message sent during it is injected and answered after. Never compact by deleting events.

**Decision models** (`internal/llm/decide.go`, `internal/app/models/decide.go`, `internal/app/approval`). A model is one of two **kinds** (`llm.KindText`, `llm.KindDecision`). A text model writes (`llm.Client`); a decision model (TypeSafe's Jev and the family that followed: Clef, Solar Decide, …) is shown a `state` and typed questions and answers each with probabilities, no text (`llm.Decider`: `DecisionRequest{State, Questions}` → `Answers`). The three questions keep the hosted APIs' names: `noul` (yes/no, the answer is P(yes)), `choice` (one of the options the caller describes), `score` (2 to 10 ordered levels); `llm.Question` marshals to the wire shape both APIs share and `DecisionRequest.Validate` refuses a bad one in words the Bot can act on before anything is sent. `DecisionResponse.check` fails a call whose answer is missing or of another type than asked: callers branch on these numbers without reading them, so a zero value must never pass for an answer. Two providers are Deciders, and `Descriptor.Kinds` says so (`TestDecisionProviders` pins that the descriptor and the interface agree): **`openrouter`** posts to its Decisions API, which sits *beside* the OpenAI-compatible root (`…/api/alpha/decisions`, `openRouterDecisions(base)` — not under `/v1`) and serves every decision model it lists; **`typesafe`** (`internal/llm/typesafe.go`) is TypeSafe's own System One API (`POST {base}/systemone`, default base `https://api.typesafe.ai/v1`), decision-only, so its `Complete`/`Stream` answer an error. They share one `decisionEndpoint` (same body, same answer; errors read from `error.message` or `detail.message`, key masked; 429/503/529 retried twice). OpenAI's own `/v1/decisions` (limited preview, no public schema) and llama.cpp's typed-decision API are not wired: a new one is a `Decider` on its provider plus `Kinds`. **Listing:** `ModelInfo.Kind` — OpenRouter's default `/models` lists only text, so `openRouterClient.ListModels` makes a second query (`?output_modalities=decisions`) and keeps only entries whose `architecture.output_modalities` has `decisions` (a proxy that ignores the query answers with the text list again); TypeSafe's `GET {base}/models` is a bare list of `{name, description, release_date}`. **Config:** `decision_models` is its own allowlist next to `models` (an id is in one only, its provider must serve that kind: `validateModels`), `model_decision` the default (`Config.DecisionModel`: the setting while still allowed, else the first allowed, else none — so a stale default never blocks taking a model off the list), and `Config.ModelKind(id)` is how anything asks what a model is (in `decision_models`, or a decision-only provider). The text roles (`model`, `model_title`, `model_subagent`, `model_memory`) refuse a decision model; `model_approval` takes either (`admin.modelRoles`). `SetModels` carries `kind`; `Settings.decision_models` and `Provider.kinds`/`ProviderModel.kind` feed the UI: Admin → Settings → Models has **Allowed text models** and **Allowed decision models** (`AllowedModels kind=…`), a **Default decision model** picker, and an auto-approval picker that offers both kinds (`eitherKind`); a provider's **List models** shows a Text | Decision switch when it has both. Chats, Bots and `switch_model` only ever see `models`. **`decide`** (`models.Service.DecideTool`, rule `model.decide`, Allow) is on both surfaces — a chat tool for a judgment or two mid-turn, `silo_runtime.decide(state, questions, model=None)` for a loop over many items — and asks the default decision model or another allowed one, answering `{model, answers, usage}` as JSON either way. Its chat schema spells the question shape out (`questions` is an object whose `additionalProperties` is `{type: noul|choice|score, instructions, criteria}`; `state` is an object of named fields; `criteria` is described, not typed, because its shape follows the type) and sticks to what every provider takes: no type unions, no array without `items`. `TestLiveDecideToolCall` (build tag `live`) offers it to real chat models and runs the calls they write; re-run it after touching the schema, the description or the prompt section. A model that writes `questions` as a JSON string is read anyway (`rawQuestions`). It is `Enabled` only while a decision model is allowed, so it is in nobody's tool list otherwise, and so is its prompt section (`prompts/DECIDE.md`, `{default}`/`{models}` filled from operator config, the same text for every Bot), which says when to call the tool and when to loop in Python. The thread shows a call as Decision · the questions' names (`toolInfo.ts` `asked`). `list_models` adds `decision_models`/`default_decision`. Every decision goes through `models.Service.Decide`, which records it in the LLM debug log (state + questions as the request, answers as the response). **Auto-approval** (`approval.Service.Judge`, called by `AuthorizeAction` for a rule set to Auto) builds one `approval.Request` whichever kind of model judges: the Bot's policy, the action (`security.Describe` of the redacted arguments), where it came from, and **the human's latest message in that conversation** (`lastHuman`: the newest `user` event with no sender tag, so a lead's brief or a quoted mail is not it; a subagent gets its lead chat's). An automation, an orphan call (Console, a background process, stray code) or a chat nobody wrote in has no such message, and **nothing is put in its place**: the gate is told `Automations: …` or `Unknown: …` (`Request.from`) and the automation's own prompt is never passed off as the human's (`TestAutoApproveFromAutomationHasNoHumanMessage`). A text model gets `prompts/APPROVAL.md` + the policy as the system prompt and the request as one user message with the human's words and the action fenced as data, and answers one word (`parseVerdict`: anything unrecognised is ask). A decision model gets the request as the `state` and two `noul` questions, `allowed` and `forbidden` (two, so a policy that is silent answers no to both), and `verdict` holds them to `approval.Sure`/`Unsure` (0.9/0.1): deny when forbidden is sure, approve only when allowed is sure *and* forbidden is unsure, otherwise ask. A model error, a timeout (30 s) or an empty policy is ask, never allow. An approval the gate fell back to is marked (`approvals.auto`, `Approval.auto`): its slip offers only Allow and Deny plus a link to Rules, and `DecideApproval` reads an `always` vote on it as `allow_once`, so answering one call never turns the Auto rule into Allow. Tests drive both through the dummy provider, which is also a Decider (`dummy/judge`; `Test_Yes_<q>`/`Test_No_<q>`, `Test_Pick_<option>`, `Test_Unsure`, `Test_Decide_Error`, and `Test_Approve`/`Test_Deny` on the gate's questions; `dummy.Decided()`/`Completed()` show what was sent).

**Output rules** (`internal/app/filter`, `internal/app/filter_hook.go`, `internal/security/output.go`). A rule has two sides. The call rule says whether an action may run; the **output rule** says what happens to its result before the Bot reads it: `pass`, `flag` (always framed as untrusted, no model asked), `check` (the filter model judges) or `withhold`. It is `rules.output` on the same row (`''` = the default; a row may hold only an output rule, `ruleDecision` skips an empty `Decision`), looked up by `App.ruleOutput` with the call rule's precedence (the action's row, the connector's `*` row, the catalog's `spec.output` via `security.DefaultOutput`, then `Def.OutMode`). **Defaults:** what comes from outside is checked (`web.search`, `mailbox.list`/`read`, `chats.read`, `bot.transcribe`, and every connector action: `connector.toolDef` sets `OutMode: check`), everything else passes, and every row is the owner's to change — `python.run`/`terminal.run` set to Check is how content a script fetched itself gets judged. `SetRule` carries `optional output`; a request with an output and an empty decision changes the output side alone. Secrets, channel sends and `tunnels.public` have no output side (`outputApplies`; `Rule.output` is empty and the Results view drops the row). **One hook:** `tool.Engine.Run` hands what every handler returns to `Engine.Filter` (`tool.ResultFilter`, implemented by `App.FilterResult`), so both surfaces and every connector go through it; a handler's error is filtered too (an MCP `IsError` body is its server's text), the gate's own `denied`/`canceled` and the Python-`Local` grant are not. **Verdicts** (`filter.Service.Check`): `clean` passes untouched, `flagged` passes framed, `withheld` never reaches the Bot, and `unchecked` — a model error, the 30 s timeout, an answer that is no verdict, or a result over `filter.max_chars` — **passes with a warning frame**: the filter never holds a run up and never asks the human. A long result is judged in overlapping 8000-rune parts (4 at once) and the worst part wins; a verdict is cached 10 minutes per model + policy + call + text (never an unchecked one). The model is `model_filter` (either kind; falls back to `model_approval`): a text model gets `prompts/FILTER.md` + the policy as the system prompt and answers one word (`parseVerdict`), with the result fenced between two lines that carry a random id so text inside cannot close the fence; a decision model gets one `choice` question (`clean`/`suspicious`/`malicious`) held to `approval.Sure`/`Unsure` (`grade`: withheld at 0.9 malicious, clean at 0.9 clean, flagged at 0.1 or less clean, otherwise unchecked). Both are shown what the approval gate is shown about where the call came from (`approval.Service.Source`: origin and the human's latest message, never invented) plus the call itself, so a README's install steps are clean when the human asked for the setup. The policy is per Bot (`bots.output_policy`, Rules → Results; `UpdateBot.output_policy` is `optional`), and empty means the built-in `prompts/FILTER_POLICY.md`: the severity ladder for indirect prompt injection (it judges attempts to steer the Bot, not truth or taste). `TestLiveFilter` (build tag `live`) runs a corpus through real models of both kinds; re-run it after touching either prompt, the question or the levels. **Nothing a model writes reaches the Bot:** the frames are fixed text in `filter/frame.go`, and the action name in them is reduced to plain characters (a connector's server picks it). **What the Bot gets:** on the chat surface the frame is the head of the tool message itself (the 12000-byte cap cuts the tail), a withheld result is a fixed placeholder; and since `Engine.Run` returns the final text, what is emitted, appended and replayed is the same bytes (append-only holds with no replay-time transform). From Python the code gets the data in its own shape (a withheld result is an error, so a script cannot carry on without it), and **the warning is the control plane's to deliver, never the machine's**: what a cell prints is up to the code, and a Bot's worker can be older than the CP, so `FilterResult` holds a `filter.CellNotice` for the run (`App.holdNotice`) and the chat loop puts what is held at the head of the result of the tool call that code ran in (`takeNotices`, before the mask and the cap; one line per action and verdict). A call that named no run (an old `silo_runtime`, a raw socket call, a process a cell left behind) is held for the Bot instead and rides on the next tool result there within 6 minutes. Do not move this back into `silo_runtime` or the worker: a warning the Bot's own code can drop is not one (`TestCodeCannotHideAFilteredResult`, `TestFlaggedWebSearchReachesTheBot`). **Only the CP speaks as the filter:** every completion-surface result, whatever its rule and even with the filter off, goes through `filter.Defang`, which rewrites an opening `[Silo output filter` in the result's own text to `[quoted, not from the filter:…`, so a page cannot forge a notice or seem to close a frame. **Hidden text:** `filter.reveal` spells out text written in invisible Unicode tag characters for the judge (the Bot's copy is unchanged; a flag emoji's region code is left alone). A result that is pixels alone still obeys Flag and Withhold (Withhold drops the image); Check has no text to judge there. SYSTEM.md has an **Outside content** section saying what the frame means. **The thread:** a `filtered` event (`Tool` = `connector.action`, body `{verdict, mode, original}`) is emitted while the call is still running, just before its result; `fold/tools.ts` puts it on the nested call of that name or the running tool row, and the row's tail shows one word. `original` (a withheld result, masked, capped) is for the owner only: `replayEvents` has no case for the kind and the memory collector reads through replay, so no model sees it. Every non-clean verdict is an audit row (actor `filter`, `output_flagged`/`output_withheld`/`output_unchecked`). Config: `filter.enabled` (the operator's cost switch: off, every result passes and the rules are kept; `ListRules.filter_enabled` tells the page), `filter.max_chars`, `model_filter` (Admin → Settings → Models and Context & runs). Tests drive it through the dummy: a decision model picks `Test_Pick_suspicious`/`Test_Pick_malicious`, a text model answers `Test_Flag`/`Test_Withhold` when its system prompt carries `dummy.FilterMarker`, `Test_Unsure` is no verdict for either, and with no token both answer clean. Not covered, by design, and worth saying to an owner who asks: image pixels under Check (`look`, `present`, screenshots); the live `tool_chunk` stream the human watches; messages that are not tool results (channel inbound, a mail that wakes the Bot); and **data that code kept**: a cell that stores a flagged result in a variable or a file and prints it in a later cell is warned about in the first cell's result, not the later one. Setting `python.run`/`terminal.run` (and `files.*`) to Check is what covers that.

**Thinking levels** (`internal/llm/thinking.go`, `internal/app/models/thinking.go`) are one neutral ladder (`off`/`minimal`/`low`/`medium`/`high`/`xhigh`/`max`; `""` = model default, nothing sent) on `llm.Request.Thinking`. Which levels a model takes comes from `thinking.levels` in silo.yaml, then the optional `llm.Thinker` (OpenRouter `/models` `supported_parameters` has `reasoning`; Anthropic Models API `capabilities` — adaptive+effort or budget-only; OpenAI by family); `ListModels` carries them per option. The chat stores its choice (`chats.thinking`, `SetChatThinking`) and each turn fits it with `NearestThinking`, so it survives a model switch; the composer's picker shows the fitted level (`web/src/thinking.ts` mirrors the fit) and hides when the model lists none. Each provider maps the level itself: OpenRouter `reasoning.effort` (`off`→`none`), OpenAI/local `reasoning_effort`, Anthropic adaptive thinking (`display: summarized`) + `output_config.effort` or a `budget_tokens` budget with `max_tokens` raised past it. Anthropic's signed thinking blocks come back as `EventThinkingBlock`, ride on the in-run assistant message (`Message.Thinking`/`ThinkingModel`, never persisted), and are replayed first in that turn only to the model that wrote them — a tool loop with thinking needs them.

**Knowledge** (RAG; `internal/rag`, `internal/app/knowledge`, worker `knowledge.go`) lets the owner pick any workspace folder, drives included, and the Bot search it with `search_docs` (chat tool + `silo_runtime.search_docs`, rule `bot.search_docs`, Allow; offered only while the Bot has a folder and `knowledge.enabled`). Files stay on the box; `knowledge_folders` / `knowledge_sources` / `knowledge_chunks` (`vector(1536)` + generated `tsv`, HNSW + GIN) live in Postgres, per Bot, separate from `memories`. The worker has two read-only commands: `Walk` (path/size/mtime, recursive, skips hidden + heavy dirs + symlinks, skips `drives/` unless the root is in one, **a missing or unreadable root is an error, never an empty list**) and `Extract` (text + sha256 of the bytes: text/sniffed as is, PDF `pdftotext -layout` with form feeds as pages, docx/odt/rtf/epub/html `pandoc -t gfm`, `.doc` `catdoc`; binary or over 50 MB is `skipped`; the converter is looked up before the file is read so a missing tool costs no drive download). Sync (`knowledge.Service.SyncFolder`, one per folder under a lock) is **size+mtime first, sha256 only for changed candidates**: same hash = refresh mtime, no embed; a vanished path whose hash shows up at a new path is a rename and keeps its chunks; a changed `embedding_model` re-embeds (`embed_model` is on the source); an error source retries after 1 h. An empty listing of a `drives/` folder that had an index is treated as a disconnected drive (error, nothing deleted). Chunks come from `rag.Split` (form-feed pages, markdown heading path, ~2400 chars with overlap, the embedded text is prefixed with file + heading). Search is hybrid: top 30 by cosine (dropped past 0.85 distance) + top 30 keyword (`plainto_tsquery('simple')`, all-words matches first, stopwords stripped), fused by reciprocal rank in one SQL; it runs on the raw ConnPool with `$n` args because GORM `Raw` mis-handles `@@`, and sets `hnsw.iterative_scan` (pgvector 0.8) behind a savepoint so the per-Bot filter still returns k rows. The sweep (a `tickLoop`, `knowledge.Tick` = 30 s, `knowledge.sync_interval` default 15 m, drives ×4) syncs a folder when it is stale or `dirty_at` is 15 s old (set by the Bot's `write`/`patch`/`delete` and the Files tab's put/remove via `knowledge.Service.Dirty`), skips Bots with no worker (never starts a box), at most 2 per tick, pauses 15 min on a provider error. Add refuses the workspace root, `bot/`, `tmp/`, the bare `drives` root, anything missing, and any folder nested in or holding another. Caps: 5000 files and 2 MB of text per file. **OCR** (`knowledge.ocr`, default on; worker `ocr.go`): after `pdftotext`, only pages with under 20 non-space characters are rasterized (`pdftoppm -r 200`) and read with tesseract (every installed language, English first; the image ships eng + pol in its own layer), 3 pages in parallel at one thread each, at most 100 pages and 4 minutes per file; image files (png/jpg/tif/bmp/gif/webp, at least 8 KB) go straight to tesseract. Recognized text must be at least 60 % letters/digits or it is dropped as photo noise. With OCR off the worker words a scan with `OCR is off`, the source is recorded as skipped/ok with that detail, and `sourceUnchanged` re-reads such files once OCR is turned on (a file OCR already looked at is not retried). A missing tesseract fails that file only. The worker tests that need the image tools skip on a host and run for real in the image (TESTING.md); `TestContainerKnowledgeAllFormats` is the end-to-end proof. The `Knowledge` side page (`/bots/:id/knowledge`, a row in the sidebar) has a folder picker (dirs only, drive disclaimer, `NeedMachine` when the worker is down), per-folder status/Sync now/armed remove, the not-indexed list, and a try-a-search panel (`SearchKnowledge`). The prompt lists folder paths only (counts would bust the cache tier). Snippets can lag edits: the tool tells the model to `read` the cited path before relying on one.

**Changes** (`internal/app/changes`, worker `history.go`) show what changed in a Bot's workspace as diffs. It compares **state, not actions**: a file a script wrote is seen like one `write` wrote, so never track the file tools instead. The worker keeps a shadow git repository **outside the workspace** (`/var/lib/silo/history`, bound from `data/bots/<id>/history`, so Files, grep and Knowledge never see it and it outlives a container reset; `GIT_DIR`/`GIT_WORK_TREE`, the user's and system git config ignored) and uses it as a snapshot store only: a **checkpoint** is a parentless commit under its own ref (`refs/silo/cp/<unix nanos>`), so any two diff and forgetting one is deleting a ref; an unchanged tree makes no checkpoint. What keeps it from swallowing the workspace: `info/exclude` holds `/drives/` (remote data behind FUSE — it must never be listed), `/tmp/`, `/bot/` and `grepPruneDirs`, and excluded directories are not descended into; the workspace's own `.gitignore` files are honoured; a file over `changes.max_file_mb` is never hashed — the tree gets a **stub** blob (size + mtime) through a throwaway index, because a stub in the real index would make git hash the file to refresh it; a nested repository is one gitlink; one checkpoint adds at most 20k files / 512 MB (a huge workspace is indexed over several, marked `partial`, and a change set whose base was partial is the index catching up, not a change); checkpoints expire by count (300), `changes.keep_days` and a 1 GB store budget. `git add` runs with `--ignore-errors` (an unreadable file must not cost the checkpoint) and is retried once when a listed path vanished; a stale `index.lock` from a cancelled git is removed under the worker's history mutex. Five worker commands: `Restore` (below), `Checkpoint` (carries the CP's opaque `note`), `Changes` (lists consecutive pairs newest first, computes **pending** — the working tree against the last checkpoint, uncommitted — and takes the baseline or the next partial slice itself), `ChangeFiles` and `ChangePatch` (ids must be 40–64 hex: they go to git as arguments). **Nothing is in Postgres**: the store is the history, so the pane needs the machine up. The CP decides *when* and *who*: `changes.Service.Begin` runs before a run's first tool that can change files (`changesWorkspace`: terminal, exec_python, write, patch, delete, and the desktop's click/type/key) and `End` after `finish` (in a goroutine: nothing waits for the worker round trip). A change set is attributed to **every run that has begun changing things on that Bot** in that stretch (the workspace is per Bot, so concurrent chats share a diff — the pane says so rather than guess); what a run's opening snapshot finds is nobody's run ("Outside a run": the owner in Files or the Console, a background process). A snapshot never fails a tool. An old worker (`unknown cmd`) or an image without git reads as `ListChanges.state = outdated` and the pane asks for a container reset. `GetChangePatch` masks secrets like `ReadFile`. **Restore** (`RestoreChange`, worker `Restore`) puts files back as they were before a change — one file, or every file of the change — and is the owner's button only, not a Bot tool. The worker checkpoints what is there first (`before_restore`), acts on the difference between the wanted snapshot and that checkpoint, then checkpoints again (`restore`; the pane titles it "Restored by you"), so a restore never loses anything and is undone like any other change. Acting only on that difference is the safety: a path the history never tracked (a drive, `bot/`, an ignored folder) cannot be removed whatever the caller names. It skips, and reports, what could not be taken back — a file over the cap or a nested repository on either side (`large`/`repo`: the content was never kept) and a path with a link, a file or a non-empty folder in its way (`blocked`: `realParents` keeps a write from following a symlink out of the workspace). Files are written by `git checkout-index` from a throwaway index of the old tree (exec bit, symlinks, replace-not-write-through). It refuses while the workspace is still being indexed, and marks Knowledge dirty through `workspace.Service.Changed`. Restoring from an older change also drops what was done to those files since; the pre-restore checkpoint is what brings that back. A tracked path under a folder that became a link or a file is dropped from the index with `update-index --force-remove`, never handed to `git add` (it dies on "beyond a symbolic link" and would cost the whole checkpoint). Config: `changes.enabled`/`max_file_mb`/`keep_days` (Admin → Settings → Context & runs). The pane (`web/src/Changes.tsx`, helpers in `changeset.ts` because `changes.ts` would clash on a case-insensitive disk) is a right-rail pane: change rows open into files, files into the diff; it polls only while visible, since every look snapshots the workspace. **Drives get a journal, not snapshots** (`internal/drivehost/journal.go`, `internal/app/changes/drives.go`): listing a drive is network calls and reading one downloads the owner's other data, but everything that writes to a drive crosses its FUSE mount, so the sidecar reads each change off rclone's own log — which is what catches a script. rclone logs an upload reaching the remote at INFO (`Copied (new)` / `Copied (replaced existing)`, with the size) but a delete or a folder rename **only at DEBUG**, as the mount layer's call and its result (`Remove: name="x"` then `>Remove: err=<nil>`, `objectType` `*mount.Dir`); so mounts run `--log-level DEBUG --use-json-log` (reserved flags: a spec cannot change them). `logSink` is rclone's stderr: it decides on the raw bytes, parses only the lines that matter, and passes on just notices/errors/non-JSON as rclone's plain log line, so `CleanError` and the container log read as before and the debug chatter never leaves the sidecar. Calls on one directory are matched to results first in, first out; a failed call (`err` not `<nil>`) is nothing. The line shapes are rclone's: `TestJournalReadsRcloneLines` pins a capture of the real thing and the engine test (`-tags engine`, `TestDriveEngine`) checks them against the image's rclone — re-check both when bumping rclone. A file written and removed before rclone uploads it (write-back is a few seconds) never shows; an upload shows when it reaches the provider. Changes leave the sidecar in batches (`DriveUp.changes`, 200 a frame, a 300 ms gather; frames queued while the CP is away can overflow the outbox and are lost). The CP files them as `drive_changes` rows (`Seq` orders them; newest `changes.DriveKeep` = 2000 per Bot; the drive's name is on the row so a line outlives its drive; what a sidecar sends is cleaned, not believed) through `drive.Service.OnChange` → `changes.Service.RecordDrive`, stamped with the runs at work **or ended within 45 s** (`driveGrace`: the upload lands after the tool call). No content is kept and there is no restore: the pane says to use the provider's version history or trash. `ListDriveChanges` needs no worker, so the pane's **Drives** view (a Workspace | Drives switch, shown once the Bot has a drive) reads while the Bot is stopped, which is why `ChangesPane` keeps its own header like Mail. `DeleteBot` drops the journal (`changes.Service.Drop`).

**Web search** (`internal/search`, `internal/app/websearch.go`) has three engines: the **Built-in Scraper** (`builtin`, below), and two keyed ones that are one provider's own index behind the operator's key — **Brave Search** (`brave`, `api.search.brave.com`, `X-Subscription-Token`) and **Exa** (`exa`, `POST api.exa.ai/search`, `x-api-key`, highlights as the snippet) — each with a secret `search.<id>.api_key` (`internal/search/keyed.go`: cached 5 minutes with one flight per query, a 429 retried once, 401/403/402 worded as the operator's problem, the key never in an error; a failure is an error, not a `blocked` note, because no other source could cover it; Brave retries without `country`/`search_lang` on a 422 for a region it does not list; Exa takes only the country). The rest of this paragraph is the Built-in Scraper: a keyless metasearch. A `source` is one site (`duckduckgo`, `mojeek`, `brave`, `startpage`, and the APIs `wikipedia`, `marginalia`; `search.builtin.sources` narrows the list). Two things rule it. **Speed:** `meta.run` never waits for a stuck source — each has 2.5 s, once 3 providers have answered the rest get 300 ms, after 1.2 s any results in hand are enough, and 4 s is the ceiling (the constants head `meta.go`). **Manners:** the Control Plane is one address to a search site however many Bots it serves, and a site asked too often blocks that address for everyone (DuckDuckGo answered four requests in three seconds and then 202 to everything for twenty minutes; Brave 429 after a dozen in a few minutes). So every scraped site has a token `bucket` (`scraped`: one request per 6 s, 2 at once; shared package state), and a search asks the APIs plus at most `fanout` (2) scraped sites — the one with the most budget left, and a second only while it is *idle* (full budget), so a lone search hears several voices and a burst spreads thin instead of spending every site on its first searches. The sites not asked are a reserve: one is asked for each that fails. With every budget spent a search queues up to `queueMax` (8 s, before the ceiling) for the next turn; past that the site is `busy` and listed like a blocked one, with no verdict on its health. Do not add a scraped source without a `limit` (`TestScrapedSourcesAreLimited`), and do not loop the live test: it spends the same budgets from the same address as the running CP. Lists are merged by reciprocal rank fusion on a canonical URL (`fuse.go`: no scheme, `www.`, fragment, trailing slash or tracking parameters), and `Hit.engines` is how many providers returned the page. A source answers `errBlocked` for a refusal, a captcha, or a page with neither results nor the site's own "no results" notice — a true empty page is `nil, nil`, and telling the two apart is the point: the `breaker` backs a failed source off (30 s doubling to 30 min; a `refused` that is `limited` — 429, DuckDuckGo's 202, 503 — rests at least 2 min or its `Retry-After`, because asking a rate-limited site again renews the limit; a source cut short because the search was already done gets no verdict), `Result.blocked` names the providers that did not answer, and a result that is empty because of them carries a `note` saying the search failed, so the model does not conclude nothing exists (SYSTEM.md says the same). Answers are cached 5 minutes per text+language+country (never an empty-because-blocked one) and identical concurrent queries share one flight. **The browser the sites see** (`http.go`) is Chrome 145 on macOS in every layer a site can read: utls's Chrome 133 TLS hello (still what 145 sends), Chrome's HTTP/2 SETTINGS and window, pseudo-header and header order (`chromeOrder`), and the headers of the navigation it claims (`navigation`: `sec-fetch-site` none/same-origin, `origin` + `cache-control: max-age=0` on a form post, `accept-encoding: gzip, deflate, br, zstd` with req decoding). It is built by hand on `imroc/req`, not with `ImpersonateChrome`, whose preset mixes versions (an old SETTINGS frame, `accept-encoding: gzip`, the no-cache pair of a hard reload) — a client that is Chrome in one layer and not in another is what bot detection looks for. `TestFingerprint` (live) compares it with the known hashes; re-run it when moving to a newer Chrome, and copy a real one's values rather than guess. No cookie jar: region cookies are per query. The two real APIs are asked under our own name instead, because Wikipedia refuses a client that only looks like a browser. No fingerprint gets past an address a site has already flagged: Mojeek and Startpage showed a captcha to the development machine from the first request, to the reference library too. DuckDuckGo's html and lite pages are one source (html, then lite when html is broken, never when it is rate-limited: they share one index and one limit). Wikipedia is a *title* search (`generator=prefixsearch` with extracts, disambiguation pages dropped): its full-text search answers a long question with articles that merely share words, and in rank fusion a source's first hit weighs as much as anyone's. Google is not scraped (it needs a JS runtime), nor Bing (it answers a scripted client with unrelated pages). The model picks the language per query (`language`, optional `country`; `region()` fills in the other); `queries` (max 10) is a batch in one call, which is what `silo_runtime.web_search_many` sends. Source tests replace `fetch` and read captured pages in `testdata/`; `SILO_SEARCH_LIVE=1 go test ./internal/search -run 'TestLive$' -v` runs two real searches (`SILO_SEARCH_ONLY=brave` asks one source directly, past its budget: sparingly).

**Dashboard** (`internal/app/dashboard`, `web/src/dashboard/` (the page is `dashboard/Dashboard.tsx`; the question card a thread and the board share is `web/src/ask/`)) is the owner's board per Bot, the top row of the sidebar: **widgets** the Bot keeps current and **asks** it needs decided. **The model writes a widget once and code keeps it current**: `put_widget` (rule `bot.widget_put`) stores a kind, title, size (`s`/`m`/`l` = a quarter, half, the row of a 4-column grid; `rows` 1–2), a `spec` (kind settings plus `actions`) and either pushed `data` or a `probe` — Python that sets `result` — with an interval `every`. `Sweep` (a `tickLoop`, `dashboard.Tick` = 20 s) runs due probes on the box through `Host.RunPython` (a throwaway `ExecPythonCmd` outside any run, 60 s, at most 4 at once, never starts a box, a claimed `next_at` so a slow probe is not started twice); a new probe runs at once inside `put_widget` so the Bot sees its `data` or `probe_error`. Code in a widget (its probe and every `run` action) goes through `AuthorizeAction(python.run)` **once, when it is put**, and only that code runs later (`ApprovedHash` over the probe and actions; a change is a new approval; a rule now at Deny stops it) — no new rule and no approval per refresh. `harness` binds `ARGS`/`STATE`/`DATA` from base64 and reports `result` on a nonce-marked line. `set_widget` (rule `bot.widget_set`) pushes data from any cell with no model and no approval. Kinds are a closed set Silo draws itself (`dashboard.Kinds`: note, stat, chart, list, table, timeline, status, checklist, progress, ideas, app; their data shapes are in SYSTEM.md and `web/src/dashboard/widgets.ts`); an **app** widget is an artifact live app (`artifact` = id or path, resolved at put) in the hatch, loaded on its own origin through `OpenArtifactApp` only once scrolled into view. The owner acts in place: a checklist's checks are widget state (`SetWidgetState`, no run, the Bot reads it in `list_dashboard`); a `run` action executes the stored code with `ARGS` = the row or `{}` (`RunWidgetAction`), may return `{"receipt", "data"}`, re-runs the probe otherwise, and leaves a receipt on the widget; a `hand` action opens a chat quoting the widget as it stood (see **Quotes** under Feed) with the press as the owner's own turn ("I pressed **X** on it."). The page never receives action code (`publicSpec`). The owner owns placement: `ArrangeDashboard` sets `owner_placed`, after which the Bot's `size`/`rows` are ignored. `ListDashboard` also carries the unread Feed posts (shown for the visit as "Since you last looked"; `MarkDashboardRead` reads them, the asks and the changed widgets — `changed_at` vs `seen_at`) and the pinned Dashboard automation's last/next run. **The ask bar** (`AskDashboard`) sends the owner's words, with a picked widget, to the Dashboard automation's log via `automation.Service.Ask` (joins a live run or starts one with the automation origin), so changing the board never adds a chat. **Asks** are the old cards (`DashboardCard`, tools `upsert_dashboard_card`/`remove_dashboard_card`, rules `bot.dashboard_upsert`/`dashboard_remove`): a slip with display blocks and form controls whose submit opens a chat quoting the ask, with the values as the owner's turn ("I chose **X** with: …"); dismissing with "Don't suggest this again" saves a memory. The model touches the board only in its **curator**, `dashboard.Curator`: a pinned automation the dashboard package registers itself (`automation.Service.Pin` in `dashboard.New`; the automation package knows no Dashboard), whose prompt (`prompts/DASHBOARD.md`) is curation, not copying numbers (`Pinned.Replaces` + `UpgradePinned` move bots still on the first prompt). The Feed's posts reach the board through `feed.Service` (`UnreadPosts`, `MarkRead`), never its table, and a chat that quotes the board is `quote.Put` through `Place`, the one way both domains put one (a run that cannot start takes it back). Widget writes name their columns (`dataColumns`, `Select`), never `Save` the row: an approval can wait on the owner while they check items or arrange. A stopped Bot's due probes are moved on (`offlineRetry`) without touching their data or error. `Bot.dashboard_asks` (`dashboard.Service.Open`) is what the sidebar's Dashboard row reads, with the pending approvals, for its Needs you; it never loads the board. `DeleteBot` drops it all (`dashboard.Service.Drop`).

**Feed** (`internal/app/feed`) is the owner's read-only inbox per Bot. The Bot posts markdown with the `feed` chat tool or `silo_runtime.feed` (optional title; both gate on rule `bot.feed`, Allow, inside `feed.Service.Tool`) from any run — chat, automation, or channel — and each `feed_posts` row records its source (kind + chat title / automation name / channel name). `Bot.feed_unread` rides on `GetBot`/`ListBots`, so the polled bot row drives the sidebar badge (a cobalt count; a dot on the narrow chip); opening the Feed calls `MarkFeedRead` and reloads whenever the count moves. Humans cannot post; they can delete (armed) or **Quote** (`QuoteFeedPost`): into the main chat, or a chat of its own titled `Re: …`. **Quotes** are one package shared with the Dashboard (`internal/app/quote`): `quote.Put` writes its one `feed_quote` event in a run of origin `quote` (body = what the model reads as quoted, `tool` = where the Bot made it, `Meta` = `{from: feed|widget|ask|asked, title, widget, card}`), `quote.Text` is the user turn that frames it — and says truthfully what it is: a Feed post, the “X” widget from the Dashboard as it stood (its data as JSON), or the card “X” on the Dashboard; never call a Dashboard thing a Feed post — and `quote.Proto` hands the thread `RunEvent.quoted`, so `Opened` (`thread/Bubbles.tsx`) captions it by kind and draws a quoted widget with `WidgetSnapshot` (the board's body, read-only, no actions) instead of its JSON. An event with no `Meta` is a Feed post's old bytes (append-only). The human's next message folds into the quote's user turn so roles alternate. The Feed keeps the newest 500 posts per Bot.

**Content host & Tunnels** (`internal/app/tunnels`, `internal/tunnel`, `internal/app/artifact/serve.go`) serve Bot-made content on `<kind>-<name>.<content.host>`, dispatched by prefix (`tunnel-`, `app-`, `share-`). A `Tunnel` row is a generated `adjective-colour-animal` name, a port, and `Public`; one per port, 20 per Bot. The CP answers `tunnel-<name>.<content.host>` (`App.Handler` wraps the mux in `Tunnels.Route` and `Artifacts.Route`; every other Host falls through) with one `httputil.ReverseProxy` whose `Transport.DialContext` calls `Hub.DialTunnel`: that queues `Cmd.open_tunnel{conn_id, port}` on the `Commands` stream, the worker dials `127.0.0.1:port` and opens a `BotWorker.Tunnel` bidi stream (first frame names `conn_id` or carries the dial `error`), and both ends wrap their stream in `tunnel.Conn`, a real `net.Conn` (deadlines, partial reads), so keep-alive, SSE and WebSocket upgrades need no special code. Rules that bit: a worker must close **gracefully** (`CloseRequest`, then wait for the CP to end the stream) or it cancels away the last frames of a service that writes and hangs up; the CP handler must not return while a conn's write goroutine is inside `stream.Send` (connect forbids it; the send guard in `App.Tunnel`); a `Conn` copies the caller's slice before sending because its goroutine outlives a write deadline. `tunnel.CheckPort` refuses 5900 (x11vnc) and 9222 (Chromium) on both CP and worker. Config is `content.host`/`content.scheme` and `tunnels.enabled`; with no `content.host`, a local `public_url` derives `localhost:<http_addr port>` (the CP's port, not Vite's: Vite would serve the SPA), anything else is "not configured" (`ListTunnels.state` = `ok`/`off`/`no_host`) and the tools, prompt note and add form disappear. `host` equal to the `public_url` host is refused (a tunnelled app could set cookies for the CP's domain). **Private** tunnels hand off the owner's session: no grant → a page load redirects to `{public_url}/tunnels/auth?name&rd` (the CP session cookie never leaves the CP origin), which (signed out) first redirects to `/signin?next=<the handoff>` — the SPA honors `next` for the `/tunnels/auth` path only, by full navigation (`web/src/signinNext.ts`; anything else is ignored, so it is no open redirect) — then mints a 30 s single-use ticket and redirects to `<name>.<host>/.silo/auth`, which sets the host-only `silo_tunnel` cookie (a `TunnelGrant` keyed by the cookie's hash, 12 h, **bound to the Silo session that made it** and re-checked on every request against that session still being live and the Bot's current owner — so signing out, or the session expiring, ends tunnel access at once; `SignOut` therefore deletes the `Session` row (`auth.EndSession`, which also drops its grants), it is not just a cleared cookie; stripped from the request before the service sees it); an API call without a grant is a 401, never a redirect, and `rd` is only ever a plain path. A tunnel request never starts a box (no worker → 503). The Bot's tools (`open_tunnel`/`list_tunnels`/`close_tunnel`, `silo_runtime.open_tunnel`/…) gate on `tunnels.open|list|close` (Allow) and **`tunnels.public` (Ask)** for anything exposed to people other than the owner, including flipping an existing tunnel; opening an existing port returns it and never downgrades it. The prompt section (`prompts/TUNNELS.md`) is the same for every Bot so it stays in the cached prefix. The Tunnels tab (`/bots/:id/tunnels`) lists, adds, flips Private | Public (`TunnelAccess`, the same segmented control as a rule; going Public on an existing tunnel takes a second click) and deletes (armed); it polls because the Bot can add rows. Admin Settings has a Tunnels & apps section (`content.host`, `content.scheme`, `tunnels.enabled`), and `Settings.content_host` is the effective suffix shown where the field is unset. Changing the suffix re-points every tunnel at once (rows hold only the name).

**Mail** (`internal/app/mailbox`, primitives in `internal/mailin`) gives every Bot a **receive-only** address. It is a feature of the Bot, not a connector: the Email connector (`internal/builtin/email`) is a client of somebody's IMAP/SMTP account and shares no code with it beyond `internal/htmltext`. A `Mailbox` row is a generated `adjective-colour-animal` name (`internal/names`, shared with tunnels), made lazily by `mailbox.Service.Box`; the address is `<name>@<mail.domain>`, so a change of the domain moves every address at once, and `name+tag@` reaches `name`. The CP runs one SMTP listener (`mailin.Listen`, go-smtp's server; `mail.addr`, default `:2525`, the world's port 25 is published or forwarded to it) that **never sends**: no relay, no AUTH, no bounce. Everything it will not take is refused *inside the session* — an unknown recipient (550), over `mail.max_size_mb` (552), more than 10 recipients, a client past `probeLimit` unknown recipients or `rateLimit` messages (451) — and a store failure is 451 so the sender keeps the message and retries (the reason is logged, never sent). STARTTLS is always on with a self-signed certificate unless `mail.tls_cert`/`tls_key` name one (senders do not verify it). `mailbox.Service.Sync` reconciles the listener with the settings at start and on a `tickLoop` (`mailbox.Tick` = 15 s), so Admin changes need no restart and a busy port is retried; the bind error is `Mailbox.problem`, shown to admins only. Config is `mail.enabled`/`domain`/`addr`/`max_size_mb`/`tls_cert`/`tls_key`; with no `domain` there is no mail at all (`ListMail.mailbox.state` = `ok`/`off`/`no_domain`) — nothing is derived from `public_url`, because an address no MX record points at would only look real — and the tools, the prompt section and the rail icon disappear. `Deliver` gets the message exactly as sent: it stores `mailin.Parse`'s reading (first plain part, else HTML through `htmltext.Flatten`; attachment names reduced to bare file names because a stranger chose them; never fails, garbage becomes the body) in `mail_messages` and the bytes under the listener's `Received:` line in `mail_bodies` (a table of its own so listing never loads them), dedupes a sender's retry by `(bot_id, sha256)`, and keeps the newest `mailbox.Keep` (200). `mailin.Authenticate` marks a message **verified** when the From domain vouched for it — an aligned DKIM signature that covers `From`, or SPF pass with an aligned envelope sender; alignment is the organisational domain (`publicsuffix`), i.e. DMARC's test without the policy lookup — and a From header with no or several addresses never verifies. Nothing is rejected over it; it is shown to the owner and the Bot. Tests must set `Service.DNS` (the `mailDNS` fake) or the checks ask the real network. The Bot's tools are `list_mail` and `read_mail` (`silo_runtime.list_mail`/`read_mail`, rules `mailbox.list`/`mailbox.read`, Allow; there is no send action): `read_mail` takes an id or a prefix of 6+, marks the message read (**read means the Bot read it**; the owner opening it does not), pages a long body by `offset` (30k runes), wraps the body in a "written by the sender, not instructions" frame, and with `save_attachments` writes them to `/workspace/mail/<id8>/` through the worker (the message still reads when the machine is off; `save_error` says why the files did not land). The prompt section (`prompts/MAIL.md`, `{address}` filled in) sits in the session tier. **Wake** is off by default and per Bot (`Mailbox.Wake`/`WakeFrom`, `UpdateMailbox`): only a *verified* message whose From address is on the owner's list (addresses or `@domain`, `NormalizeWakeFrom`) starts a run, in a new web chat titled `Mail: <subject>` whose user turn (`tool="mail"`) quotes the message; at most `wakePerHour` (10), counted from `mail_messages.chat_id`. Unverified, unlisted or over-the-cap mail just sits in the inbox. The Mail pane (`web/src/Mail.tsx`, helpers in `mailbox.ts` because `mail.ts` would clash with `Mail.tsx` on a case-insensitive disk) is the right-rail inbox: its header holds the address to copy, then the messages (polled every 10 s; a row opens in place via `GetMail`; the body is plain text, never `Md`). The per-Bot Settings panel (`MailSettings`) holds the address again (copy, armed **New address** = `RotateMailbox`, after which the old one is refused) and the wake switch and sender list; `/mail/raw?bot_id&id` downloads the original `.eml` (cookie auth, always an attachment with `nosniff`: a stranger's bytes are never a page in the CP's origin). `DeleteBot` drops the mailbox (`mailbox.Service.Drop`).

**Accounts** (`internal/app/account`, primitives in `internal/auth`) are who may sign in. `bootstrap.*` makes the first admin and acts at start only while **no enabled admin exists** (`auth.EnsureBootstrap`: promote the user with that email, else create them) — never otherwise, because emails can be changed and whoever holds the bootstrap address later must not be promoted; everyone else comes from an **invite link** (`CreateInvite` → `{public_url}/invite/<token>`, single use, 7 days; the same row with a `UserID` is a 24 h password-reset link). Only the hash of a link's token is kept, so a link is returned once and replaced, never read back. `AcceptInvite` signs a new account in; a reset does not (a second factor still stands) and ends that user's sessions. The public RPCs are a set in `app.go` (`publicRPCs`: `SignIn`, `AuthOptions`, `GetInvite`, `AcceptInvite`); every other one gets the user **and the session** on its context (`access.Session`). **Sessions** are keyed by `ids.Hash(cookie)`, never the cookie (`Migrate` rehashes rows from before, marked by `created_at IS NULL`, with their tunnel grants); they carry user agent, client address and method, `last_seen_at` is touched at most every 5 minutes, and `auth.EndUserSessions` (password change, reset, disable, "sign out everywhere") drops the tunnel grants made from them too. **Email** is the sign-in name, stored lower-cased; a user changes their own with `ChangeEmail`, with no confirmation (Silo sends no mail), which sets `users.email_self_set`. OIDC must never match an account by a self-set email (a user could take a colleague's address and be handed their identity, and their admin group, at the colleague's next sign-in); an admin setting the email (`UpdateUser.email`) clears the flag. A wrong *current* password is `InvalidArgument`, never `Unauthenticated`: the web client reads `Unauthenticated` as the session having ended. **Two-factor** is hand-rolled RFC 6238 (`auth/totp.go`, ±1 step) for password sign-in only: `SignIn` with a right password and no code answers `needs_code` and signs nobody in, and the client resends email + password + code (no pending state on the server). A used time step is stored (`users.totp_step`) and the update is conditional, so a code cannot be replayed or raced; recovery codes are rows of `hash(userID:code)` crossed off the same way. **Throttling** (`auth.Limiter`, in memory) counts failures per account+address (5, then a wait doubling 30 s → 15 min), per address (20 / 15 min) and per account (50 / h), for passwords, codes and invite tokens. The address is `auth.ClientIP`: the connection's peer, unless the peer is in `auth.trusted_proxies`, then the right-most `X-Forwarded-For` hop that is not itself trusted — never read the header anywhere else. **OIDC** is one provider (`oidc.*`; on when issuer and client id are set) behind two plain routes, `/auth/oidc/start` and `/auth/oidc/callback` (go-oidc + PKCE + nonce; the state lives in memory for 10 min and in an HttpOnly cookie so a callback from another browser is refused). A sign-in resolves to the user linked to (issuer, subject); else the user with that email **only if `email_verified`**, not linked elsewhere and not `email_self_set` (linked now); else a new passwordless user when `oidc.auto_create` and `allowed_domains` allow; else nobody. `oidc.admin_group` sets Admin at each sign-in but never demotes the last enabled admin. Failures redirect to `/signin?error=<code>` and the page words the code (`web/src/signinFlow.ts`): never put free text in that redirect. The landing path goes through `access.SafeReturn`. `auth.password=false` is honoured only while OIDC is on (`Config.PasswordSignIn`). The provider's discovery is cached per issuer and the other trailing-slash spelling is tried; `CheckOIDC` (admin) re-discovers and is never `Unavailable`. Tests use the in-memory provider `internal/auth/oidctest`; dev has Dex on `:5556`. **Disable** (`users.disabled`) is `ErrAuth` in `SessionFromRequest`, and `account.Host.SuspendUser` stops that user's Bots (channel workers via `channel.Service.Suspend`, runs and boxes via `haltBot`); while disabled `StartRun` refuses their Bots (`errOwnerDisabled` — automations, channel inbound and subagent wakes all pass through it), `Reconcile` skips their channels, and the tunnel proxy answers 404 even for public tunnels. **Delete** is `DropUserBots`: the Workspaces the user is alone in go with their Bots (`App.dropBot`, the body of `DeleteBot`) and skills, and they are taken off every other one. An admin cannot demote, disable or delete themselves, which is what keeps one admin; do not add a path around that. Columns added to `users` need `not null;default:…` so rows from before are not NULL.

**WhatsApp and Discord** (`internal/channels/whatsapp`, `internal/channels/discord`) have the Telegram shape: one row binds one conversation (`requires_target`), `GUIDE.md`, live-only inbound, `reply_mode` gates groups/servers (DMs always answer). Shared in `internal/channels`: `Chunk` (rune-aware cut at paragraph/line/word that closes and reopens a ``` fence across a split) and `Seen` (bounded id set for redelivery and echoes). `channels.Remover` is an optional adapter hook that `channel.Service.Delete` calls *before* stopping the worker (so `DeleteBot` runs it too); its failure is logged and never blocks the delete. `Host.DatabaseURL()` is for libraries that keep a session in SQL; it carries the password, never log it. **WhatsApp** is whatsmeow as a *linked device* on the owner's account, so the account is the Bot and there are no fields beyond `reply_mode`. The session lives in the CP Postgres (`whatsmeow_*` tables via the pgx `database/sql` driver), not a SQLite file: `CGO_ENABLED=0`, and it is backed up with the rest. A device is found again by the JID the adapter saves in channel state (`Values["jid"]`, published on `PairSuccess` before anything else can fail); a JID with no row (DB reset) pairs fresh. Pairing is a QR (`rsc.io/qr` → PNG data URL in `StateQR`, status `pending_auth` = “Needs linking”) that the library rotates; a timeout does not loop, the run waits for the **Link device** action (`run.relink` is unbuffered on purpose: a press nobody is waiting for is dropped, never remembered). The Setup page adopts the polled state only while it is a pairing state (`qr`/`auth`), because Telegram/Discord publish value-only states that must not replace the picker list under the user. `LoggedOut` (the library has already deleted the device) clears the JID and waits for Link device; `StreamReplaced`/`ClientOutdated`/`TemporaryBan` end the run as errors. Chats are matched by user+server, and a direct chat can arrive as a phone number or a LID: use `SenderAlt` for a message from them and `RecipientAlt` for one the owner sent — never the owner's own alt, or a message to Alice reads as a note to self — then the library's LID→number map. `IsFromMe` is ignored except in the “message yourself” chat, and there the Bot's own sends are ignored too (`client.sent`: the id is remembered *before* `SendMessage`, because the echo can beat its return). Messages older than `liveSince` (start minus 5 s) are dropped: the server delivers an offline queue on connect. Event handlers run one at a time on the library's queue, so a slow one delays every later event: the read receipt and “typing…” go through `client.spawn`. Outbound Markdown becomes WhatsApp markup (`format.go`); files go as image (png/jpeg/webp), video, audio or document by mime (GIF/SVG are documents); inbound media is a `[image]`/`[voice message]` placeholder plus caption, not downloaded; `History` always errors so `chats` reads the local log; `Outbound.ReplyTo` is unused (a quote needs the quoted body). It is the unofficial protocol: GUIDE.md says to use a spare number. `Remove` logs the device out (unlinks it on the phone) and deletes its keys. **Discord** is discordgo: the gateway for inbound, REST for send, history and the picker. The target is a channel id (a `discord.com/channels/…` link or `<#id>` is accepted; ids are numeric snowflakes). A bot, unlike Telegram's, can enumerate: **Pick a channel** lists every text/news channel it can write in across its servers plus the DMs it has seen (kept as `dm:<channelID>` state values, like Telegram peers); **Invite link** builds the OAuth URL (`client_id` is the bot user id). Intents are guilds + guild/DM messages + the privileged Message Content; gateway close `4014` retries without it and runs *limited* (DMs and @mentions only) with a warning in the status, `4004` is a bad token. In a server it answers an @mention or a reply to the bot unless `reply_mode=always`; other bots, webhooks and system messages are ignored. Sends use `allowed_mentions: users only` (a model-written `@everyone` must not page a server), chunk at 1900 runes, and put files (10 per message) on the last chunk. Tests drive the adapters without a network: Discord through a fake `http.RoundTripper` on the session plus direct calls of the inbound handler, WhatsApp through a `waAPI`/`directory` seam over the client and the real dev Postgres for the session store.

**Built-in connectors** (`internal/builtin`, transport `builtin`) are connectors written in Go on the CP: a descriptor declares config fields (`Advanced` ones fold under "More settings"), tools (JSON-schema `Params`, per-action `Mode`), and a `Check` login, and registers from `init()` (blank-imported in `internal/app/connector/builtin.go`). They use the connector engine unchanged — catalog preset (`"builtin": "<key>"`), Workspace connection, cached `ToolsJSON` per grant, `pushTools` stubs, Rules, prompt section — except `refreshTools` runs `refreshBuiltin` and `CallTool` runs `connector.Service.RunBuiltin` instead of an MCP session. Per-action modes are the `AuthorizeAction` fallback (`connector.BuiltinMode`). Config is on the connection (the time zone is the calling Bot's): `ConfigJSON` plain, `SecretsJSON` secret (never returned; a blank secret on update keeps it; library rows hold none). A required field unset is `needs_auth` with a "Fill in …" detail, and the UI shows **Set up** (edit) instead of Authorize. Secrets are masked from results and errors. The descriptor `Prompt` (short, code-owned usage notes; `{slug}` becomes the copy's slug) is appended after the row's catalog prompt in the Connectors section, so it stays current on old copies — keep it terse and show the exact call shape. Tools touch the workspace only through `builtin.Env` (worker `browse_file`/`put_file`; no `..`). **Email** (`internal/builtin/email`) is the first: IMAP via go-imap v2, SMTP via go-smtp, provider presets (Gmail/Outlook skip the Sent APPEND), attachments by index from `read`; `emailtest` runs an in-memory IMAP + capturing SMTP server for tests. **Calendar** (`internal/builtin/calendar`) is CalDAV via go-webdav/go-ical: provider presets or a URL (manual `/.well-known/caldav` redirect — Go drops the PROPFIND body on 301); the home set is read by hand and the session moves to its host (iCloud answers with an absolute `pNN-caldav.icloud.com` URL and its front host returns no events to a REPORT — go-webdav keeps only the path); the event REPORT is hand-built with plain `<calendar-data/>`, hrefs without data are GET, unreadable objects surface as `skipped_unreadable`, and discovery is cached 5 min per account; recurrences expanded client-side (servers treat the time-range filter loosely), timed events written with the zone TZID + generated VTIMEZONE, PUT with `If-None-Match`/`If-Match` itself (`PutCalendarObject` has no preconditions); `caldavtest` serves go-webdav's own handler in memory, and dev Radicale is on `:5232` (`silo`/`silo`).

**Drives** (`internal/drives`, `internal/drivehost`, `internal/app/drive`) mount rclone remotes at `/workspace/drives/<name>`. Providers are an embedded, predefined template library (`internal/drives/catalog/<key>/{drive.yaml,icon.svg,GUIDE.md,SETUP.md}`; no user/admin authoring): one rclone remote plus its questions, with `{{kind.var|filter}}` expressions rendered to `RCLONE_CONFIG_<REMOTE>_*` env. Vars are **user** (the Drives tab), **system** (admin, `drives.providers.<template>.<var>` in silo.yaml, Admin → Drives), or **dynamic** (OAuth token, callback params like pCloud's host, declarative JSON `lookup`s for the account label and pickers). Adding a provider is a new catalog dir; tests pin every template's env and check option names and password obscuring against `testdata/rclone_options.json` (`rclone config providers`). One drive sidecar per Bot (`silo-drive-<bot>`, `driveimage/`, guest `cmd/silo-drive`) holds `/dev/fuse` + SYS_ADMIN and every credential; the Bot gets neither. It dials the CP over `DriveHost.Session` (per-Bot token; hello first), gets a full `DriveApply` on every connect and change, and supervises one `rclone mount` per drive; mounts survive CP reconnects. Mounts reach the Bot by propagation: the sidecar binds `<mount_root>/<bot>` rshared, the Bot binds it rslave at `/workspace/drives`. A privileged throwaway helper (`PrepareDriveDir`, before every sidecar start) makes the root a shared mount inside the engine's namespace (rootless pause process, or pid 1) and labels it `container_file_t` — never `:z` (it would walk live FUSE mounts). Stop the sidecar gracefully (`DropDrive`): a killed rclone leaves dead mounts. An OAuth token travels as `DriveSpec.token` into a private token-only rclone config (env would shadow rclone's refresh write); the guest reports refreshes back and the CP stores them. Drive secrets and dynamic values live on the `drives` row (`SecretsJSON`), never as Secret rows. **A drive is its Workspace's** (`drives.space_id`, names unique per Workspace) and is mounted in the Bots it is granted to (`bot_drives`: per-grant `read_only` — a Bot mounts it read-only when the drive or its grant is — and the grant's mount `state`); `GrantDrive`/`RevokeDrive` give and take (Manage to give, Administer to take), `SaveDrive` from a Bot grants it to that Bot and from the hub (`space_id`) to `bot_ids`, editing or deleting it is whoever added it or a Workspace admin (`canEdit`; delete unmounts it everywhere), and only its lender (`lent_by`, who signed it in) may browse or pick inside its account. A refreshed token is stored once and re-applied to every Bot that mounts it. The Bot's Drives tab lists its grants and the Workspace's other drives (**From the workspace**); the hub's Drives tab (`/w/$spaceId/customize/drives`) holds them all with Choose Bots. The add form keeps a `draft` row for sign-in/test/browse (swept after a day; `drives.bot_id` is only the Bot whose sidecar a draft lists through). `delete` refuses drive roots; a workspace-wide `grep` skips `drives/`. A box made before drives has no bind: the tab asks for a Container reset.

**Time zones** (`internal/zone`, `internal/app/timezone.go`). A Bot's machine is **UTC**, always (`TZ=UTC` in `dockerx.botEnv`), and SYSTEM.md tells the model so; the human's zone belongs to the Bot: `bots.time_zone`, an IANA name. It **follows the owner**: `CreateBot`, `Send` and `EditMessage` carry the device's zone (`deviceZone()` in `web/src/zones.ts`, `TimeZone.current` on iOS) and `App.followZone` moves an unpinned Bot to it before the message is written; `bots.time_zone_pinned` (Settings → Time zone, **Follow my device | Fixed**, `web/src/TimeZone.tsx`) keeps it where the owner put it; the Bot's `silo_runtime.set_timezone` (rule `bot.set_timezone`, Allow) is for a human who says where they are in a channel, which has no device to read. A zone a client sends is never an error on a message: unknown or empty changes nothing. `App.setBotZone` is the one writer (one column, never the whole row) and calls `automation.Service.Rezone`, because cron is wall-clock time in the Bot's zone (`nextRun(au, from, loc)` hands robfig a time in that zone; DST is its business). `zone.Resolve` turns a stored name into a location and never answers `Local`: an unset Bot (from before zones) reads as the server's zone *by name*; `zone.OfBot` asks the database each time, since the zone can move during a run; `zone.Stamp` is the one layout for a time the model reads (`Sun, 2026-10-11 14:30:05 +02:00 Europe/Warsaw`: offset and name). **The zone is frozen on each message**: `run_events.zone` records the Bot's zone when a `user`, `subagent_report` or `feed_quote` event is written, and `replayEvents` stamps it in that zone forever, so a trip never rewrites history (an event with no zone keeps the old server-zone layout byte for byte). For the same reason the zone is never in the system prompt, and the memory dates that sit in the prompt are UTC. Mail, feed and automation times in tool results use the Bot's zone; the Calendar connector falls back to it (`builtin.Config.TimeZone`) when its own field is blank. The web shows every instant in the viewer's device zone; only the schedule editor names the Bot's.

**Automations** are scheduled background prompts (`internal/app/automation`). Each has a name, a prompt, a 5-field cron schedule in the Bot's time zone (see **Time zones**), and an on/off switch; the prompt is sent as the user message of a run through the same engine as chat, with a trailing per-run note (`prompts.AUTOMATION.md`) naming the automation and saying nobody is watching live. Every run starts from a **fresh context** (`historyFromRuns` of just this run, not `historyFromDB`) so the log does not grow with each firing — the prompt must be self-contained and keep state in files/`bot` or memory. The scheduler (a `tickLoop`, `automation.Tick` = 20 s) fires due rows **once**: `automation.Service.FireDue` claims the slot with a conditional `next_run_at` update so two writers cannot both fire, and a firing that lands while the previous run is live is skipped, never queued. `rescheduleAutomations` advances anything missed while the CP was down without backfilling. `parseSchedule` rejects a schedule whose first two firings are under 5 minutes apart (`* * * * *` cannot burn a call a minute), and a Bot has at most 50 automations. Every Bot has one pinned **Heartbeat** (`kind=heartbeat`, created with no schedule so it never fires until given one; cannot be deleted), and one of every other pinned kind a domain registers with `automation.Service.Pin` (an `automation.Pinned`: kind, fixed name, default prompt, the prompts it `Replaces`; the Dashboard's curator is one). `EnsurePinned` makes the missing ones, they list first in registration order, and `Pinned`/`Ask` are how the owning domain reads its row and hands it the owner's words; the partial unique index `automations_pinned` is made from `db.PinnedAutomationKinds` (remade when it misses one), so a new kind is added there too (`TestPinnedKindsAreIndexed`). Each automation owns a hidden `Chat` (`chats.automation_id`) that is its run log: it is excluded from web chat lists and Send/Edit/Diverge/Delete refuse it (`writableChat`); deleting the automation drops the log (`chats.Drop`). Bot tools `list_automations`/`create_automation`/`update_automation`/`delete_automation` sit under the `automations` rule (create/update Ask, list/delete Allow; `update_automation` sets the Heartbeat's schedule). UI: `/bots/:id/automations` list + `/bots/:id/automations/:id` log + `/new` and inline editor; the log renders the shared `Thread` with `userAs="run"` (each run is a "Ran …" divider), and `web/src/schedule.ts` is the schedule picker. Chat and automation logs share `useRunStream`.

**Subagents** (`internal/app/subagents.go`) are background agent loops a chat's lead starts with `spawn_agent` (name, goal, context, optional allowlisted model — default `model_subagent` when set and allowed, else the lead's model; rules `agents.*`, Allow). Subagents keep their own trimmed tool list: the prompt cache is per model and siblings spawn in parallel, so matching the lead's tools would not buy cache hits. The prompt tells a lead to end its turn after spawning rather than `sleep`, since every wake from `sleep` is a full turn. Like an automation, each owns a hidden log `Chat` (`chats.subagent_id`; excluded from web chat lists, `writableChat` refuses it) and runs through the same engine from a **fresh context** (its history is only its own log; the brief and later `message_agent` texts are `user` events with `tool="lead"`). A subagent run gets the tool list minus the `LeadOnly` definitions (no agent tools, `task_reset`, `channel`, `switch_model`, automations) and the trailing `prompts/SUBAGENT.md` note. Depth is 1; at most 8 run at once per lead chat. **Waking:** a subagent's `finish` stores its result (`runResult`: the last model turn's text) with `reported=false`, nudges the lead's live run (`liveRun.wake`, which `sleep` selects on; `inject` nudges it too), and `scheduleWake` (debounced) calls `wakeLead`: if the lead chat has no live run it marks the finished results reported and starts a lead run that opens with a persisted `subagent_report` event (Tool `name:status,…`), replayed as a framed user turn. A running lead inspects on its own; a lead run that ends `done`/`error` with unseen results wakes once (no loop: the report marks them seen). Automation logs are never woken. Stops the lead already knows about (its Stop — `StopRun` cascades via `stopSubagents` — `stop_agent`, Stop Bot) go through `quietSubagents` first so they do not wake it; a human `StopSubagent` does. `DeleteChat` drops the lead's subagents and board. **Taskboard:** `task_items` rows per lead chat, shared with its subagents (`boardChat`); `task_add` parses a leading `[NAME]` into the assignee; a subagent cannot reset. The board and the lead's subagent states are told as a `note` turn **when they change** (`turnNote`), and stay in history like any other turn (see Context is append-only). Board and subagent changes publish transient `board`/`subagents` bus pings (no id; `useRunStream` hands them to `onPing`, not the thread). Runs are capped by `runs.max_duration` (default 120m, `-1` unlimited; `runContext`). UI: `Taskboard` strip above the lead thread, `SubagentTray` between thread and composer (running cards + "N finished"), and `/bots/:id/run/:chatId/agent/:agentId` is the read-only `SubagentPage` (shared `Thread`, Brief, Stop; its lead chat stays lit in the sidebar).

**Other people's bytes in our origin** (pinned by `feature_hardening_test.go`). The console's origin is where a signed-in owner's cookie works, so nothing a Bot, a sender or another user wrote may act as a page there. `/artifacts/file` opens in place (`inline=1`) only a type that cannot script (`workspace.Passive`: raster images, PDF, audio, video, plain text); HTML, SVG and anything unknown is always an attachment, and `workspace.Untrusted` adds `nosniff` and a sandbox policy. The preview overlay reads the bytes with `fetch`, so it never needed the page. A connector's mark is an image by its **bytes** (`connector.imageType`; the upload's claimed type is not believed, and `ServeImage` asks the bytes again for rows from before the check). HTML made from a document (`DocxView`, mammoth does not clean links) goes through `web/src/safeHtml.ts`. `/vnc` and `/console` check the `Origin` themselves (`socketOrigin`: the request's host or `public_url`; none at all is a native client): CORS does not hold a WebSocket back and a tunnelled app on a sibling subdomain is same-site, so the cookie alone is not the gate. A connector's OAuth callback finishes only in the browser of the user who started it (`oauthWait.user`; a refusal does not spend the state), since the authorize link can be sent to anyone; drives are not bound, because the iOS flow ends in Safari. **A library preset's header values, STDIO environment and OAuth client secret are the operator's**: a Bot's copy keeps them only while it talks to what the preset talks to (`sameTarget`: same URL, or same command, arguments and image); re-pointing a copy, or creating one already pointed elsewhere, keeps only what that request supplied (`keepOnlyGiven`). **`auth.host_cookie`** (off by default; `Config.HostCookies()`, which is true only while `public_url` is https, since a browser drops a `__Host-` cookie set over http and nobody could sign in) is for tunnels under Silo's own registrable domain (`silo.example.com` + `*.tunnels.example.com`): any host under `example.com` can plant a `silo_session` for the parent domain and sign a visitor into another account, but none can set a `__Host-` one. On, the session is `__Host-silo_session` and the OIDC round trip `__Host-silo_oidc` (`Path=/`, as the prefix demands), and **the plain names are never read**: every `auth.SessionFromRequest`/`UserFromRequest`/`EndSession` takes `hostOnly` from the config, so a new cookie-authed route cannot forget it. Flipping it signs everyone out once; `ClearSession` clears both names. STDIO sidecars share an npm directory per Bot (`data/bots/<id>/mcp-npm`, `dockerx.stdioCacheDir`), never across Bots: npx runs what is in `~/.npm/_npx`, and a sidecar runs its owner's choice of package as root.

**Outbound connections** (`internal/netguard`, `config.Outbound`, `Config.OutboundPolicy()`). Some connections the control plane makes itself to an address **a user typed**, and it sits on the operator's network. `outbound.block_private` (off by default; `outbound.allow` lists IPs/CIDRs, each optionally with one port, that stay reachable) refuses internal addresses for exactly those: an HTTP connector's URL (`mcpx.Dial.Base`) and the OAuth endpoints its server names (`AuthorizationCodeHandlerConfig.Client`), the Email and Calendar connectors (`builtin.Config.Net`, which every dial and HTTP client in a built-in must go through), a skill's download (`skills.InstallURL` takes the client) and a drive provider's sign-in (`drive.Service.httpClient`: pCloud's API host arrives as a callback parameter). The check is `net.Dialer.Control`, on the literal address being connected to: after DNS, so a name resolving inside, a redirect leading inside and DNS rebinding are all the same refusal; never check a hostname before dialing instead. `netguard.Internal` judges an IPv6 address that carries an IPv4 one (mapped, NAT64, 6to4) by the one inside. **The operator's own targets are exempt** (`connector.Service.outbound`/`operatorTarget`): a library preset, or a Bot's copy that still points where its preset points (`sameTarget` on both sides resolved), connects unrestricted, which is what keeps Lightpanda on localhost working; re-pointed, it is the user's word again. Not covered, on purpose: model providers, search, OIDC (the operator's), and what a Bot's box or a sidecar reaches (that is the container network). A new feature that connects somewhere a user names takes its dialer or client from `OutboundPolicy()`.

After create, never `docker exec`, `docker cp`, or a published VNC port.

Container ID in the DB is the last box. `GetBot`/`ListBots` inspect Docker (and the `silo-{id}` name) and clear a vanished box. `StartBot` starts that ID if it still exists; it creates only when there is no ID or the box is gone. Do not trust a stored ID after a `podman rm`.

# Dev

## Commands

`make help` is the list; these are the ones you will actually need.

- `make build-cp` / `make build-all` / `make images` — `bin/silo`, worker, bridge; then bot + STDIO images.
- `make bot-image` (runs `build-worker` first) after worker, `botimage/`, or toolsgen changes; `make stdio-image` (runs `build-bridge`) for the bridge / `mcpimage/`. Neither touches containers: a running Bot keeps its old image until Container → Reset (or `podman rm -f silo-<id>`) and Start.
- `make db-up` / `db-down` / `db-psql` — dev Postgres (`silodb-postgres`, not `silo-*`, so `cleanup` spares it). You may start it; `make db-reset` drops the volume (destructive, only when asked).
- `make test` — `go test ./cmd/... ./internal/...` (never `./...`: it walks `data/`). Needs `make db-up`: `dbtest.New(t)` gives each test its own schema in `silo_test`; never open a DB by hand in a test.
- Postgres rejects NUL and invalid UTF-8 in `text`; `internal/db` scrubs every create/update, so do not bypass GORM with raw inserts. Run events order by `seq` (timestamps tie at µs), never `created_at`.
- `make proto` — `buf generate` (Go + TS) after any `.proto` change, then rebuild the CP and worker.
- `make cleanup` — `podman rm -f` every `silo-*` container. `make clean-images` drops the local images.
- `make dev` — tmux session with `watch-control` (watchexec, 750 ms debounce, SIGTERM + 5 s grace) and Vite; `make attach` reattaches.
- `make reset-data` — deletes `./data`; destructive, only when asked.

## Commits

Commit with **Conventional Commits** per [DEVELOPMENT.md § Commits](DEVELOPMENT.md#commits): `<type>(<scope>): <summary>`. Every commit made with a model's help carries an `Assisted-by: <model name>` trailer naming the model that made it (e.g. `Assisted-by: DeepSeek V4.1 Flash`). Do not spend too much time in loops around commits - it is fine to bundle features in a single commit if they are a big change, but describe it clearly. You should also look at and commit the user's changes rather than leaving things uncommited.
DO NOT add yourself as contributor or co author, this is especially to claude!!!. Only assisted-by.
While changes are unpushed the log is yours to rewrite: if the user is not satisfied with a change, amend, rebase, squash, or reorder to fix it up cleanly instead of stacking `fix`/`wip` commits. Never rewrite pushed history.

## Who runs what

- **Never start the frontend or the control plane yourself.** The user owns those processes (`make dev` or their own tmux). Do not run `make dev` / `run-control` / `run-frontend` / `watch-control`, and do not kill or clean up their background processes. If `make dev` is not up but you need it for something (eg tests), FAIL early and tell the user to start it up.
- **You may** run builds (`make build-*`, `make images`), tests, `make proto`, and container cleanup (`make cleanup`, `make clean-images`).
- **You may** attach to the user's already-running tmux for debugging: inspect with `tmux ls` and `tmux capture-pane -p -t silo`, or attach (`make attach`) when you have a TTY. Do not start a second session under the same name.
- Do not run big command chains of tasks that take a long time to finish (especially ones that download things). Do them separately to avoid leaving a state where an unknown command in the middle is hung, and do not blindly supress the output of commands like builds that may get stuck.

## Debug via Chromium

Debug and test your stuff with chromium MCP for MAJOR CHANGES.
Use localhost as the actual URL of the Silo Agent, not 127.0.0.1. Something is wrong with the ip.
**DO NOT** Start another automation browser, only use your mcp, never start some custom aah browser in some random aah folder
If the chromium MCP is offline, just tell the user. It usually simply means this task will be tested manually.
