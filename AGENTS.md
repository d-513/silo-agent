# Silo Agent

Token-conserving multi-user agent. Each **Bot** is a durable container with a GUI. Architecture: `docs/Description.md`. UI: `DESIGN.md`.

How to build and run: [DEVELOPMENT.md](DEVELOPMENT.md). The DB is Postgres 17 + pgvector (`database_url`, default the dev compose on `localhost:5433`); `docker-compose.dev.yml` runs only Postgres, never the CP. `Makefile` is the command surface — `make help` lists every target. Never start the dev servers yourself; see Dev below.

Operator config: [docs/CONFIGURATION.md](docs/CONFIGURATION.md). Koanf **defaults → `silo.yaml` → `SILO_*` env**. Nested keys use `__` (`SILO_PROVIDERS__OPENROUTER__API_KEY` → `providers.openrouter.api_key`). Admin Settings edits `silo.yaml` (form + YAML editor). Env still wins; the UI warns and disables those fields. Providers carry `api_key`/`base_url`/`cache`/`cache_ttl`; `local` is any self-hosted OpenAI-compatible server (required `base_url`, optional key; Silo never hosts models); `models` is the allowlist, `model` the default (`provider/model`), `model_title` the title model. `providers.openrouter.ignore` (default `DeepInfra`) is sent as OpenRouter `provider.ignore`: some upstreams buffer tool-call arguments into one final chunk, which kills the live `tool_args_chunk` stream of exec_python/terminal/write input. Default model when unset: `openrouter/openai/gpt-5.6-luna`. Default search engine when unset: `duckduckgo_scraper`.

The project should follow test-driven-development. For now end to end testing is not yet to be fully implemented, but the unit tests in Go should test as much as possible using the dummies.

## Shape

- **Control Plane (Go):** users, bots, secrets, skills (bodies on `data/skills/`; enablement in Postgres; `ListSkillFiles`/`ReadSkillFile` walk the CP volume, no worker), **security engine** (`internal/security` — catalog of connector.action → title/fields/default; `*` for files/desktop; each secret is `secrets.<name>` not `secrets.get`; unknown MCP actions get a generic prompt), **HTTP MCP client** (`internal/mcpx` — streamable HTTP over a URL or an injected transport), **STDIO MCP sidecars** (one isolated container per attached STDIO connector; `silo-mcp-bridge` **dials the CP** over ConnectRPC `MCPHost.Tunnel` with a per-attachment bridge token and raw-pumps JSON-RPC to its child; curated image or generic Node/`npx` command; structured argv, never a shell; no published port), **agent loop** (the modular `internal/llm` engine: providers `openrouter`/`openai` speak the OpenAI-compatible API, `anthropic` the native Messages API; model ids are `provider/model`; operator allowlist `models`, default `model`, chat override `chats.model`; the system prompt is a base `SYSTEM.md` plus ordered session providers in `internal/app/systemprompt.go` — connectors, skills, channels, then SOUL/CORE MEMORY and the per-run channel note; blocks are ordered stable→volatile with provider cache breakpoints; bots get `list_models`/`switch_model` under the `model` rule), **web search** (`internal/search` — engine registry on the CP; `web_search` chat tool and `silo_runtime.web_search` share `web.search`; MCP stays Python-only), Docker lifecycle = create/start/stop/inspect only (bots and STDIO sidecars). Chat tools and Python `CallTool`/`GetSecret` share `authorizeAction`. Approval slip never dumps `args_json` (and redacts `desktop.type` text). `allow_once` is a valid vote. Connector tokens and extra headers stay on the CP. Reserved connector slugs: python, terminal, files, desktop, bot, secrets, skills, web, artifact, channels, chats, model, automations, agents, tasks. **Channels** are built-in adapters (`internal/channels`, Telegram via gotd MTProto) that talk to a Bot. One adapter instance is a `Channel` row (per bot, unique name); channel conversations are `Chat` rows tagged `channel_id`+`external_id` (web chats keep `channel_id=''`). Adapters own config (per-channel secrets live as `channel.<id>.<key>` Secret rows, hidden from the Secrets tab and `secrets.*`), dynamic state (`State`: info/QR/select for QR logins and chat pickers), and lifecycle. The Channels tab adds/edits them from adapter-declared fields, with sub-routes `/bots/:id/channels[/new[/:adapter]|/:channelID[/setup]]` so browser back works; `requires_target` adapters (Telegram) bind the row to exactly one chat picked in the Setup menu (`set_target` → `external_id`/`target_title`), and only that chat is read or written. Telegram bot accounts cannot enumerate dialogs (`messages.getDialogs` → `BOT_METHOD_INVALID`), so the picker lists chats the bot has seen (persisted in channel state) and accepts a manually entered `@username`/`t.me` link/id. Adapters declare interactive `Setup` actions (`pick`/`run`/`qr`) and an embedded `GUIDE.md`; a channel that still needs its target shows a blinking **Set up**. The `chats` tool asks the adapter for a channel conversation's history (Telegram `messages.getHistory`) so the Bot can see older messages; bot accounts are refused (`BOT_METHOD_INVALID`), so it falls back to the local run log (adapter flags `noHistory` per channel and stops retrying). `present`/`artifact` on a channel attach the real bytes (`workspaceAttachment`; a skill directory is zipped by `skillZipAttachment`), and the Telegram adapter uploads them with `uploader.FromBytes` + `.File`. A channel with `inbound=false` is send-only (tools only). Channel workers start from `reconcileChannels`; adapter `Start` is live-only — never backfill missed messages. The `channel` chat tool sends (default the origin channel; rule key `channels.<channelID>`); `chats` reads history through the adapter for channel conversations and the DB for web chats (rule `chats.read`); `silo_runtime.send_channel`/`read_chats`/`feed` are the Python paths. Python and chat tools should be roughly equivalent for any action that is not chat-only: each built-in shares one function that authorizes inside it (`channelSendTool`, `chatsReadTool`, and `runShared` in `internal/app/builtins.go`) and `callBuiltin` routes the Python `call` to it. `sharedTools` maps chat tool → `connector.action` for `feed`, `remember`/`recall`/`forget`, the four automation tools, the four taskboard tools, and `list_models`; add a new non-chat-only tool there and give it a `silo_runtime` helper. Python gets JSON where the chat tool gets prose (`recall` → `{memories: [...]}`). Chat-only: `soul`, `core_memory`, `switch_model`, the agent tools (`spawn_agent`/`agent_status`/`message_agent`/`stop_agent`), and `sleep`. `artifact` is one engine: the chat tool and Python `silo_runtime.artifact`/`CallTool` share `artifact.emit`, `describeArtifact` turns a dir-with-`SKILL.md` into a skill card or any file into a downloadable card, and `/artifacts/skill.zip` + `/artifacts/file` stream the bytes (cookie auth).

Desktop is the hatch only. A connected worker is **online** (pine lamp), not idle. The CP holds the VNC and Console streams until a viewer attaches, then the Worker dials x11vnc or opens a PTY. Each hatch/console WebSocket gets a viewer ticket; closing an old socket must not clear a newer one (React Strict Mode remounts the hatch). VNC and console are separate lanes — both can stay up. Replacing a worker session must cancel any waiter on the old session. Sign-in must call `setSession` from the response (email + admin) or the session cookie is ignored. `StreamRun` persists every event, replays history, and accepts `after_event_id` so the client can reconnect without duplicates. Every string that is persisted or emitted is normalized to valid UTF-8 and capped on rune boundaries: a single invalid byte in a `RunEvent` makes protobuf replay fail, and the client then spins on an open run forever (surviving restarts) because it never sees the `done`. Interrupted runs get a synthetic `done` in `recoverOrphans`. Chat Stop is `StopRun` (that chat’s live run + worker `CancelCmd`); it is not Stop Bot. Commands carry `run_id`; children get `SILO_RUN_ID`. The model ends a user-visible block with `<section_send />`; that finalizes a `section` event (its own chat bubble) and delivers it on a channel. If a message arrives while the box is down, the run starts the container and worker-backed tools wait (`waitWorker`) for the worker to connect. `startRun` always calls `ensureRunning`, which confirms the box with Docker even when a worker session exists — a session can outlive a container removed out of band, and trusting it would leave the Bot unreachable. Bot status is derived from remaining running runs and pending approvals. A stopped box keeps its ID. Stop is `docker stop`, not rm. `ResetContainer` is stop+rm and clears the ID. Persist a new token hash only after Create succeeds; a failed recreate plus `live()` adopting the leftover box is what makes the worker hammer 401s. Worker auth misses and rule lookups (no row = catalog default) use `Find`, not `First` — GORM `record not found` is not an error log. Desktop processes are fail-fast: if Xvfb/Openbox/x11vnc/worker dies, the container exits and `unless-stopped` recreates it. Chromium is a dock launcher (`silo-chromium`), not a supervised process. Chrome profile bind is `/home/silo/chrome-profile`. The wrapper is `--enable-low-end-device-mode` + 128MB disk cache + `--load-extension=/opt/silo/ubol`; site isolation stays on — do not launch raw `chromium`. Do not also Chrome-Web-Store force-install uBOL (that duplicates it). Managed policy sets page zoom to ~67% and uBOL lists (ads + cookie/overlay). If `exec_python` mentions Playwright / `chrome_page` and :9222 is down, the worker starts headed `silo-chromium` on `DISPLAY=:1` (not a start.sh child). Connectors are discovered as `import tools` in `exec_python`, not as extra OpenAI tools. Those calls emit `call` / `call_result` and render above the Python fold. ## Two hops

1. **CP ↔ Worker:** ConnectRPC, Worker-initiated, bot token. Concurrent RPCs.
2. **Python ↔ Worker:** HTTP/JSON on `unix:///var/run/silo/worker.sock`.

File tools stay five: `read` (numbered lines; the Worker slices `offset`/`limit`, rejects binaries, and returns `next_offset`; displayed `N|` is the file's absolute line number), `write`, `patch` (exactly one `old_text` match), `delete` (recursive `Cmd_Remove`, refuses the workspace root), `grep` (ripgrep-only, `include` glob, `max_hits` cap, deterministic `--sort path`, heavy dirs pruned; runs without the shell so it emits no `tool_chunk`). A repeat guard short-circuits a 3rd identical `read`/`grep` in a run and resets on any mutating tool. Do not add a sixth unless a real loop needs it. `present` is a chat tool on the CP (shows a workspace file in the thread via `browse_file`); it is not a fifth worker file tool. A presented image is also attached as pixels on the next model turn so Chromium work can Perceive → Reason → Act → Verify — do not oneshot cookies+search with guessed labels. Scratch lives in `/workspace/bot`; user-facing files in `/workspace`. Chat uploads go to `/workspace/tmp` via the composer paperclip (ConnectRPC `PutFile`, 50 MB cap), carried as a `RunEvent.attachments` list persisted in `RunEvent.Meta`; `start.sh` wipes `/workspace/tmp` on every container start, session_start etc, so it is input only. The model is told the paths in `historyFromDB`; it chooses to `read`/`present`. `present` asks `browse_file` for up to 32 MB (worker `presentLimit`), while the Files tab previews at 2 MB (`browseLimit`) and uploads cap at 50 MB (`putLimit`). `present bot/…` is a collapsed “Looked at …” row, not a folio. The Files tab is a human browser (`mkdir` / `remove` / `put_file` / `browse_file` on the worker). Recreate the box after those worker cmds change.

Long-term memories are pgvector rows (`memories`, `vector(1536)`, per bot) behind `remember`/`recall`/`forget` (rules `bot.*`, default allow); `embedding_model` must be OpenAI-compatible (`llm.Embedder`; Anthropic cannot embed), and auto-recall puts close matches in the trailing prompt block once per run — never above a cache breakpoint. Vector `ORDER BY` goes through `Clauses(clause.OrderBy{Expression: …})`: GORM silently drops `Order(clause.Expr)`. SOUL and CORE MEMORY live in Postgres (`bots.soul` / `bots.memory`), not on the box. Injected into the system prompt every run. Tools `soul` and `core_memory` (rule `bot.core_memory`; `Migrate` renames old `bot.memory` rules) write the DB (no worker hop). Model may write both; Settings edits SOUL, the Memories page edits CORE MEMORY. CORE MEMORY cap is 8000 chars — over that the prompt and the tool tell the model to compact, they do not silent-truncate. ListBots omits the bodies; GetBot/UpdateBot include them.

**Memory collector** (`internal/app/collect.go`, prompt `prompts/MEMORY.md`) saves what the Bot forgot to `remember`. It reads a chat's events after its watermark (`chats.memory_seq`, a `run_events.seq`) as a flat transcript (tool output capped short, failures kept longer), and one tool-less completion with `model_memory` (default: the title model) answers JSON `save` (`kind` `fact`|`lesson`) / `update` / `forget`. The model is shown CORE MEMORY plus the 15 closest existing memories, and may `update`/`forget` only those ids. Saves go through `saveMemory` (the `remember` dedupe). The watermark advances after a read, including an unreadable reply, but never on a provider/embed error, so every event is read once. Chats older than the column start at their newest event (`Migrate`). The sweep (`memoryLoop`, 5 min tick, `memory.collect`) reads web and channel chats (never automation or subagent logs) whose newest new event is over 10 min old and that have no live run, at most 5 per tick, and pauses 15 min after a provider error. A delta over 12k tokens is split into at most 3 calls and the oldest excess dropped. The composer's brain button (`MemoryCollect.tsx`, `CollectMemories` RPC) runs it now for one chat. Memories carry `kind` and `chat_id`; recall marks lessons.

**Compaction** (`internal/app/compact.go`) keeps a conversation inside the model's context window. The window is `context.windows` (per-model override) → the provider's `llm.ContextWindower` (OpenRouter `/models` `context_length`, cached 6 h) → `context.window`. Before each turn `runLoop` takes the last turn's provider usage plus an estimate of what was appended (runes/3.5; the whole request on a run's first turn) and, at `context.compact_at` of the window, summarizes the history with the chat model (`prompts/COMPACT.md` over a flat, front-trimmed transcript) — mid-run too, with a continue note. A provider context-length error compacts once and retries the turn. A compaction is a persisted `compaction` event (body = summary, `tool` = auto/manual, `Meta.after` = last summarized event), opened by a `compacting` event; the thread keeps every event and `historyFromEvents` replays the last summary then only events after its anchor (so a message injected while the summary was written survives), folding the next user turn into it. Diverge remaps the anchor. Usage events carry `window`; the composer's context meter (ring + %) shows it and its click is `CompactChat` — a manual compaction run (origin `compact`, no user event) refused while a reply runs, for channel chats, or when the history is already just a summary; a message sent during it is injected and answered after. Never compact by deleting events.

**Feed** (`internal/app/feed.go`) is the owner's read-only inbox per Bot. The Bot posts markdown with the `feed` chat tool or `silo_runtime.feed` (optional title; both gate on rule `bot.feed`, Allow, inside `feedTool`) from any run — chat, automation, or channel — and each `feed_posts` row records its source (kind + chat title / automation name / channel name). `Bot.feed_unread` rides on `GetBot`/`ListBots`, so the polled bot row drives the sidebar badge (a cobalt count; a dot on the narrow chip); opening the Feed calls `MarkFeedRead` and reloads whenever the count moves. Humans cannot post; they can delete (armed) or **Quote** (`QuoteFeedPost`): a new web chat titled `Re: …` whose only run holds one `feed_quote` event (body = post, `tool` = source label). The thread renders it as the shared `Md` in a quote card; `historyFromRuns` turns it into a user turn that frames the post and folds the human's next message into that same turn so roles alternate. The Feed keeps the newest 500 posts per Bot.

**Built-in connectors** (`internal/builtin`, transport `builtin`) are connectors written in Go on the CP: a descriptor declares config fields (`Advanced` ones fold under "More settings"), tools (JSON-schema `Params`, per-action `Mode`), and a `Check` login, and registers from `init()` (blank-imported in `internal/app/builtinconn.go`). They use the connector engine unchanged — catalog preset (`"builtin": "<key>"`), per-Bot copy, cached `ToolsJSON`, `pushTools` stubs, Rules, prompt section — except `refreshTools` runs `refreshBuiltin` and `CallTool` runs `runBuiltin` instead of an MCP session. Per-action modes are the `authorizeAction` fallback (`builtinMode`). Config is on the Bot's copy: `ConfigJSON` plain, `SecretsJSON` secret (never returned; a blank secret on update keeps it; library rows hold none). A required field unset is `needs_auth` with a "Fill in …" detail, and the UI shows **Set up** (edit) instead of Authorize. Secrets are masked from results and errors. The descriptor `Prompt` (short, code-owned usage notes; `{slug}` becomes the copy's slug) is appended after the row's catalog prompt in the Connectors section, so it stays current on old copies — keep it terse and show the exact call shape. Tools touch the workspace only through `builtin.Env` (worker `browse_file`/`put_file`; no `..`). **Email** (`internal/builtin/email`) is the first: IMAP via go-imap v2, SMTP via go-smtp, provider presets (Gmail/Outlook skip the Sent APPEND), attachments by index from `read`; `emailtest` runs an in-memory IMAP + capturing SMTP server for tests. **Calendar** (`internal/builtin/calendar`) is CalDAV via go-webdav/go-ical: provider presets or a URL (manual `/.well-known/caldav` redirect — Go drops the PROPFIND body on 301); the home set is read by hand and the session moves to its host (iCloud answers with an absolute `pNN-caldav.icloud.com` URL and its front host returns no events to a REPORT — go-webdav keeps only the path); the event REPORT is hand-built with plain `<calendar-data/>`, hrefs without data are GET, unreadable objects surface as `skipped_unreadable`, and discovery is cached 5 min per account; recurrences expanded client-side (servers treat the time-range filter loosely), timed events written with the zone TZID + generated VTIMEZONE, PUT with `If-None-Match`/`If-Match` itself (`PutCalendarObject` has no preconditions); `caldavtest` serves go-webdav's own handler in memory, and dev Radicale is on `:5232` (`silo`/`silo`).

**Drives** (`internal/drives`, `internal/drivehost`, `internal/app/drives*.go`) mount rclone remotes at `/workspace/drives/<name>`. Providers are an embedded, predefined template library (`internal/drives/catalog/<key>/{drive.yaml,icon.svg,GUIDE.md,SETUP.md}`; no user/admin authoring): one rclone remote plus its questions, with `{{kind.var|filter}}` expressions rendered to `RCLONE_CONFIG_<REMOTE>_*` env. Vars are **user** (the Drives tab), **system** (admin, `drives.providers.<template>.<var>` in silo.yaml, Admin → Drives), or **dynamic** (OAuth token, callback params like pCloud's host, declarative JSON `lookup`s for the account label and pickers). Adding a provider is a new catalog dir; tests pin every template's env and check option names and password obscuring against `testdata/rclone_options.json` (`rclone config providers`). One drive sidecar per Bot (`silo-drive-<bot>`, `driveimage/`, guest `cmd/silo-drive`) holds `/dev/fuse` + SYS_ADMIN and every credential; the Bot gets neither. It dials the CP over `DriveHost.Session` (per-Bot token; hello first), gets a full `DriveApply` on every connect and change, and supervises one `rclone mount` per drive; mounts survive CP reconnects. Mounts reach the Bot by propagation: the sidecar binds `<mount_root>/<bot>` rshared, the Bot binds it rslave at `/workspace/drives`. A privileged throwaway helper (`PrepareDriveDir`, before every sidecar start) makes the root a shared mount inside the engine's namespace (rootless pause process, or pid 1) and labels it `container_file_t` — never `:z` (it would walk live FUSE mounts). Stop the sidecar gracefully (`DropDrive`): a killed rclone leaves dead mounts. An OAuth token travels as `DriveSpec.token` into a private token-only rclone config (env would shadow rclone's refresh write); the guest reports refreshes back and the CP stores them. Drive secrets and dynamic values live on the `drives` row (`SecretsJSON`), never as Secret rows. The add form keeps a `draft` row for sign-in/test/browse (swept after a day). `delete` refuses drive roots; a workspace-wide `grep` skips `drives/`. A box made before drives has no bind: the tab asks for a Container reset.

**Automations** are scheduled background prompts (`internal/app/automations.go`). Each has a name, a prompt, a 5-field cron schedule in the CP's local time, and an on/off switch; the prompt is sent as the user message of a run through the same engine as chat, with a trailing per-run note (`prompts.AUTOMATION.md`) naming the automation and saying nobody is watching live. Every run starts from a **fresh context** (`historyFromRuns` of just this run, not `historyFromDB`) so the log does not grow with each firing — the prompt must be self-contained and keep state in files/`bot` or memory. The scheduler (`automationLoop`, 20 s tick) fires due rows **once**: `FireDueAutomations` claims the slot with a conditional `next_run_at` update so two writers cannot both fire, and a firing that lands while the previous run is live is skipped, never queued. `rescheduleAutomations` advances anything missed while the CP was down without backfilling. `parseSchedule` rejects a schedule whose first two firings are under 5 minutes apart (`* * * * *` cannot burn a call a minute), and a Bot has at most 50 automations. Every Bot has one pinned **Heartbeat** (`kind=heartbeat`, created with no schedule so it never fires until given one; cannot be deleted). Each automation owns a hidden `Chat` (`chats.automation_id`) that is its run log: it is excluded from web chat lists and Send/Edit/Diverge/Delete refuse it (`writableChat`); deleting the automation drops the log (`dropChat`). Bot tools `list_automations`/`create_automation`/`update_automation`/`delete_automation` sit under the `automations` rule (create/update Ask, list/delete Allow; `update_automation` sets the Heartbeat's schedule). UI: `/bots/:id/automations` list + `/bots/:id/automations/:id` log + `/new` and inline editor; the log renders the shared `Thread` with `userAs="run"` (each run is a "Ran …" divider), and `web/src/schedule.ts` is the schedule picker. Chat and automation logs share `useRunStream`.

**Subagents** (`internal/app/subagents.go`) are background agent loops a chat's lead starts with `spawn_agent` (name, goal, context, optional allowlisted model — default `model_subagent` when set and allowed, else the lead's model; rules `agents.*`, Allow). Subagents keep their own trimmed tool list: the prompt cache is per model and siblings spawn in parallel, so matching the lead's tools would not buy cache hits. The prompt tells a lead to end its turn after spawning rather than `sleep`, since every wake from `sleep` is a full turn. Like an automation, each owns a hidden log `Chat` (`chats.subagent_id`; excluded from web chat lists, `writableChat` refuses it) and runs through the same engine from a **fresh context** (its history is only its own log; the brief and later `message_agent` texts are `user` events with `tool="lead"`). A subagent run gets the tool list minus `leadOnlyTools` (no agent tools, `task_reset`, `channel`, `switch_model`, automations) and the trailing `prompts/SUBAGENT.md` note. Depth is 1; at most 8 run at once per lead chat. **Waking:** a subagent's `finish` stores its result (`runResult`: the last model turn's text) with `reported=false`, nudges the lead's live run (`liveRun.wake`, which `sleep` selects on; `inject` nudges it too), and `scheduleWake` (debounced) calls `wakeLead`: if the lead chat has no live run it marks the finished results reported and starts a lead run that opens with a persisted `subagent_report` event (Tool `name:status,…`), replayed as a framed user turn. A running lead inspects on its own; a lead run that ends `done`/`error` with unseen results wakes once (no loop: the report marks them seen). Automation logs are never woken. Stops the lead already knows about (its Stop — `StopRun` cascades via `stopSubagents` — `stop_agent`, Stop Bot) go through `quietSubagents` first so they do not wake it; a human `StopSubagent` does. `DeleteChat` drops the lead's subagents and board. **Taskboard:** `task_items` rows per lead chat, shared with its subagents (`boardChat`); `task_add` parses a leading `[NAME]` into the assignee; a subagent cannot reset. The board and the lead's subagent status ride on the **last message of each request only** (`withTurnNote`), never in stored history, so the model sees only the latest version and cache breakpoints stay ahead of it. Board and subagent changes publish transient `board`/`subagents` bus pings (no id; `useRunStream` hands them to `onPing`, not the thread). Runs are capped by `runs.max_duration` (default 120m, `-1` unlimited; `runContext`). UI: `Taskboard` strip above the lead thread, `SubagentTray` between thread and composer (running cards + "N finished"), and `/bots/:id/run/:chatId/agent/:agentId` is the read-only `SubagentPage` (shared `Thread`, Brief, Stop; the Chat tab stays lit).

After create, never `docker exec`, `docker cp`, or a published VNC port.

Container ID in the DB is the last box. `GetBot`/`ListBots` inspect Docker (and the `silo-{id}` name) and clear a vanished box. `StartBot` starts that ID if it still exists; it creates only when there is no ID or the box is gone. Do not trust a stored ID after a `podman rm`.

# Dev

## Commands

`make help` is the list; these are the ones you will actually need.

- `make build-cp` / `make build-all` / `make images` — `bin/silo`, worker, bridge; then bot + STDIO images.
- `make bot-image` (runs `build-worker` first) after worker, `botimage/`, or toolsgen changes; `make stdio-image` (runs `build-bridge`) for the bridge / `mcpimage/`. Neither touches containers: a running Bot keeps its old image until Container → Reset (or `podman rm -f silo-<id>`) and Start.
- `make db-up` / `db-down` / `db-psql` — dev Postgres (`silodb-postgres`, not `silo-*`, so `cleanup` spares it). You may start it; `make db-reset` drops the volume (destructive, only when asked).
- `make test` — `go test ./cmd/... ./internal/...` (never `./...`: it walks `data/`). Needs `make db-up`: `dbtest.New(t)` gives each test its own schema in `silo_test`; never open a DB by hand in a test.
- Postgres rejects NUL and invalid UTF-8 in `text`; `internal/db` scrubs every create/update, so do not bypass GORM with raw inserts. Run events order by `seq` (timestamps tie at µs), never `created_at`.
- `make proto` — `buf generate` (Go + TS) after any `.proto` change, then rebuild the CP and worker.
- `make cleanup` — `podman rm -f` every `silo-*` container. `make clean-images` drops the local images.
- `make dev` — tmux session with `watch-control` (watchexec, 750 ms debounce, SIGTERM + 5 s grace) and Vite; `make attach` reattaches.
- `make reset-data` — deletes `./data`; destructive, only when asked.

## Commits

Commit with **Conventional Commits** per [DEVELOPMENT.md § Commits](DEVELOPMENT.md#commits): `<type>(<scope>): <summary>`. Every commit made with a model's help carries an `Assisted-by: <model name>` trailer naming the model that made it (e.g. `Assisted-by: DeepSeek V4.1 Flash`). Do not spend too much time in loops around commits - it is fine to bundle features in a single commit if they are a big change, but describe it clearly. You should also look at and commit the user's changes rather than leaving things uncommited.

While changes are unpushed the log is yours to rewrite: if the user is not satisfied with a change, amend, rebase, squash, or reorder to fix it up cleanly instead of stacking `fix`/`wip` commits. Never rewrite pushed history.

## Who runs what

- **Never start the frontend or the control plane yourself.** The user owns those processes (`make dev` or their own tmux). Do not run `make dev` / `run-control` / `run-frontend` / `watch-control`, and do not kill or clean up their background processes. If `make dev` is not up but you need it for something (eg tests), FAIL early and tell the user to start it up.
- **You may** run builds (`make build-*`, `make images`), tests, `make proto`, and container cleanup (`make cleanup`, `make clean-images`).
- **You may** attach to the user's already-running tmux for debugging: inspect with `tmux ls` and `tmux capture-pane -p -t silo`, or attach (`make attach`) when you have a TTY. Do not start a second session under the same name.
- Do not run big command chains of tasks that take a long time to finish (especially ones that download things). Do them separately to avoid leaving a state where an unknown command in the middle is hung, and do not blindly supress the output of commands like builds that may get stuck.

Debug and test your stuff with chromium MCP for MAJOR CHANGES.
Use localhost as the actual URL of the Silo Agent, not 127.0.0.1. Something is wrong with the ip.
