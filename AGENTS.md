# Silo Agent

Token-conserving multi-user agent. Each **Bot** is a durable container with a GUI. Architecture: `docs/Description.md`. UI: `DESIGN.md`.

How to build and run: [DEVELOPMENT.md](DEVELOPMENT.md). The DB is Postgres 17 + pgvector (`database_url`, default the dev compose on `localhost:5433`); `docker-compose.dev.yml` runs only Postgres, never the CP. `Makefile` is the command surface — `make help` lists every target. Never start the dev servers yourself; see Dev below.

Operator config: [docs/CONFIGURATION.md](docs/CONFIGURATION.md). Koanf **defaults → `silo.yaml` → `SILO_*` env**. Nested keys use `__` (`SILO_PROVIDERS__OPENROUTER__API_KEY` → `providers.openrouter.api_key`). Admin Settings edits `silo.yaml` (form + YAML editor). Env still wins; the UI warns and disables those fields. Providers carry `api_key`/`base_url`/`cache`/`cache_ttl`; `models` is the allowlist, `model` the default (`provider/model`), `model_title` the title model. Default model when unset: `openrouter/openai/gpt-5.6-luna`. Default search engine when unset: `duckduckgo_scraper`.

The project should follow test-driven-development. For now end to end testing is not yet to be fully implemented, but the unit tests in Go should test as much as possible using the dummies.

## Shape

- **Control Plane (Go):** users, bots, secrets, skills (bodies on `data/skills/`; enablement in Postgres; `ListSkillFiles`/`ReadSkillFile` walk the CP volume, no worker), **security engine** (`internal/security` — catalog of connector.action → title/fields/default; `*` for files/desktop; each secret is `secrets.<name>` not `secrets.get`; unknown MCP actions get a generic prompt), **HTTP MCP client** (`internal/mcpx` — streamable HTTP over a URL or an injected transport), **STDIO MCP sidecars** (one isolated container per attached STDIO connector; `silo-mcp-bridge` **dials the CP** over ConnectRPC `MCPHost.Tunnel` with a per-attachment bridge token and raw-pumps JSON-RPC to its child; curated image or generic Node/`npx` command; structured argv, never a shell; no published port), **agent loop** (the modular `internal/llm` engine: providers `openrouter`/`openai` speak the OpenAI-compatible API, `anthropic` the native Messages API; model ids are `provider/model`; operator allowlist `models`, default `model`, chat override `chats.model`; the system prompt is a base `SYSTEM.md` plus ordered session providers in `internal/app/systemprompt.go` — connectors, skills, channels, then SOUL/MEMORY and the per-run channel note; blocks are ordered stable→volatile with provider cache breakpoints; bots get `list_models`/`switch_model` under the `model` rule), **web search** (`internal/search` — engine registry on the CP; `web_search` chat tool and `silo_runtime.web_search` share `web.search`; MCP stays Python-only), Docker lifecycle = create/start/stop/inspect only (bots and STDIO sidecars). Chat tools and Python `CallTool`/`GetSecret` share `authorizeAction`. Approval slip never dumps `args_json` (and redacts `desktop.type` text). `allow_once` is a valid vote. Connector tokens and extra headers stay on the CP. Reserved connector slugs: python, terminal, files, desktop, bot, secrets, skills, web, artifact, channels, chats, model. **Channels** are built-in adapters (`internal/channels`, Telegram via gotd MTProto) that talk to a Bot. One adapter instance is a `Channel` row (per bot, unique name); channel conversations are `Chat` rows tagged `channel_id`+`external_id` (web chats keep `channel_id=''`). Adapters own config (per-channel secrets live as `channel.<id>.<key>` Secret rows, hidden from the Secrets tab and `secrets.*`), dynamic state (`State`: info/QR/select for QR logins and chat pickers), and lifecycle. The Channels tab adds/edits them from adapter-declared fields, with sub-routes `/bots/:id/channels[/new[/:adapter]|/:channelID[/setup]]` so browser back works; `requires_target` adapters (Telegram) bind the row to exactly one chat picked in the Setup menu (`set_target` → `external_id`/`target_title`), and only that chat is read or written. Telegram bot accounts cannot enumerate dialogs (`messages.getDialogs` → `BOT_METHOD_INVALID`), so the picker lists chats the bot has seen (persisted in channel state) and accepts a manually entered `@username`/`t.me` link/id. Adapters declare interactive `Setup` actions (`pick`/`run`/`qr`) and an embedded `GUIDE.md`; a channel that still needs its target shows a blinking **Set up**. The `chats` tool asks the adapter for a channel conversation's history (Telegram `messages.getHistory`) so the Bot can see older messages; bot accounts are refused (`BOT_METHOD_INVALID`), so it falls back to the local run log (adapter flags `noHistory` per channel and stops retrying). `present`/`artifact` on a channel attach the real bytes (`workspaceAttachment`; a skill directory is zipped by `skillZipAttachment`), and the Telegram adapter uploads them with `uploader.FromBytes` + `.File`. A channel with `inbound=false` is send-only (tools only). Channel workers start from `reconcileChannels`; adapter `Start` is live-only — never backfill missed messages. The `channel` chat tool sends (default the origin channel; rule key `channels.<channelID>`); `chats` reads history through the adapter for channel conversations and the DB for web chats (rule `chats.read`); `silo_runtime.send_channel`/`read_chats` are the Python paths. `artifact` is one engine: the chat tool and Python `silo_runtime.artifact`/`CallTool` share `artifact.emit`, `describeArtifact` turns a dir-with-`SKILL.md` into a skill card or any file into a downloadable card, and `/artifacts/skill.zip` + `/artifacts/file` stream the bytes (cookie auth).
- **Worker (Go, inside Bot):** dials the CP. Local Unix-socket HTTP for Python tools (`get_secret`, `call`, desktop). `desktop.*` CallTool is a grant; the Worker runs look/click/type/key/scroll and strips type text before the RPC. Writes `/opt/silo/tools` from `SyncTools` and `/opt/silo/skills` from `SyncSkills` (empty those dirs; do not rmdir them — `/opt/silo` is root). `start.sh` mkdir+chowns both. Tunnels VNC and a console PTY. Desktop is Openbox + Thunar + mousepad + iron wallpaper (`botimage/`). Dock: Files, Terminal, Editor, Chromium. `start.sh` is root only to chown mounts and supervise; the worker, X stack, console PTY, and dock apps run as user `silo` (uid 1000) with passwordless sudo. `start.sh` starts the worker before the X stack so the bot is online without waiting for x11vnc. ConnectRPC bidi does not send headers until the first `Send` — `Commands` must heartbeat immediately or the CP treats the worker as offline until the 10s ticker. x11vnc uses `-speeds lan` (localhost tunnel; skip the link-speed probe). Double-click text in Thunar opens the editor.
- **Python in the Bot:** `exec_python` + `silo_runtime` + generated `tools.*`. Not the orchestrator. `toolsgen` escapes `\` and `"` in generated docstrings — a description ending in `"` must not become `""""` and SyntaxError the whole package import. A nonzero exit from `exec_python`/terminal returns the captured output (the traceback) as the result; never just `exit status 1`. Desktop GUI is first-class `look` / `click` / `type` / `key` / `scroll` (1600×900 X11; worker uses `scrot`/`xdotool`) — that is how the model clicks the machine. The same actions are on `silo_runtime` (`type_text`, not `type`) so a secret can be typed without a chat `type` call. `silo_runtime.web_search` is the Python path for CP web search (same `web.search` gate as the chat tool). Playwright `silo_runtime.chrome_page()` is page screenshots, mutating displayed HTML, and automated scripts — not the live click loop. The worker opens `silo-chromium` when `exec_python` mentions Playwright / `chrome_page` (and `chrome_page` hits `/v1/chrome/ensure` again). Do not ship `chrome_eval` / raw CDP helpers or `pyautogui`. SYSTEM.md must forbid the model `xdotool`, `pyautogui`, `playwright install`, and `apt` for a GUI driver. Computer-use shots attach without `detail: high` (OpenAI-family tiling breaks xy).
- **Frontend:** pnpm + React + Tailwind. ConnectRPC + VNC websocket. Right-side “Needs you” panels (permission vote and MCP OAuth) share `NeedYouSlip` — do not hand-roll a second folio drawer. Files / Desktop / Console when the worker is down share `NeedMachine` — do not hand-roll a second offline well. Files tree + preview is `FileBrowser` (`FsSource`: bot workspace, CP skill dir, or a workspace proposal prefix). Skill Hub / Admin library / Bot Skills / Artifact inspect share one hatch overlay. `artifact` is Allow and emits a thread `artifact` card (skill or file); a skill does not install until **Save skill** on the card (`SaveSkill`) copies the workspace dir to personal. Files show a type icon, subtitle, download, and a preview hatch. `Seeded` is embed library names only (`catalog.SeededName`); personal never gets the catalog chip.

UI: 64px rail on every page (Bots, Skills hub, crest switcher, +). Below 960 the rail is a 48px top bar (crests scroll sideways); the Bot page does not repeat name or crest (the rail mark is enough). Bot tabs always scroll instead of clipping, and below 960 they are icons with the label only on the active tab; Start/Stop is the power glyph. Approval is a right slip on wide and a bottom sheet below 960. Bottom: wrench Admin (admins only), user Account stub, Sign out. Crest is a picked shape+color (`color * 8 + shape`), not hashed from the name. Bot tabs are `/bots/:id/{run,desktop,files,connectors,skills,secrets,rules,container,settings}` labeled Chat, Desktop, Files, Connectors, Skills, Secrets, Rules, Container, Settings. Skills tab is a bindery switch per Library / Personal skill (unique `name` per bot); click the row to inspect in the hatch overlay. Skill Hub is `/skills` (Personal | Library; install URL or zip on Personal; click row inspects). Admin Skills Library takes the same URL or zip. `InstallSkill` archive uses the existing zip/tar extract (10 MB / 25 MB / 1000 files, no `..`). `catalog` chip only when `kind==library` and the name is in the embed. Files is a workspace `FileBrowser` (tree + preview); upload / new / delete stay on `FilesPane`. `artifact` peeks `SKILL.md` (that dir becomes a skill card) or stats a file (downloadable card with a type icon, download, and preview hatch; `artifact.emit` Allow; Save skill copies to personal). Rules is Bot / Secrets / per-connector folio sections (Allow/Ask/Deny); detach and delete-secret prune rules so ghosts do not stay. Desktop is a dropdown: the tab shows Desktop or Console for the open view (one underline across label + caret); the caret drops a folio menu with only the other view (`/bots/:id/console`, PTY in `/workspace` via the worker — not `podman exec`). The menu is portaled so the tab scroller does not clip it. Admin is `/admin/settings` (operator YAML form + editor, source chips, env warning, audit), `/admin/connectors` (Connectors Library: HTTP and STDIO MCP presets; default mode allow/ask/deny; Re-add defaults + row remove), `/admin/skills` (Skills Library: same re-add/remove; install from GitHub URL or zip), and `/admin/search-extract` (search engine picker writes `search.engine` in YAML; extract later). Library connector rows are templates — attach copies them onto the Bot. A Bot may attach the same preset more than once (GitHub, GitHub 2); each copy has its own OAuth and `tools.<slug>`. Bots can also add a custom MCP. Presets seed from `internal/catalog` (`connectors.json` + images; insert-if-absent by `seed_key`). Library presets carry a `prompt` (extra system-prompt guidance, injected only once the connector is authorized) and `auto_attach` (default false; `CreateBot` copies flagged presets exactly once, so a preset the human removes from a bot is never re-added). Skills seed from `internal/catalog/skills` into `data/skills/library/` (insert-if-absent). The catalog default skills (`product-self-knowledge` plus the `pdf` / `word` / `spreadsheets` / `presentations` / `images` family) auto-enable on new and existing bots; owners can disable any of them. Catalog `guide` is display-only copy on the Bot add screen (not a textarea, not stored on the row). Clicking a library preset shows mark + large name, a bindery-edged “Before you add” well, and collapsed Advanced settings; submit is `CreateBotConnector` with `source_id`. The add form is shared between Admin library and Bot custom. OAuth opens `{public_url}/oauth/callback`. The SDK tries CIMD, then a pre-registered `client_id`/`client_secret` on the connector, then DCR — GitHub has no `registration_endpoint`, so the library/custom form takes an optional OAuth Client ID and Secret (callback `{public_url}/oauth/callback`). MCP HTTP URLs keep their query — `?codemode=false` is real server config (it turns off Cloudflare’s code-mode `execute` wrapper and exposes the full tool list) — but the query/fragment must be stripped from the request handed to OAuth `Authorize`, because the SDK derives the resource identity (`resource=`, `.well-known` lookups) from it and Cloudflare validates that strictly (its issuer is `https://mcp.cloudflare.com`). `internal/mcpx` is a thin wrapper over the official go-sdk client — do not hand-roll the transport (handshake, sessions, SSE, `Mcp-Method`/`Mcp-Name` headers all live in the SDK). Connect tries Streamable HTTP (± trailing slash), then the legacy 2024-11-05 HTTP+SSE transport (spec back-compat; Cloudflare-style `/sse` URLs need it). Connector headers and OAuth (bearer + Authorize-on-401 + one retry via `GetBody`) live in one `RoundTripper` so both transports share them. Cloudflare (and similar) advertise RFC 9207 `iss` but omit it on the callback — fill from the authorize URL origin. A 401 with an empty body is a challenge; do not swallow the OAuth error behind `initialize: http 401: (empty)`. Container is Docker stats (CPU, RAM) plus Start/Stop (`GetContainer`). Create takes a description (shown on the folio). Settings edits name + description + the per-Bot default model via `UpdateBot`; below the form a Long-term memories panel lists `memories` (`ListMemories`) with an armed delete (`DeleteMemory`) (the picker offers the operator allowlist; a chat override still wins). Dangerous: `ResetContainer` is stop+rm (workspace bind stays; Start makes a new box); `DeleteBot` drops the box, the row, and `data/bots/<id>`. Second click, not `confirm()`. Chat is the chats list + thread (`/bots/:id/run/:chatId`). The first title is a short model name from the opening prompt (not the raw message); the sidebar can rename (`RenameChat`). A `chat_title` stream event updates the list and is not shown in the thread. Tools start collapsed. Markdown tables scroll inside the thread (`silo-md-table`); they must not widen the column. `present` of a user path is a folio (not collapsed). `present` of `bot/…` is a collapsed “Looked at …” row. The model must not retype it. A presented png/jpg/webp/gif is attached as pixels on the next completion so the model can see Chromium. Persist fetched blobs from `exec_python` to `/workspace`, then `present` — do not copy them through `write`. Thinking is a spinner only while `thinking_chunk`s are the live tail — a later tool/assistant event (or send end) becomes Thought; leaving `streaming` true keeps the spinner forever. Desktop is the hatch only. A connected worker is **online** (pine lamp), not idle. The CP holds the VNC and Console streams until a viewer attaches, then the Worker dials x11vnc or opens a PTY. Each hatch/console WebSocket gets a viewer ticket; closing an old socket must not clear a newer one (React Strict Mode remounts the hatch). VNC and console are separate lanes — both can stay up. Replacing a worker session must cancel any waiter on the old session. Sign-in must call `setSession` from the response (email + admin) or the session cookie is ignored. `StreamRun` persists every event, replays history, and accepts `after_event_id` so the client can reconnect without duplicates. Every string that is persisted or emitted is normalized to valid UTF-8 and capped on rune boundaries: a single invalid byte in a `RunEvent` makes protobuf replay fail, and the client then spins on an open run forever (surviving restarts) because it never sees the `done`. Interrupted runs get a synthetic `done` in `recoverOrphans`. Chat Stop is `StopRun` (that chat’s live run + worker `CancelCmd`); it is not Stop Bot. Commands carry `run_id`; children get `SILO_RUN_ID`. One live run per conversation: a new chat message while a run is active is injected into that run's inbox (`startOrInject`), not run in parallel; parallel runs across different conversations are allowed. The model ends a user-visible block with `<section_send />`; that finalizes a `section` event (its own chat bubble) and delivers it on a channel. A sentinel closed mid-tool-turn emits `section_live` (shown/delivered, not replayed as history). Channel runs deliver only sections — thinking/tool output stays in the log. If a message arrives while the box is down, the run starts the container and worker-backed tools wait (`waitWorker`) for the worker to connect. `startRun` always calls `ensureRunning`, which confirms the box with Docker even when a worker session exists — a session can outlive a container removed out of band, and trusting it would leave the Bot unreachable. Bot status is derived from remaining running runs and pending approvals. A Docker inspect error is not proof the box is gone — only not-found or a box whose `SILO_BOT_TOKEN` hash ≠ `bots.token_hash` clears the cached ID and `Drop`s. `live` and `ensureRunning` reload the bot row under the lifecycle lock; acting on a row loaded before a concurrent create drops the just-made box as a token mismatch and writes the old hash back. A stopped box keeps its ID. Stop is `docker stop`, not rm. `ResetContainer` is stop+rm and clears the ID. Persist a new token hash only after Create succeeds; a failed recreate plus `live()` adopting the leftover box is what makes the worker hammer 401s. Worker auth misses and rule lookups (no row = catalog default) use `Find`, not `First` — GORM `record not found` is not an error log. Desktop processes are fail-fast: if Xvfb/Openbox/x11vnc/worker dies, the container exits and `unless-stopped` recreates it. Chromium is a dock launcher (`silo-chromium`), not a supervised process. Chrome profile bind is `/home/silo/chrome-profile`. The wrapper is `--enable-low-end-device-mode` + 128MB disk cache + `--load-extension=/opt/silo/ubol`; site isolation stays on — do not launch raw `chromium`. Do not also Chrome-Web-Store force-install uBOL (that duplicates it). Managed policy sets page zoom to ~67% and uBOL lists (ads + cookie/overlay). If `exec_python` mentions Playwright / `chrome_page` and :9222 is down, the worker starts headed `silo-chromium` on `DISPLAY=:1` (not a start.sh child). Connectors are discovered as `import tools` in `exec_python`, not as extra OpenAI tools. Those calls emit `call` / `call_result` and render above the Python fold. Ctrl+C must `Hub.CloseAll` then `http.Server.Close` — never `Shutdown`. The hatch WebSocket is hijacked, so graceful Shutdown waits until a timeout (`context deadline exceeded`) and `signal.NotifyContext` eats extra SIGINTs.

## Two hops

1. **CP ↔ Worker:** ConnectRPC, Worker-initiated, bot token. Concurrent RPCs.
2. **Python ↔ Worker:** HTTP/JSON on `unix:///var/run/silo/worker.sock`.

File tools stay five: `read` (numbered lines; the Worker slices `offset`/`limit`, rejects binaries, and returns `next_offset`; displayed `N|` is the file's absolute line number), `write`, `patch` (exactly one `old_text` match), `delete` (recursive `Cmd_Remove`, refuses the workspace root), `grep` (ripgrep-only, `include` glob, `max_hits` cap, deterministic `--sort path`, heavy dirs pruned; runs without the shell so it emits no `tool_chunk`). A repeat guard short-circuits a 3rd identical `read`/`grep` in a run and resets on any mutating tool. Do not add a sixth unless a real loop needs it. `present` is a chat tool on the CP (shows a workspace file in the thread via `browse_file`); it is not a fifth worker file tool. A presented image is also attached as pixels on the next model turn so Chromium work can Perceive → Reason → Act → Verify — do not oneshot cookies+search with guessed labels. Scratch lives in `/workspace/bot`; user-facing files in `/workspace`. Chat uploads go to `/workspace/tmp` via the composer paperclip (ConnectRPC `PutFile`, 50 MB cap), carried as a `RunEvent.attachments` list persisted in `RunEvent.Meta`; `start.sh` wipes `/workspace/tmp` on every container start, session_start etc, so it is input only. The model is told the paths in `historyFromDB`; it chooses to `read`/`present`. `present` asks `browse_file` for up to 32 MB (worker `presentLimit`), while the Files tab previews at 2 MB (`browseLimit`) and uploads cap at 50 MB (`putLimit`). `present bot/…` is a collapsed “Looked at …” row, not a folio. The Files tab is a human browser (`mkdir` / `remove` / `put_file` / `browse_file` on the worker). Recreate the box after those worker cmds change.

Long-term memories are pgvector rows (`memories`, `vector(1536)`, per bot) behind `remember`/`recall`/`forget` (rules `bot.*`, default allow); `embedding_model` must be OpenAI-compatible (`llm.Embedder`; Anthropic cannot embed), and auto-recall puts close matches in the trailing prompt block once per run — never above a cache breakpoint. Vector `ORDER BY` goes through `Clauses(clause.OrderBy{Expression: …})`: GORM silently drops `Order(clause.Expr)`. SOUL and MEMORY live in Postgres (`bots.soul` / `bots.memory`), not on the box. Injected into the system prompt every run. Tools `soul` and `memory` write the DB (no worker hop). Model may write both; Settings can edit them. MEMORY cap is 8000 chars — over that the prompt and the tool tell the model to compact, they do not silent-truncate. ListBots omits the bodies; GetBot/UpdateBot include them.

After create, never `docker exec`, `docker cp`, or a published VNC port.

Container ID in the DB is the last box. `GetBot`/`ListBots` inspect Docker (and the `silo-{id}` name) and clear a vanished box. `StartBot` starts that ID if it still exists; it creates only when there is no ID or the box is gone. Do not trust a stored ID after a `podman rm`.

# Dev

## Commands

`make help` is the list; these are the ones you will actually need.

- `make build-cp` / `make build-all` / `make images` — `bin/silo`, worker, bridge; then bot + STDIO images (worker/bridge must exist before the image builds).
- `make rebuild MODE=cp|bot|stdio|all` — wraps `rebuild.sh`. `all` rebuilds everything and `rm -f`s every `silo-*` container; `cp`/`bot`/`stdio` leave containers alone.
- `make db-up` / `db-down` / `db-psql` — dev Postgres (`silodb-postgres`, not `silo-*`, so `cleanup` spares it). You may start it; `make db-reset` drops the volume (destructive, only when asked).
- `make test` — `go test ./cmd/... ./internal/...` (never `./...`: it walks `data/`). Needs `make db-up`: `dbtest.New(t)` gives each test its own schema in `silo_test`; never open a DB by hand in a test.
- Postgres rejects NUL and invalid UTF-8 in `text`; `internal/db` scrubs every create/update, so do not bypass GORM with raw inserts. Run events order by `seq` (timestamps tie at µs), never `created_at`.
- `make proto` — `buf generate` (Go + TS) after any `.proto` change, then rebuild the CP and worker.
- `make cleanup` — `podman rm -f` every `silo-*` container. `make clean-images` drops the local images.
- `make dev` — tmux session with `watch-control` (watchexec, 750 ms debounce, SIGTERM + 5 s grace) and Vite; `make attach` reattaches.
- `make reset-data` — deletes `./data`; destructive, only when asked.

## Commits

Commit with **Conventional Commits** per [DEVELOPMENT.md § Commits](DEVELOPMENT.md#commits): `<type>(<scope>): <summary>`. Every commit made with a model's help carries an `Assisted-by: <model name>` trailer naming the model that made it (e.g. `Assisted-by: DeepSeek V4.1 Flash`). Do not spend too much time in loops around commits - it is fine to bundle features in a single commit if they are a big change, but describe it clearly. You should also look at and commit the user's changes rather than leaving things uncommited.

While changes are unpushed the log is yours to rewrite: if the user is not satisfied with a change, amend, rebase, squash, or reorder to fix it up cleanly instead of stacking `fix`/`wip` commits. Never rewrite pushed history.

## Who runs what

- **Never start the frontend or the control plane yourself.** The user owns those processes (`make dev` or their own tmux). Do not run `make dev` / `run-control` / `run-frontend` / `watch-control`, and do not kill or clean up their background processes. If `make dev` is not up but you need it for something (eg tests), FAIL early and tell the user to start it up.
- **You may** run builds (`make build-*`, `make images`), tests, `make proto`, and container cleanup (`make cleanup`, `make clean-images`).
- **You may** attach to the user's already-running tmux for debugging: inspect with `tmux ls` and `tmux capture-pane -p -t silo`, or attach (`make attach`) when you have a TTY. Do not start a second session under the same name.
- Do not run big command chains of tasks that take a long time to finish (especially ones that download things). Do them separately to avoid leaving a state where an unknown command in the middle is hung, and do not blindly supress the output of commands like builds that may get stuck.

## Debug via Chromium

Debug and test your stuff with chromium MCP for MAJOR CHANGES.
Use localhost as the actual URL of the Silo Agent, not 127.0.0.1. Something is wrong with the ip.
**DO NOT** Start another automation browser, only use your mcp, never start some custom aah browser in some random aah folder
If the chromium MCP is offline, just tell the user. It usually simply means this task will be tested manually.
