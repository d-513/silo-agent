# Synchronous vs asynchronous delegation between LLM agents, and asynchronous inter-agent messaging

Scope: (a) sync "subagent as a blocking tool call", (b) async spawn-and-continue / end-turn-and-wake, (c) messaging between running agents (mailboxes, steering, interrupts). Frontier-era work only (2025–2026); one Dec-2024 paper is flagged as borderline-historical. Research date 2026-11-17.

Source quality note: arXiv entries below were read on arxiv.org (abstract and, where marked, HTML full text). Vendor claims (Kimi, Cursor, Cognition, Anthropic) are self-reported and not independently evaluated. A few arXiv IDs carry 2026 dates later than my training data; I read them directly on arxiv.org, but I could not verify peer review.

## 1. Research on asynchronous agent reasoning / execution

### Takeaway
The research signal splits cleanly. Making the *orchestrator itself* non-blocking (fork-join inside one model, async function calls, trained parallel orchestrators) reliably cuts latency (roughly 1.4x–5x, or 28% on critical path) at equal or better accuracy, **but only when trained or scaffolded for it, and with explicit rewards against both "serial collapse" and "spurious parallelism"**. Benchmarks that hand a lead agent subagent results *one at a time while it keeps working* find off-the-shelf frontier models do slightly worse than when results arrive as one batch.

### Cited Findings
**AsyncThink (Microsoft Research, fork-join thinking)**
- "The Era of Agentic Organization: Learning to Organize with Language Models", Chi, Dong, Dong, Hao, Wu, Huang, Wei; arXiv:2510.26658, submitted 2025-10-30. One model plays organizer and workers; organizer actions are Think / Fork / Join / Answer. — [arXiv abs](https://arxiv.org/abs/2510.26658)
- Protocol is genuinely non-blocking: after `<FORK-i>` the organizer keeps generating its own tokens; it pauses only at a `<JOIN-i>` whose worker has not finished; the worker's `<RETURN>` takeaways are spliced into the organizer's context between JOIN tags. — [arXiv HTML v1](https://arxiv.org/html/2510.26658v1)
- RL reward = accuracy + λ·thinking-concurrency reward R_η (η = mean active workers / pool size, clipped at threshold τ "to limit reward hacking"), with a constant format penalty for duplicate fork ids, pool overflow, joining a never-forked sub-query, or stopping without an answer. — [arXiv HTML v1](https://arxiv.org/html/2510.26658v1)
- Results (Qwen3-4B): AIME-24 38.7% at critical-path latency 1468 vs parallel thinking 38.7% at 2048 and sequential 35.3% at 2048; AMC-23 73.3% @1459.5 vs parallel 72.8% @2031.4; "28% lower inference latency compared to parallel thinking". Multi-solution Countdown "All Correct" 89.0% vs 68.6%/70.5%. Out-of-domain Sudoku 89.4% @2853 vs parallel 84.2% @3694.7, sequential 65.7% @2055.5. — [arXiv HTML v1](https://arxiv.org/html/2510.26658v1); [abs](https://arxiv.org/abs/2510.26658)
- Ablations: without RL the format alone gives 0.0 (Countdown) / 3.6 (AMC-23); without format SFT the model forks but never overlaps (η = 1/c); without the concurrency reward accuracy drops (85.3/71.3) and latency rises. An extra "leverage" reward caused instability and "sometimes collapsed to near-sequential behavior." Latency is a theoretical critical-path measure, not wall-clock; authors note communication overhead at Join "is non-trivial." — [arXiv HTML v1](https://arxiv.org/html/2510.26658v1)
- Authors propose recursive organization (workers become sub-organizers) as future work. — [arXiv 2510.26658 PDF](https://arxiv.org/pdf/2510.26658)

**Asynchronous function calling**
- AsyncLM (HISTORICAL/borderline: Dec 2024, GPT-4o era): "Asynchronous LLM Function Calling", Gim, Lee, Zhong; arXiv:2412.07017, 2024-12-09. LLM keeps generating while calls run; completions arrive as *interrupts* expressed in a token-efficient DSL (CML). 1.6x–5.4x lower end-to-end latency vs synchronous calling on BFCL tasks; fine-tuned Llama keeps accuracy; GPT-4o handled async calls without fine-tuning; small models need fine-tuning. — [arXiv abs](https://arxiv.org/abs/2412.07017)
- AsyncFC: "Concurrency without Model Changes: Future-based Asynchronous Function Calling for LLMs", Feng, Mao, Dutta, Gonzalez; arXiv:2605.15077, v1 2026-05-14, v2 2026-10-09. Pure execution-layer framework: decoding overlaps execution, independent calls run in parallel; the LLM reasons over *symbolic futures* for unresolved results; no fine-tuning and no change to the standard synchronous function-calling protocol. 1.4x end-to-end speedup on coding tasks at preserved accuracy. — [arXiv abs](https://arxiv.org/abs/2605.15077)

**Trained parallel orchestrators (Kimi PARL / Agent Swarm)**
- Moonshot's Kimi K2.5 (blog, ~Jan 2026): PARL = Parallel-Agent RL; a *trainable orchestrator* decomposes into parallelizable subtasks run by "dynamically instantiated, frozen subagents"; reward = task outcome + instantiation (parallelism) reward + sub-agent finish-rate reward, the auxiliary weights annealed to zero. Up to 100 sub-agents, up to 1,500 tool calls/steps; "up to 4.5x" faster than single agent; internal evals "80% reduction in end-to-end runtime." — [Kimi K2.5 blog](https://www.kimi.com/blog/kimi-k2-5)
- Two named failure modes: **serial collapse** ("the orchestrator defaults to single-agent execution despite having parallel capacity") and **spurious parallelism** (reward hacking by spawning many subagents without meaningful decomposition; countered by the finish-rate reward). Metric is **Critical Steps** (sum over stages of the max steps among parallel branches): "spawning more subtasks only helps if it shortens the critical path." — [Kimi K2.5 blog](https://www.kimi.com/blog/kimi-k2-5); technical report arXiv:2602.02276 (not read directly; equations unverified) — [emergentmind entry](https://api.emergentmind.com/papers/2602.02276)
- Kimi's help page later describes up to 300 sub-agents and says the swarm runs on Kimi K3. — [Kimi Agent Swarm help](https://www.kimi.ai/help/agent/agent-swarm)

**Benchmarks of async result handling by a lead**
- Async-RBench: "Benchmarking Asynchronous Task Execution in LLM Agents", Zeng et al. (UESTC); arXiv:2610.32429v1, 2026-10-23. 200 tasks (from Terminal-Bench, Gaia2, OSWorld, SWE-bench, MultiAgentBench) in 8 scenarios; subagents run concurrently in isolated workspaces; a controller releases each result under scenario conditions. Compares **Async** (results arrive individually while the main agent keeps working) vs **Batched** (all results delivered together after every subagent finishes). — [arXiv HTML](https://arxiv.org/html/2610.32429v1)
- Every one of nine agents scored lower Async than Batched (1.0–6.0 points); mean 29.7% → 26.0%. Examples: Claude Sonnet 5 42.3 → 38.2; GPT-5.6 Terra 41.3 → 38.8; GPT-5.6 Luna 40.2 → 34.3; DeepSeek V4 Pro 35.7 → 34.7; Kimi K2.5 23.2 → 19.2; Gemini 3 Flash-H 18.3 → 12.3. Lowest Dynamic-Replanning scores: "Duplication and replay" (mean 8.6) and "Subagent failure" (12.2). Prompting a full plan rebuild after every result raised DRS 2.6–3.5 points at +7.5–10.2% model calls. Authors caution they do not establish that async delivery *caused* the failures. — [arXiv HTML](https://arxiv.org/html/2610.32429v1)
- ClawArena-Team (Xiong et al.; arXiv:2606.31174, 2026-06-30): 41 scenarios testing one LLM as manager of a fixed subagent pool; no model exceeds 50% workspace-permission precision ("privilege granting rather than perception" is the bottleneck); scores cluster within 9.9 points while orchestration behaviours diverge by over an order of magnitude; API cost varies >100x while score varies <4x. — [arXiv abs](https://arxiv.org/abs/2606.31174v1)
- Serving-side: latency-aware scheduling of multi-agent workflows on heterogeneous GPUs reports up to 36.8% lower makespan, 25.9% lower p95 latency under bursts (arXiv:2609.03335). — [arXiv abs](https://arxiv.org/abs/2609.03335); LAMaS optimises the critical execution path (arXiv:2601.10560). — [arXiv abs](https://arxiv.org/abs/2601.10560)

**Interrupt-driven continuous agents**
- "Never Stop Thinking: Continuous-Time Language Agents", Li & Shi; arXiv:2609.17416, 2026-07-11. An unmodified text model under "a lightweight interrupt-and-resume orchestrator" (async tool results and user barge-ins as interrupts) cut live-pipeline latency 19% overall, about half in the targeted regime; trained streaming completion rose 48% → 73±5%. Warns that LLM judges reward visible reasoning: a large judged advantage reversed sign under an independent judge. — [arXiv abs](https://arxiv.org/abs/2609.17416)

### Inferences
- Latency wins from async come from overlapping *independent* work on the critical path; every paper measures critical path or wall-clock, not accuracy, as the main gain. Accuracy gains appear only where breadth matters (multi-solution Countdown, wide search).
- Untrained frontier models are *not* better at async integration than at batched integration (Async-RBench). So a product that wakes a lead per-result should expect a small quality cost unless it batches, or rebuilds the plan explicitly on each arrival.
- "Serial collapse" (Kimi) and AsyncThink's "near-sequential" collapse are the same phenomenon: without explicit pressure, models default to blocking. This matches Cursor's "agents rarely used the wait tool" in reverse — models do not naturally manage concurrency either way without structure.

### Gaps
- I did not read the PARL technical report (arXiv:2602.02276) directly; reward equations and BrowseComp/WideSearch numbers are unverified.
- No paper found that directly compares, in the same harness, "lead blocks on subagent" vs "lead ends its turn and is woken" on cost and quality for general agent tasks.
- No 2025–2026 paper found on *async multi-agent RL where several learned agents message each other* beyond the orchestrator-only setups above.

## 2. What Anthropic and production builders say (Anthropic Research, Claude Code, Codex, Cursor, Cognition/Devin)

### Takeaway
Anthropic's Research system shipped **synchronous** subagents and named that as the bottleneck, but declined async because of "result coordination, state consistency, and error propagation." Since then Claude Code has moved hard to async: subagents now **start in the background by default** and report through a completion notification; agent teams add mailboxes and a shared task list. Builders converge on: async for read-heavy fan-out, single-threaded writes, wake-on-completion (not polling), hierarchy over flat peers, and handoffs as one rich message.

### Cited Findings
**Anthropic Research system (2025-06-13)**
- "Currently, our lead agents execute subagents synchronously, waiting for each set of subagents to complete before proceeding." "Synchronous execution creates bottlenecks" — the lead can't steer subagents and subagents can't coordinate. "Asynchronous execution would enable additional parallelism … this asynchronicity adds challenges in result coordination, state consistency, and error propagation across the subagents." — [Anthropic Engineering, "How we built our multi-agent research system"](https://www.anthropic.com/engineering/multi-agent-research-system)
- Opus 4 lead + Sonnet 4 subagents beat single-agent Opus 4 by 90.2% on the internal research eval; agents use ~4x chat tokens and multi-agent ~15x; parallel subagents + parallel tool calls "cut research time by up to 90% for complex queries"; recommends subagents write to external stores and "pass lightweight references back to the coordinator." — [same](https://www.anthropic.com/engineering/multi-agent-research-system)

**Claude Code subagents (docs, read 2026-11-17)**
- "Foreground subagents block the main conversation until complete … Background subagents run concurrently while you continue working." "With nothing configured, a subagent that Claude spawns from your main conversation starts in the background." Waiting is the opt-in (`CLAUDE_CODE_FORK_SUBAGENT=0`, or `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`). — [Claude Code docs: Subagents](https://code.claude.com/docs/en/sub-agents)
- "A background subagent's results reach Claude as a completion notification in a later turn," marked as an automated event, not a user message; if asked first, Claude reports the subagent is still running. — [same](https://code.claude.com/docs/en/sub-agents)
- Resume/steer: `SendMessage` to a completed subagent resumes it in the background with full history; a subagent stopped by the user is not auto-resumed (message refused, "agent was cancelled"); `SendMessage` refuses delivery if a newer agent took the name (guards against misdelivery). Background subagents get a reduced tool set and surface every permission prompt in the main session, naming the subagent. Agent messages never count as user approval. — [same](https://code.claude.com/docs/en/sub-agents)

**Claude Code agent teams (experimental; docs read 2026-11-17)**
- Lead + teammates (each a full session with its own context) + shared task list + mailbox (one JSON inbox file per agent). "Automatic message delivery … The lead doesn't need to poll for updates." "Idle notifications: when a teammate finishes and stops, it automatically notifies the lead and includes its final answer"; an API-error stop notifies the lead with the error. Task claiming "uses file locking to prevent race conditions." — [Claude Code docs: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Guidance: "Agent teams add coordination overhead and use significantly more tokens … For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective." Start with 3–5 teammates; 5–6 tasks per teammate; "Two teammates editing the same file leads to overwrites." "Letting a team run unattended for too long increases the risk of wasted effort." — [same](https://code.claude.com/docs/en/agent-teams)
- Documented failure modes: the lead "starts implementing tasks itself instead of waiting for teammates" (fix: tell it to wait); "the lead can stop early … deciding the team is finished before all tasks are actually complete"; teammates "stop after encountering errors instead of recovering"; task status lags and blocks dependents; after `/resume` the lead may message teammates that no longer exist; no nested teams; an in-process teammate's background work "can't outlive the lead's process." — [same](https://code.claude.com/docs/en/agent-teams)
- Cache cost: an in-process teammate's requests get a 5-minute cache TTL by default (1h via `subagentPromptCacheTtl`, billed higher). — [same](https://code.claude.com/docs/en/agent-teams)

**OpenAI Codex subagents (docs, undated page)**
- Spawned on request or by AGENTS.md/skills; the prompt can say whether to wait for all agents; on completion the main thread gathers summaries into one response. Users can ask Codex to steer a running subagent, stop it, or close finished threads; concurrency capped by `agents.max_concurrent_threads_per_session` (alias `agents.max_threads`). Recommends parallel agents for read-heavy work (exploration, tests, triage, summarization) and caution for write-heavy parallel work because concurrent edits conflict. — [OpenAI Codex docs: Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) (redirected from developers.openai.com/codex/subagents)
- User steering in Codex: secondary sources report "steer" (inject into the current turn) vs "queue" (next turn) modes and a Follow-up setting; a community report says steers apply only after the current turn ends — conflicting, unverified against official docs. — [OpenAI community](https://community.openai.com/t/a-practical-codex-app-steer-workflow-splitting-a-task-into-staged-follow-ups/1377757); [remio.ai on Codex 0.163.0](https://www.remio.ai/post/openai-codex-0-163-0-turns-the-cli-into-a-live-control-surface)

**Cursor long-running agents**
- "Scaling long-running autonomous coding" (Wilson Lin, 2026-01-14): flat peers self-coordinating through a shared file with locks failed — "Agents would hold locks for too long, or forget to release them entirely"; "Twenty agents would slow down to the effective throughput of two or three"; optimistic concurrency was "simpler and more robust, but there were still deeper problems"; "With no hierarchy, agents became risk-averse." Planners create tasks (and spawn sub-planners); workers "don't coordinate with other workers"; a judge decides whether to continue and "the next iteration would start fresh." Next step stated: "Planners should wake up when their tasks complete to plan the next step." Dropped integrator ("created more bottlenecks than it solved"). "Many of our improvements came from removing complexity." — [Cursor blog](https://cursor.com/blog/scaling-agents)
- "Towards self-driving codebases" (2026-02-05): "We tried giving agents a tool to explicitly wait on another agent's work, but they rarely used it." Workers write "a single handoff that the system submits to the planner that requested the task" containing what was done plus "notes, concerns, deviations, findings"; "The planner receives this as a follow-up message" and a "done" planner "continues to receive updates." Failures: lock contention ("20 agents would slow to the throughput of 1-3"), "many agents would pile on and trample each other trying to fix the same issue," a continuous executor "given too many roles," a balanced judge/planner design "bottlenecked by the slowest worker," and 100%-correct-per-commit causing serialization. Peak ~1,000 commits/hour over 10M tool calls in a week. — [Cursor blog](https://cursor.com/blog/self-driving-codebases)

**Cognition / Devin**
- "Don't Build Multi-Agents" (Walden Yan, 2025-06-12): share full context/traces; subagents given only their subtask make conflicting implicit decisions (Flappy Bird example). — [Cognition blog](https://cognition.ai/blog/dont-build-multi-agents)
- "Multi-Agents: What's Actually Working" (2026-04-22): works when "multiple agents contribute intelligence to a task while writes stay single-threaded"; manager Devin can "spawn child Devins … and coordinate their progress through an internal MCP"; cross-agent communication "doesn't happen by default" because models weren't trained for it; "Agents assume they share state with their children when they don't"; managers "default to being overly prescriptive"; forking full context to a "smart friend" is "a reasonable 80/20." Prefers "map-reduce-and-manage"; swarms "mostly a distraction." The post does not discuss sync vs async. — [Cognition blog](https://cognition.com/blog/multi-agents-working)

### Inferences
- The industry trajectory since mid-2025 is from blocking delegation (Anthropic Research, June 2025) to wake-on-completion delegation (Claude Code background default; Cursor handoffs as follow-up messages; Codex threads). The "coordination / state consistency / error propagation" risks Anthropic named are handled in practice by: isolating workers (own context, own repo copy), returning one structured handoff, keeping writes single-owner, and delivering completion as a system event rather than having the lead poll.
- Peer-to-peer messaging is the least validated piece: Claude Code ships it as experimental with a list of coordination failures; Cognition says models are not trained to communicate; Cursor found workers did best *not* talking to each other.

### Gaps
- Google Jules, Cursor's in-IDE background agents product docs, and Devin's child-session mechanics (whether the manager blocks) were not checked in primary sources within this budget.
- No Simon Willison or Latent Space write-up was retrieved; no quantitative production data (e.g., % of runs where async beat sync) from any vendor.
- The Anthropic Research post has not (as far as found) been updated to say whether Research moved to async.

## 3. Does mid-run messaging to a running agent (steering, follow-ups) help or hurt?

### Takeaway
It depends on *what* is sent and *when*. A real change of goal delivered mid-run helps compared with ignoring it, and the strongest models handle even late updates well; but every study finds integration is hard, smaller models get entangled in stale state, late updates to a reasoning model can cost up to 60%, and unsolicited result arrivals (async subagent returns) slightly lower success versus batching. Wake-on-completion is preferred to polling in every production system examined.

### Cited Findings
- InterruptBench ("When Users Change Their Mind: Evaluating Interruptible Agents in Long-Horizon Web Navigation", Zou et al.; arXiv:2604.00892, 2026-04-01): WebArena-Lite, interruptions of type addition / revision / retraction injected at 60% of trajectory by default; six backbones (Claude Haiku/Sonnet/Opus 4.5, Qwen3-235B, DeepSeek-V3.1, Mistral-Large-3). — [arXiv HTML](https://arxiv.org/html/2604.00892v1)
  - Multi-turn updates (success %, n = 0→3 updates): Opus 4.5 5.45 → 21.21 → 36.36 → 41.82; Sonnet 4.5 4.24 → 41.21 at n=3; Mistral-Large-3 3.03 → 13.94; DeepSeek-V3.1 21.21 at n=2 then 20.61 at n=3 (later updates interfering). — [same](https://arxiv.org/html/2604.00892v1)
  - Timing: Opus does *better* with late interruptions (~47% at 20% vs ~57% at 80%); Haiku drops from ~44% (20%) to ~24% (80%); authors: smaller models "get entangled with the earlier, now-stale state." — [same](https://arxiv.org/html/2604.00892v1)
  - Cost: additions add tokens (Haiku +1,699, Sonnet +671); revisions/retractions mostly *reduce* actions (Opus −4.37 on revision; −1.72 to −8.13 on retraction). Failure modes: stale assumptions kept and reported, updates never integrated, prolonged unproductive re-planning, a few previously successful episodes broken by the interruption. — [same](https://arxiv.org/html/2604.00892v1)
- "Are Large Reasoning Models Interruptible?" (Wu, Miroyan, Chan, Darrell, Norouzi, Gonzalez; arXiv:2510.11713, 2025-10-13, v4 2026-06-01, ICML 2026): static evals overestimate robustness; performance drops "by up to 60%" when updates arrive late in reasoning; failure modes "reasoning leakage" (unfinished reasoning folded into the answer), "panic" (abandoning reasoning under time pressure), "self-doubt" (degrading while incorporating an update). — [arXiv abs](https://arxiv.org/abs/2510.11713)
- Async-RBench: results arriving one-by-one while the lead works lowered success for all nine agents (mean 29.7% → 26.0%) versus batched delivery. — [arXiv HTML](https://arxiv.org/html/2610.32429v1)
- Never Stop Thinking: interrupt-and-resume on an unmodified model cut latency 19% (voice setting). — [arXiv abs](https://arxiv.org/abs/2609.17416)
- Anthropic named the *inability* to steer as a cost of sync subagents ("lead agent cannot steer subagents"). — [Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
- Claude Code docs advise "Monitor and steer … redirect approaches that aren't working," and a message from the lead wakes a teammate stuck waiting to retry an API call so it retries at once. — [Claude Code docs: Agent teams](https://code.claude.com/docs/en/agent-teams)
- Polling vs wake: Claude Code agent teams deliver messages automatically ("doesn't need to poll"); subagent results come "as a completion notification in a later turn." — [Agent teams](https://code.claude.com/docs/en/agent-teams); [Subagents](https://code.claude.com/docs/en/sub-agents). Cursor: an explicit wait tool was "rarely used"; handoffs arrive as follow-up messages; wake-on-completion named as the target. — [self-driving codebases](https://cursor.com/blog/self-driving-codebases); [scaling agents](https://cursor.com/blog/scaling-agents)
- Cognition's "smart friend" works better when the primary is told to "investigate this file and ask again later" than when it guesses. — [Cognition blog](https://cognition.com/blog/multi-agents-working)

### Inferences
- Steering is net-positive when it carries *new information the agent needs* (goal change, a correction); unsolicited status/result pings that arrive mid-reasoning add integration burden with a measurable cost. Design implication: deliver subagent results at turn boundaries (or batched), not injected mid-turn; let the human's own corrections in immediately.
- The cost of a "sleeping" lead is mostly a full turn per wake (context re-read, cache misses past TTL — Claude Code's 5-minute default for teammates). Wake-on-completion with debouncing/batching amortises this; polling multiplies it. No paper quantified this directly.
- Strong models benefit from later, better-informed updates; weaker ones should get updates early or be restarted fresh — suggests choosing the "inject vs restart" policy by model capability.

### Gaps
- No controlled study found measuring token/latency cost of polling vs notification for an LLM lead.
- No study found on steering messages *between agents* (lead → running subagent) specifically, as opposed to human → agent updates.

## 4. Failure modes specific to async delegation

### Takeaway
The recurring list across papers and production: stale results acted on as current, duplicate/replayed reports, subagent failures not handled, lead ending before results are integrated (or starting the work itself), lock/contention collapse and trampling on shared state, conflicting implicit decisions from parallel writers, orphaned workers after resume/restart, and degenerate concurrency (serial collapse / spurious parallelism).

### Cited Findings
- **Stale / deferred results treated as final; duplicates; subagent failure:** Async-RBench lists "execution-state confusion, such as using a deferred result as if it were final," mishandling "stale updates and duplicate reports," ending the run before subagent artifacts are integrated, goal drift (fabricating a missing receipt), missed global constraints (plans that pass local checks but jointly exceed a budget). Lowest scores: duplication/replay (8.6), subagent failure (12.2). — [arXiv 2610.32429](https://arxiv.org/html/2610.32429v1)
- **Stale state after an update:** InterruptBench case study keeps an old origin and reports on it. — [arXiv 2604.00892](https://arxiv.org/html/2604.00892v1)
- **Race conditions / locks on shared state:** Cursor: locks held too long or never released, agents failing while holding locks, 20 agents at the throughput of 1–3; many agents "pile on and trample each other trying to fix the same issue"; agents "touch the same file or refactor the same code." Mitigations: optimistic concurrency, hierarchy, scratchpad "rewritten versus being appended to," workers pull latest repo on follow-up, tolerate a small error rate. — [Cursor scaling agents](https://cursor.com/blog/scaling-agents); [self-driving codebases](https://cursor.com/blog/self-driving-codebases). Claude Code uses file locking for task claims and warns same-file edits overwrite. — [Agent teams](https://code.claude.com/docs/en/agent-teams)
- **Lead losing track / acting prematurely:** Claude Code: lead implements tasks itself instead of waiting; lead declares the team finished early; task status lags and blocks dependents. — [Agent teams](https://code.claude.com/docs/en/agent-teams). Cognition: "Agents assume they share state with their children when they don't." — [Cognition](https://cognition.com/blog/multi-agents-working)
- **Orphaned workers:** Claude Code: after `/resume` the lead may message teammates that no longer exist; orphaned tmux sessions; background work can't outlive the lead's process; `SendMessage` refuses a name now held by a newer agent. — [Agent teams](https://code.claude.com/docs/en/agent-teams); [Subagents](https://code.claude.com/docs/en/sub-agents)
- **Error propagation:** Anthropic names it as a reason not to go async. — [Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system). Claude Code: teammates "stop after encountering errors instead of recovering"; API-error stops are reported to the lead with error text. — [Agent teams](https://code.claude.com/docs/en/agent-teams)
- **Conflicting implicit decisions by parallel writers:** Cognition's Flappy Bird example; fix is single-threaded writes. — [Don't build multi-agents](https://cognition.ai/blog/dont-build-multi-agents); [What's working](https://cognition.com/blog/multi-agents-working)
- **Degenerate concurrency:** serial collapse and spurious parallelism (Kimi PARL) — [Kimi K2.5 blog](https://www.kimi.com/blog/kimi-k2-5); AsyncThink's near-sequential collapse and concurrency-reward hacking (τ cap) — [arXiv 2510.26658 HTML](https://arxiv.org/html/2510.26658v1)
- **Over-structure bottlenecks:** Cursor's integrator and slowest-worker bottleneck; "Too little structure and agents conflict … Too much structure creates fragility." — [Cursor scaling agents](https://cursor.com/blog/scaling-agents)
- **Permission/privilege mistakes by a manager:** no model above 50% workspace-permission precision. — [ClawArena-Team](https://arxiv.org/abs/2606.31174v1)

### Inferences
- Most async failure modes are classic distributed-systems problems (stale reads, duplicate delivery, lost workers, lock contention) showing up in a component — the LLM lead — that does not reliably apply idempotency or freshness checks. Mitigations that live in code (dedupe by worker id, mark results reported once, cancel children on lead stop, refuse delivery to a reused name, structured single handoff) are more dependable than prompting the lead to be careful.
- A per-result "rebuild the plan" prompt buys a few points (Async-RBench) at ~8–10% more calls; batching results at a turn boundary is a cheaper way to get most of the batched-mode advantage.

### Gaps
- No quantitative production data on how often orphaned or duplicated subagents occur.
- No 2025–2026 study isolating "state consistency" failures on a shared filesystem across concurrent LLM agents beyond Cursor's qualitative reports.
